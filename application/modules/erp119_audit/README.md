# Журнал действий (erp119_audit)

Отвечает на вопрос «кто, когда и что изменил» — требование производственного
аудита: партия, норма расхода, производственный заказ должны иметь историю.

Раньше в проекте была заглушка `application/classes/Audit.php`: вызовы
`Audit::log()` со всей системы уходили в файловый лог и нигде не сохранялись.
Теперь эти же вызовы попадают в журнал, а событийная шина (erp208) служит
источником записей для тех действий, которые модули и так публикуют.

## Что внутри

| Слой | Файлы |
| :--- | :--- |
| Таблицы | `erp_119_audit_log` (секции по месяцам, append-only), `erp_119_audit_cursors` (указатель чтения шины), `erp_119_audit_settings` (названия сущностей, аудит просмотров) |
| Миграции | `001` таблицы и секции, `002` справочник сущностей, `003` след события шины (`event_id`) и уникальность внутри секции |
| Сервисы | `Service_Erp119_Journal` (запись, сравнение до/после, маскирование секретов, файл-страховка), `Service_Erp119_Mapper` (событие → запись), `Service_Erp119_Query` (лента, статистика, история объекта), `Service_Erp119_Partitions` (секции и срок хранения), `Service_Erp119_Export` (CSV) |
| Контроллеры | `Erp119\Index` (сводка), `Erp119\Journal` (лента, запись, история объекта, выгрузка), `Erp119\Partitions` (обслуживание секций), `Erp119\Api` (JSON), `Erp119\Widget` (виджеты) |
| Задачи | `bin/console erp119:sync`, `bin/console erp119:partitions` |
| Права | `erp119_audit.view` (чтение), `erp119_audit.export` (выгрузка), `erp119_audit.manage` (секции) |

## Как запись попадает в журнал

1. **Явный вызов из сервиса модуля** — основной путь:

   ```php
   Service_Erp119_Journal::instance()->change('tech_card', $card->uuid, 'update', $before, $after, array(
       'entity_label' => $card->title,
       'message'      => 'Изменена техкарта',
   ));
   ```

   Метод сам сравнивает наборы значений (`diff()`), пишет только реальные
   изменения и возвращает `NULL`, если изменений нет (нажатие «Сохранить»
   без правок в журнал не попадает).

2. **Совместимость со старым `Audit::log()`** — четыре исторических формата
   вызова разбираются в `Service_Erp119_Journal::legacy()`; файловый лог
   сохраняется как зеркало. Модулям ничего менять не нужно.

3. **События шины (outbox)** — модули публикуют события
   (`erp228.card.status`, `erp301.contract.updated`, …), шина складывает их
   в `erp_208_events`, а задача `erp119:sync` дочитывает новые строки по
   указателю и превращает в записи журнала по конвенции имени
   `<модуль>.<сущность>.<действие>`. Исключения и шум описаны в
   `config/erp119_audit.php` → `event_rules` / `ignore_events`.

   Перенос идемпотентен: у записи хранится номер события шины (`event_id`),
   поэтому повторное чтение с начала (`erp119:sync --reset` — например, после
   правки правил разбора) не задваивает журнал. Итог прогона показывает
   четыре числа: прочитано, записано, без правил, уже было; для событий без
   правила печатается список имён (по нему видно, что дописать в `event_rules`).

## Надёжность

* Сбой записи **не ломает бизнес-операцию**: запись уходит в
  `application/logs/audit-fallback.log` (JSON Lines), а
  `bin/console erp119:sync --replay` возвращает её в БД и переименовывает файл.
  Строгий режим (`fallback.throw = TRUE`) — для тестов и для тех контуров,
  где потеря записи недопустима.
* Таблица защищена триггером: `UPDATE` и `DELETE` в журнале запрещены.
  Единственная операция обслуживания — разбор DEFAULT-секции
  (`Service_Erp119_Partitions::attach_default()`), где триггер отключается
  на время переноса.
* Секреты маскируются **до** записи: поля из `redact.keys` (и по шаблону `redact.pattern`)
  (password, token, secret, api_key, card_number …) сохраняются как `***`,
  в том числе внутри `changes` и `context`.

## Секции и срок хранения

Журнал секционирован по месяцам (`RANGE` по `occurred_at`). Удаление по сроку
хранения — это `DROP` секции, а не построчный `DELETE`. Месяцы вперёд создаются
задачей; если сервер простоял и месяц не был создан, запись всё равно сохранится
в DEFAULT-секции, а `--attach-default` разложит её по местам.

```bash
bin/console erp119:partitions                       # сводка + создать месяцы вперёд
bin/console erp119:partitions --attach-default      # разобрать DEFAULT
bin/console erp119:partitions --drop-expired --retention=36
```

Регламент (из README модуля и `docs/DEVELOPMENT.md`):

```
*/5 * * * * cd /srv/promerp && bin/console erp119:sync --quiet
10 3 * * *  cd /srv/promerp && bin/console erp119:partitions --attach-default --drop-expired --quiet
```

## Использование из других модулей

```php
// История объекта — вкладкой в карточке:
/audit/widget/timeline?entity_type=tech_card&entity_id=7

// JSON для своей страницы:
/audit/api/entity?entity_type=counterparty&entity_id=CP-0001&limit=20

// Лента за период:
/audit/api/search?module=erp301&action=update&from=2026-09-01&limit=50
```

Сущности описываются в `erp_119_audit_settings` (название для интерфейса,
нужен ли аудит просмотров) — записи добавляются миграцией и правятся без
изменения кода.

## Права

| Право | Кому по умолчанию | Что даёт |
| :--- | :--- | :--- |
| `erp119_audit.view` | admin, manager, accountant | сводка, лента, история объекта, API чтения |
| `erp119_audit.export` | admin, manager | выгрузка CSV (сама выгрузка тоже попадает в журнал) |
| `erp119_audit.manage` | admin | секции журнала, срок хранения |

разбор событий шины, указатель чтения, лента и фильтры, статистика, история
объекта, выгрузка CSV, неизменяемость журнала, файл-страховка и его разбор.
