# erp405_quality — качество

Отвечает на вопрос «годится ли эта партия и что делать с браком» — и доводит
ответ до склада. Модуль закрывает разрыв между «пришло/сделали» и «можно
пускать в дело»:

```
партия (приёмка erp403, заказ erp402, операция erp408, вручную)
  → контроль (годная / брак)
  → несоответствия: код дефекта, количество, причина, виновник
  → изоляция партии на склад карантина
  → решение: использовать как есть / переделать / вернуть поставщику / в утиль / сортировка
  → исполнение решением склада (перемещение), закрытие контроля
```

Место модуля в цепочке производства:

```
техкарты → ПЗ → цех → планирование → закупки → [качество] → документы → себестоимость
```

Модуль не заводит свои справочники: номенклатура — реестр erp227 (через
erp401), склады — erp401, поставщики — контрагенты erp301, приёмки — erp403.
Ссылки на чужие модули мягкие (без внешних ключей): модули включаются и
выключаются независимо, а документы качества остаются читаемыми.

## Как это работает

1. **Контроль заводится** на партию: вид (`incoming` — приёмка, `operational` —
   между переделами, `final` — выпуск), количество, позиция, склад, где партия
   лежит. Для входного контроля есть отдельный путь —
   `Inspections::from_receipt_line()` берёт партию из позиции приёмки erp403
   (количество, поставщик и склад уже известны) и не задваивает контроль при
   повторном вызове.
2. **Проверка**: `start()` переводит черновик в рабочий контроль. Годная партия —
   осознанное действие `mark_passed()`: отсутствие дефектов ещё не значит, что
   проверку провели. Для входного контроля итог сразу уходит в приёмку
   (`Service_Erp403_Receipts::set_quality()`), снимая или подтверждая блокировку
   прихода.
3. **Дефекты** пишутся отдельными записями: код (справочник), количество,
   причина (`supplier` / `production` / `warehouse` / `equipment` / `design` /
   `unknown`), важность, ссылка на заказ или операцию. Факт дефекта **сам**
   переводит итог в «брак» и пересчитывает `defect_qty`; дефектов не может быть
   больше, чем в партии (`qty_exceeded`).
4. **Карантин** — это движение склада, а не пометка: `quarantine()` перемещает
   партию на склад типа `quarantine` через `Service_Erp401_Stock::transfer()`.
   Пока партия на карантине, контроль не закрывается, а отменить контроль
   нельзя — сначала выпуск (`release()`).
5. **Решения** исполняет склад:
   * `scrap` — перемещение на склад типа `scrap` (нет склада — честная ошибка
     `warehouse_required`, а не запись «утилизировано» без движения);
   * `return` — партия изолируется, публикуется `erp405.decision.return` для
     рекламации поставщику;
   * `rework` — событие `erp405.decision.rework` для производства (erp402);
   * `use_as_is`, `sort` — событие `erp405.decision.accepted`.
6. **Итог и решение — разные вещи.** `result` ставится проверкой, `decision`
   принимает человек и может принять позже: партия может стоять на карантине с
   итогом «брак» без решения — это рабочее состояние, а не незаполненное поле.
   Очередь таких партий (`pending`) — главный рабочий список контролёра.
7. **Статистика** считает PostgreSQL: брак по кодам, причинам, поставщикам,
   номенклатуре и месяцам, доля брака, карантин. Все агрегаты — `GROUP BY`, без
   выгрузки дефектов в память.

## События

| Событие | Когда |
|---------|-------|
| `erp405.inspection.created` | контроль заведён |
| `erp405.inspection.started` | проверка начата |
| `erp405.defect.found` | записан дефект (код, количество, причина) |
| `erp405.inspection.quarantined` / `released` | партия изолирована / выпущена |
| `erp405.inspection.passed` | партия признана годной |
| `erp405.inspection.decided` | решение принято |
| `erp405.inspection.closed` | контроль закрыт |
| `erp405.scrap.written_off` | брак списан в утиль (со ссылкой на движение) |
| `erp405.decision.return` / `.rework` / `.accepted` | решение по браку для соседних модулей |
| `erp405.defect_code.created` | заведён код дефекта |

Payload события всегда содержит `id`/`uuid`/`number` партии и количество —
журнал erp119 строит запись по этим полям.

## JSON API

Чтение (`erp405.view`): `stats`, `inspections`, `inspection`, `pending`,
`quarantine`, `codes`, `code`, `by_cause`.

Изменения: `inspection_create`, `inspection_from_receipt`, `defect_add`,
`defect_remove` — право `erp405.inspect`; `passed`, `quarantine_apply`,
`release`, `decide`, `close`, `cancel` — право `erp405.decide`; `code_save` —
право `erp405.manage`.

Правила ядра действуют и здесь:

* **метод — часть контракта**: изменяющие действия вызываются POST-ом, GET
  получает 405 `method_not_allowed` (список чтения — `application/config/api.php`);
* **повтор не выполняется дважды**: пришлите `Idempotency-Key` — повтор вернёт
  сохранённый ответ, тот же ключ с другим телом получит 409 (`docs/MCP.md`, B15);
* `inspection_from_receipt` идемпотентен и без ключа: одна позиция приёмки —
  один контроль.

## Установка

1. Модуль уже подключён в `application/bootstrap.php` (`erp405_quality`).
2. Миграции: `bin/console db:migrate` (создаёт таблицы и стартовый справочник).
3. Склады карантина и утиля заводятся в модуле склада (erp401):
   `type = quarantine` и `type = scrap`. Без них изоляция и списание честно
   отвечают `warehouse_required`, а не «делают вид».
4. Проверки: `bin/test --filter=Erp405` (18 тестов), `bin/console dev:smoke`,
   `bin/console dev:audit --check=api_read_only`, `bin/console mcp:tools --check`.

## Что осознанно отложено

* **Паспорт партии/изделия** (документ качества с печатью) — ждёт
  `erp404_documents`: печатные формы живут там.
* **Контрольные операции в техкарте** (`erp228`): сейчас вид контроля
  назначается человеком; привязка контрольной операции к маршруту — следующий
  шаг вместе с цехом.
* **Сдельная ответственность за брак** (удержания, премии) — это `erp409` и
  расчёт зарплаты, не качество.
* **Статистика по поставщикам «в срок и без брака»** — есть данные (брак и
  приёмки), но рейтинг поставщика считается в одном месте: сейчас он живёт в
  erp403 (`Suppliers::compare()` и `on_time_rate()`), а качество отдаёт туда
  свои цифры через `Stats::by_supplier()`.
