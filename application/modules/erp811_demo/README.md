# erp811_demo — демонстрационный стенд

**ID:** 811 (диапазон 800–999: аналитика и агенты) · **таблицы:** `erp_811_*` ·
**контур:** демонстрационный, изолируется отдельной БД или схемой.

## Зачем модуль

Внедрение производственного контура «с нуля» на живом заводе идёт месяцами: пока
цех не наполнит систему данными, показать нечего — на экранах пусто, а решения
принимать не на чем. Поэтому система умеет **сымитировать работающее
производство**: собрать в отдельной базе правдоподобную историю (заказы,
техпроцессы, закупки, простои, брак, документы) и пустить посетителя посмотреть
на неё гостем — без регистрации и без риска для боевых данных.

Сценарий стенда — «Печатня 3D»: контрактная печать на FDM и SLA, смежная тема
сервиса [text-to-3d.ru](https://text-to-3d.ru) (генерация моделей под печать).
Взято то, что узнаваемо в цехе: катушки филамента, сопла, клипсы-пистоны,
формы для печенья, корпуса датчиков, кронштейны, ОТК и паспорта качества.

## Как это устроено

| Слой | Файл | Что делает |
|------|------|------------|
| Состояние стенда | `classes/Service/Erp811/Demo.php` | включён/выключен, отдельная база, cookie, вход/выход, режим «только чтение», журнал сборок |
| Сценарий | `config/scenario/print3d.php` + `classes/Service/Erp811/Scenario.php` | компания, клиенты, поставщики, материалы, детали, центры, смены, маршруты, причины простоев, дефекты, тур |
| Сборка данных | `classes/Service/Erp811/Seeder.php` | 21 слой синтетики (в т. ч. `Service_Erp811_Contour`) через сервисы модулей, детерминированный seed |
| Команда | `classes/Task/Demo.php` | `bin/console demo --status\|--plan\|--build\|--reset` |
| Страницы | `classes/Controller/Erp811/Demo.php` + `views/erp811/*` | лендинг `/demo`, вход/выход, тур |
| JSON API | `classes/Controller/Erp811/Api.php` | `/demo/api/status\|scenario\|tour\|counts\|runs` |
| MCP | `mcp.php` | `demo.status`, `demo.scenario`, `demo.tour`, `demo.counts`, `demo.runs` — только чтение |

### Изоляция: отдельная база или схема, но не «флажок в данных»

По умолчанию стенд живёт в своей базе (`DEMO_STORAGE=database`, `DB_DEMO_NAME`).
Для dev-стенда и глубокого тестирования доступен `DEMO_STORAGE=schema`: тогда
используется та же физическая основная БД, но все таблицы и синтетические данные
живут в выделенной схеме `DB_DEMO_SCHEMA` (по умолчанию `promerp_demo`). Поэтому
генератор упражняет тот же PostgreSQL-сервер без создания новой БД, но синтетика
не смешивается с рабочими строками. `public` остаётся
вторым элементом `search_path`, потому что там установлены типы и операторы
`ltree`/`vector`; demo-таблицы всегда разрешаются первыми. Поэтому schema-mode —
инструмент разработки и глубокого тестирования, а не такая же строгая граница
безопасности, как отдельная БД. В production он требует отдельного
`DEMO_ALLOW_SHARED_PRODUCTION=1`.

Подмена группы подключения `default` делается в `bootstrap.php` **до** старта
сессии и первого запроса — по cookie `promerp_demo`. В demo-схеме заранее
создаётся собственный `migrations_pg`: это не даёт migrator-у ошибочно принять
реестр из `public` и пропустить создание таблиц. Сброс в schema-mode удаляет
только выделенную схему; `public` основной базы не является целью операции.

### Демо-режим только на чтение

Пока активен cookie стенда, любой не-GET запрос получает 403 с объяснением
(`Demo::guard_read_only()` в `bootstrap.php`). Причины две: посетитель не должен
испортить сценарий следующему гостю, а мы не хотим раздавать пароль
администратора, чтобы «просто посмотреть». Вход (`/demo/enter`) и выход
(`/demo/exit`) — POST, потому что меняют состояние сессии.

### Вход под ролью: витрина начинается с главной

Гость (`demo`) видит витрины, но не рабочие места: раздел собирается под роль, а
у гостя её нет. Поэтому на главной странице системы неавторизованному
посетителю показывается витрина с выбором роли — «снабженец», «мастер»,
«экономист» и так далее (`Welcome::_demo_invite()` и `config/demo.php:roleplay`).
Форма отправляет POST на `/demo/enter` с кодом роли, стенд поднимает демо-базу и
входит соответствующей учётной записью, а посетитель попадает сразу в её раздел.
Тот же выбор предлагается на `/demo`: туда приходят из меню и из поиска, минуя
главную.

Роль берётся только из конфига: адрес приходит из браузера, и принимать
произвольную учётную запись значило бы дать посетителю войти администратором
стенда. Список ролей фильтруется по демо-базе (`Demo::roleplay()`): выбор,
который закончится отказом, не показывается. Адрес старта роли должен
открываться на стенде — модуль, которого нет в списке `modules`, отдаст ошибку.

### Данные: синтетика через сервисы, а не INSERT-ы

Сборка идёт **через сервисы модулей** (`Erp227_Registry`, `Erp401_Stock`,
`Erp402_Orders`, `Erp403_*`, `Erp405_*`, `Erp407_Mrp`, `Erp408_Operations`,
`Erp404_Documents`), поэтому на стенде работают те же переходы состояний,
резервы, списания, журналы и события, что и в бою. Прямые UPDATE-ы есть только
там, где данные исторические: даты операций, длительность простоев, учтённое
время, минимальные остатки склада. Сид детерминирован (`seed 20260916`) — сборка
повторяема, а `--seed=N` даёт другой вариант той же истории.

Слои сборки: очистка сцены → пользователи → **сотрудники и оргструктура** →
типы объектов → контрагенты → **CRM** → номенклатура → склады → рабочие центры
и смены → стартовый запас → техкарты → **составы изделий** → заказы →
**QR-метки** → пробные образцы → операции и простои → качество и брак →
отгрузка готовой продукции → программа выпуска и потребность → закупки и
приёмка → документы → пороги и снимки витрин.

Четыре выделенных слоя (`erp310_workforce`, `erp221_crm`,
`erp231_product_structure`, `erp199_sqr`) живут в `Service_Erp811_Contour`:
они опираются на результат производственной цепочки (клиенты, номенклатура,
техкарты, заказы), но не продолжают её. Данные — в разделах сценария
`workforce`, `crm`, `structures`, `qr`:

* **Сотрудники** — 14 человек по иерархии (директор → руководители → участки),
  подразделения и должности дополняют справочник миграции по коду, штатное
  расписание с вакансиями, один сотрудник в отпуске, один уволен, один
  переведён с печати на отделку (история назначений). Учётные записи стенда
  привязаны к карточкам сотрудников.
* **CRM** — профили шести клиентов, контакты с ролью в принятии решений, 12
  сделок на всех стадиях (суммы = цена × партия из каталога деталей), отказы с
  причиной, звонки/встречи/задачи в ленте и статьи базы знаний. Даты событий
  разнесены по времени задним числом: иначе воронка выглядела бы «всё за секунду».
* **Составы изделий** — для каждой детали EBOM (материал + расходник с нормой
  потерь), согласование, MBOM по технологической карте; две детали имеют вторую
  ревизию в работе и есть комплект из нескольких деталей.
* **QR** — свободные объекты (места хранения, инструмент, тара, документы; склад
  как вид цели в erp199 не предусмотрен), наклейки на номенклатуру, заказы и
  сотрудников, запас пустых наклеек, журнал сканирований, закрытая и текущая
  инвентаризации.

Сбой подшага не останавливает слой: причина попадает в замечания сборки.

Связность важнее объёма: запас материалов считается от **плана выпуска**,
нормы времени в техкарте — на одну деталь (цех умножает их на количество),
приход материалов идёт поставками за историю, а выпущенные партии уезжают
клиентам. Поэтому покрытие запасов, оборот склада, план/факт и OEE на витринах
сходятся между собой, а «позиция к дозаказу» — это действительно позиция,
которая кончается, а не следствие ошибки в расчёте.

Цифры собранного стенда (сценарий `print3d`, seed по умолчанию): 30 заказов
(24 закрыто, 3 в работе, 2 ждут старта), 116 операций цеха, 71 операция с
простоем (43,8 ч), 6 975 готовых деталей, 3 604 детали отгружено клиентам на
314 599 ₽ по прайсу сценария, 25 контролей качества, 1 просроченный заказ
поставщику и 2 позиции ниже неснижаемого минимума. На витринах это читается как:
покрытие запасов около двух месяцев расхода (цель 21 день — медиана по позициям
с расходом), OEE 76 % (цель 60), выполнение плана 95 %, доля забракованных
контролей 12 % (цель 8), просроченные поставки 25 % (цель 12). Проблемы на
стенде оставлены намеренно — система должна показывать, где теряем, а не только
зелёные цифры.

## Команды

```bash
bin/console demo --status     # включён ли стенд, собрана ли база, что в ней
bin/console demo --plan       # что будет собрано (без записи в базу)
bin/console demo --build      # собрать стенд в чистой базе стенда
bin/console demo --reset      # пересоздать схему и собрать заново
bin/console demo --build --seed=777   # другой вариант истории
```

Для shared hosting UI по умолчанию предлагает профиль `quick`. Сборка держит
межпроцессный lock, продолжает работу после разрыва браузерного соединения и
пишет живой журнал в `application/logs/demo_last_run.log`; `/demo/setup`
опрашивает `/demo/progress`. Поэтому timeout Apache больше не означает отмену
сборки. Если таблицы уже созданы, UI предлагает продолжить наполнение без
повторного `DROP SCHEMA` и миграций.

Чтобы синтетическая сборка не раздувала технические таблицы, `quick` сохраняет
каждую 20-ю запись аудита и события, `standard` — каждую 5-ю, а `full` — все.
Выборка детерминирована и действует только внутри Seeder. При этом EventBus
доставляет **каждое** событие слушателям и в центр уведомлений: прореживается
только диагностическая история в `erp_208_events`. После сборки полный режим
восстанавливается в `finally`.

При переключении базы сбрасываются и `Database::$instances`, и внутренний кэш
ORM. Это важно для `User`/`Role`: контроллер авторизации инициализирует эти
модели ещё на основной базе, а стандартный ORM сохраняет объект соединения в
метаданных модели. Без сброса производственные таблицы наполнялись в demo, но
учётные записи ошибочно уходили в `public`, оставляя demo без гостя.

После сборки: страница `/demo` (лендинг), `/demo/workspace` (рабочее место —
один экран «что делать прямо сейчас», собран из компонентов интерфейса),
`/demo/tour` (маршрут осмотра),
`/demo/api/status` (JSON для роботов и агентов).

## Права

`erp811.view` — чтение состояния стенда, сценария, тура и журнала сборок
(admin, manager, accountant, worker). Изменяющих прав у модуля нет: стенд не
принимает правок, а сборка — операция инфраструктуры (`bin/console demo --build`).

## Настройка

`application/config/demo.php`:

| Ключ | Смысл |
|------|-------|
| `enabled` | включён ли стенд (по умолчанию — да; `FALSE` полностью выключает режим) |
| `storage` / `DEMO_STORAGE` | `database` для отдельной БД или `schema` для схемы в основной БД |
| `database` / `DB_DEMO_NAME` | имя отдельной базы (используется только в database-mode) |
| `schema` / `DB_DEMO_SCHEMA` | имя изолированной схемы в schema-mode (по умолчанию `promerp_demo`) |
| `build_profile` / `DEMO_BUILD_PROFILE` | `quick` (8 заказов/30 дней), `standard` (16/60) или `full` (30/120) |
| `roleplay` | роли осмотра: код роли, учётная запись стенда, название, подсказка, адрес старта и иконка |
| `cookie` | имя cookie демо-режима (`promerp_demo`) |
| `guest` | учётная запись гостя (email/пароль; создаётся только в базе стенда) |
| `scenario` | код сценария (`print3d`) |
| `history_days` | глубина истории в днях (120) |
| `orders` | сколько производственных заказов собрать (30) |

Сценарий (`config/scenario/print3d.php`) правится без кода: компания, клиенты,
поставщики, материалы, детали с нормами и ценами, рабочие центры, смены,
маршруты FDM/SLA, причины простоев, дефекты, сотрудники и оргструктура, CRM,
составы изделий, QR-метки, шаги тура и тексты лендинга.

## Что проверено

* `bin/console demo --reset` собирал 17 слоёв без замечаний (~6 с) до добавления
  слоёв сотрудников, CRM, составов и QR; **со всеми 21 слоем сборка не запускалась** —
  этот пункт нужно перепроверить командой `bin/console demo --reset`;
* страницы `/demo`, `/demo/tour` и API отвечают, вход гостем и под каждой
  ролью осмотра работает (проверено входом под всеми пятью ролями);
* главная страница без входа показывает витрину и формы входа по ролям;
* не-GET из демо-сессии возвращает 403 (защита в `bootstrap.php`);
* сборка не касается рабочей базы: очистка сцены отказывается работать, если
  текущая база не совпадает с базой стенда;
* `make check` (lint + аудит + smoke + тесты) — зелёный.
