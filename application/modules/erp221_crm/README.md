# erp221_crm — продажи: воронка, сделки и работа с клиентом

Модуль ведёт сделку от первого обращения до решения: где она стоит в воронке,
сколько денег в работе и что менеджер уже сделал. Клиент при этом остаётся
клиентом системы, а не «клиентом CRM» — справочник организаций и контактных
лиц один на всю систему.

## Зачем он нужен

Продажа — это не таблица, а последовательность обещаний: «позвоню в четверг»,
«пришлю КП», «согласуем бюджет». Модуль хранит эти обещания рядом со сделкой
(лента работы), не даёт менеджеру закрыть сделку «просто так» (правила перехода
по стадиям) и напоминает, что срок подходит, а сделка стоит.

## Что чем является

| Сущность | Где живёт | Кто владелец |
|---|---|---|
| Клиент (организация, реквизиты, статус) | `erp_301_counterparties` | erp301_counterparty |
| Контактное лицо клиента | `erp_301_contacts` | erp301_counterparty |
| Профиль продаж клиента (сегмент, отрасль, источник, ответственный) | `erp_221_client_profiles` | этот модуль |
| Профиль контактного лица (уровень ЛПР, удобный канал) | `erp_221_contact_profiles` | этот модуль |
| Стадии воронки и правила перехода | `erp_221_stages` | этот модуль |
| Причины отказа | `erp_221_loss_reasons` | этот модуль |
| Сделка, её сумма, срок и стадия | `erp_221_deals` | этот модуль |
| Участники сделки | `erp_221_deal_contacts` | этот модуль |
| Лента: звонки, письма, встречи, задачи, файлы | `erp_221_activities` (+ `…_history`) | этот модуль |
| Разбор ИИ (резюме, вероятность, возражения) | `erp_221_ai_analysis` | этот модуль |
| База знаний менеджера | `erp_221_knowledge_base` | этот модуль |
| Сырые сообщения до разбора | `erp_221_messages` | этот модуль |
| Файлы вложений | `erp_212_files` (хранилище) | erp212_file_storage |
| Сотрудник, от чьего лица идёт работа | `users` | erp100_base |
| Заказы, счета, номенклатура | профильные модули | каждый свой |

Второго справочника клиентов модуль **не заводит**: организация заводится один
раз в «Контрагентах» и получает роль `customer`. CRM хранит только то, чего у
контрагента нет: сегмент, отрасль, источник и ответственного менеджера.

## Стадии как правило, а не украшение

Стадия — это запись в БД; её можно переименовать и настроить без выпуска новой
версии. Что она задаёт:

- `probability` — вероятность для прогноза (сумма сделок, взвешенная по стадии);
- `required_fields` — что должно быть заполнено перед переходом
  (`amount`, `deadline`, `description`, `source`, `contact_id`);
- `requires_loss_reason` — без причины отказа перейти нельзя;
- `actions` — что сделать при входе на стадию (`create_activity` — запись в ленту).

Попытка перейти на стадию с незаполненными обязательными полями возвращает
понятную ошибку, а не «сохранено». Это защита от воронки, в которой половина
сделок висит на «КП» без суммы.

## Лента работы

`erp_221_activities` — общая лента по сделке и по клиенту: комментарий, звонок,
встреча, письмо, задача, файл, системная запись, смена стадии. Виды и состояния
ограничены `CHECK`-ами; каждая правка пишет снимок в `…_activities_history`,
поэтому «кто и когда переставил срок» — вопрос с ответом.

Задача отличается от заметки сроком: незакрытые задачи со сроком попадают в
«Напоминания» и в ежедневную рассылку, а файл, приложенный к записи, хранится
штатным хранилищем (erp212), а не в файловой системе модуля.

## ИИ-разбор — подсказка, а не решение

Разбор (резюме, вероятность, возражения, следующий шаг, риск) выполняется через
общий контур LLM. Ответ модели сохраняется в `erp_221_ai_analysis` со ссылкой на
модель; сделка и контакт при этом не меняются «молча» — увиденное менеджер
подтверждает сам. Если LLM не подключён, интерфейс работает как обычно, просто
без кнопок разбора и с честным «ИИ недоступен».

## Напоминания

- `erp221:daily_reminders` — утренняя повестка: задачи со сроком, просроченные
  сделки, застой и близкие сроки. Доставку выполняет центр уведомлений (erp217):
  сотрудник получает сообщение, только если подписан на событие;
- на странице `/crm/reminders` то же видно глазами — независимо от подписок;
- срок «застоя» и окно напоминания настраиваются в
  `application/config/erp221_crm.php`.

## Обмен с таблицами

Экспорт — CSV с точкой с запятой и BOM (Excel в русской локали открывает без
пляски с кодировками). Импорт сначала показывает отчёт «что будет создано и
изменено» (`dry_run`) и только потом пишет. Неизвестный ИНН — не повод завести
клиента «на лету»: импорт подсказывает завести контрагента в его модуле.

## Интерфейс

- `/crm` — доска: колонки стадий, KPI, мои задачи, сделки без движения;
- `/crm/deals` — список с фильтрами, `/crm/deal/<id>` — карточка сделки;
- `/crm/clients`, `/crm/client/<id>` — клиенты и профиль продаж;
- `/crm/stages` — настройка воронки и причин отказа;
- `/crm/analytics` — воронка, динамика, менеджеры, источники, отказы;
- `/crm/kb` — база знаний, `/crm/journal` — лента, `/crm/reminders` — повестка;
- `/erp221/…` — старые адреса (`/erp221/deal/view/12`): контроллер `Legacy`
  отвечает постоянной переадресацией 301 на новую страницу, чтобы закладки
  менеджеров и ссылки в письмах продолжали работать. В маршруте сегмент старого
  действия назван `step`, а не `action`: имя `action` служебное — по нему Kohana
  выбирает метод контроллера, и `action_view()` в базе нет.

MCP-инструменты только читают (`crm.deals`, `crm.deal`, `crm.clients`,
`crm.analytics`, `crm.journal`, `crm.kb`): записи в сделку делает человек — у
них есть автор, а у ответа модели его нет.

## Доступ

- **человек** — сессия системы и права `erp221.*` из `application/config/acl.php`;
- **интеграция** — ключ доступа (erp804) для чтения через `/crm/api/…`; записи
  API — только POST.

## Миграции

`migrations_pg/pgMigration_001_Erp221_Crm_CreateTables.php` создаёт одиннадцать
таблиц и заводит стадии и причины отказа по умолчанию. Миграция идемпотентна и
доступна через штатную админку `/migrate_pg` после подключения модуля в
`application/bootstrap.php`.
