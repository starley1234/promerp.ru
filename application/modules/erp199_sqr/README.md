# erp199_sqr — QR-маркировка и мобильный терминал

Модуль связывает запись в системе с предметом в физическом мире: наклейка с
QR-кодом на изделии, партии, заказе, оборудовании или сотруднике, а сервер
решает, что показать тому, кто этот код отсканировал.

## Зачем он нужен

В цехе и на складе нет доступа к компьютеру, но есть телефон. Приложение
умеет только три вещи: считать QR, снять фото и определить координаты — вся
остальная логика на сервере («глупый клиент — умный сервер»). Поэтому новое
полевое действие (страница терминала) добавляется данными в `erp_199_scenarios`,
а не выпуском новой версии приложения.

## Что чем является

| Сущность | Где живёт | Кто владелец |
|---|---|---|
| Наклейка (код, состояние, привязка) | `erp_199_tokens` | этот модуль |
| Свободный объект (то, для чего нет владельца) | `erp_199_objects` + `erp_199_objects_history` | этот модуль |
| Фотографии сканирования | `erp_199_media` (файлы в `public_html/uploads/erp199/`) | этот модуль |
| Журнал касаний | `erp_199_activity` | этот модуль |
| Страницы терминала | `erp_199_scenarios` | этот модуль |
| Объект реестра | `erp_227_objects` | erp227_core_registry |
| Партия / серийный номер | `erp_412_lots` | erp412_traceability |
| Производственный заказ | `erp_402_orders` | erp402_production |
| Сотрудник | `erp_310_employees` | erp310_workforce |
| Остатки | `erp_401_*` | erp401_wms |

Номенклатуру модуль **не дублирует**: наклейка ссылается на цель вида
`target_kind` + `target_id`, а карточка предмета читается у владельца данных
(`Service_Erp199_Targets`). Виды целей: `local`, `registry`, `item`, `lot`,
`order`, `employee`.

## Состояния наклейки

`new` → `active` → (`blocked` | `damaged` | `lost`) → `archived`.

Состояние, которое видит терминал, — не только статус наклейки:

- `unknown` — кода нет в реестре: можно завести объект с телефона;
- `unbound` — наклейка есть, но ни к чему не привязана;
- `active` — всё в порядке, сценарии доступны;
- `blocked`, `damaged`, `lost`, `archived` — наклейка снята с работы, сценарии закрыты;
- `broken` — наклейка активна, а цель исчезла из системы: дефект данных, видно сразу.

## Страницы терминала (сценарии)

Сценарий — данные БД. Форму рисует клиент, эффект выполняет сервер:

- `inventory_scan` — отметка в открытой инвентаризации;
- `stage_mark` — этап изделия (изготовление, сборка, контроль, упаковка, отгрузка);
- `status_mark` — статус цели (в работе, ремонт, архив, брак);
- `photo_fix` — фотография с привязкой к наклейке;
- `location_mark` — местоположение с координатами телефона;
- `note` — запись в журнал.

Эффекты: `record`, `set_status`, `set_attributes`, `inventory_scan`. Форма —
`{"fields":[{"name":"stage","label":"Этап","type":"select","required":true,
"options":{"assembly":"Сборка"}}]}`.

## API тонкого клиента

```
GET  /qr/api/resolve/<код>     — что это, что можно сделать, какую страницу показать
GET  /qr/api/targets           — поиск цели для привязки наклейки
GET  /qr/api/scenarios         — каталог страниц терминала
GET  /qr/api/inventory         — открытая инвентаризация и прогресс
GET  /qr/api/objects|object    — свободные объекты модуля
GET  /qr/api/tokens|token      — реестр наклеек
GET  /qr/api/activity/<код>    — история сканирований наклейки
GET  /qr/api/types             — типы объектов

POST /qr/api/bind              — привязать наклейку к цели
POST /qr/api/register          — завести свободный объект с телефона
POST /qr/api/scan              — выполнить сценарий (фото, статус, этап)
POST /qr/api/photo             — добавить фото к наклейке
POST /qr/api/save|moderate     — правка и модерация свободного объекта
POST /qr/api/inventory_*       — открыть, отметить, закрыть инвентаризацию
```

Изменяющие действия — только POST, повтор с тем же `Idempotency-Key` не
выполняется второй раз: в поле связь рвётся на середине отправки.

## Доступ

- **Человек** — сессия системы и права `erp199.*` из `application/config/acl.php`;
- **устройство** — ключ `erp804_mcp` (`Authorization: Bearer …`): у ключа есть
  скоупы (`erp199.scan`, `erp199.tokens.view`, …), срок жизни, признак
  «только чтение» и `actor_id`, от имени которого пишется журнал. Отдельной
  системы паролей для телефонов нет: ключ отзывается — терминал теряет доступ.

WebView-страница терминала (`/qr/scan`) работает и по сессии, и по ключу.

## Инвентаризация

Сессия (`erp_199_inventories`) задаёт область проверки — виды целей и партию
наклеек. Ожидаемое считается на сервере, терминал только присылает отметки
`found` / `missing` / `damaged` / `foreign`. Расхождение «ожидалось − отмечено»
показывается в админке; закрытие фиксирует итоги в снимке `stats`.

## Фотографии и распознавание

Файлы: `public_html/uploads/erp199/<год>/<месяц>/`, проверка размера, типа по
содержимому и `sha256`. Распознавание фото (vision) — необязательный помощник:
без модуля `llm` объект всё равно заводится, просто без подсказок. Ответ модели
сохраняется в `ai_raw`, а объект создаётся черновиком и проходит модерацию.

## Интерфейс

- `/qr` — обзор: наклейки, открытая инвентаризация, черновики из поля, журнал;
- `/qr/tokens` — реестр наклеек, выпуск партии, печать этикеток 58×40 мм;
- `/qr/objects` — свободные объекты и модерация;
- `/qr/inventories` — сессии инвентаризации;
- `/qr/scenarios`, `/qr/types` — настройка терминала;
- `/qr/activity` — журнал касаний физического мира;
- `/qr/scan` и `/qr/<код>` — терминал; `mobile.help` — справка для того, кто
  открыл наклейку обычной камерой.

MCP-инструменты только читают (`qr.resolve`, `qr.tokens`, `qr.token`,
`qr.objects`, `qr.inventories`, `qr.journal`): записи в физический мир делает
человек, у них есть автор, место и время.

## Настройка

`application/config/erp199_sqr.php`: префикс кодов, каталог и лимиты фото,
подсказка и провайдер распознавания, поведение терминала и
`allow_register_from_field` (можно ли заводить объект прямо с телефона).

## Миграции

`migrations_pg/pgMigration_001_Erp199_Sqr_CreateTables.php` создаёт девять
таблиц и заводит типы и сценарии по умолчанию. Миграция идемпотентна и
доступна через штатную админку `/migrate_pg` после подключения модуля в
`application/bootstrap.php`.
