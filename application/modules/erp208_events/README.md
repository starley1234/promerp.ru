# Система Событий (erp208_events)

## Описание

Модуль `Система Событий` (`erp208_events`) — это центральное связующее звено (Event Bus) ERP-системы. Он реализует паттерн "Издатель-Подписчик" (Pub/Sub), обеспечивая слабую связанность (Loose Coupling) между модулями.

**Зачем это нужно:**
Модуль "Задачи" не должен знать о существовании модуля "Уведомления" или "Бонусы". Он просто объявляет: *"Задача №10 завершена"*. Все остальные модули, кому это интересно, подписываются на это событие и реагируют самостоятельно.

## Основные возможности

*   **Transactional outbox:** `Service_Erp208_Outbox::enqueue()` пишет сообщение
    в текущей транзакции бизнес-сервиса; rollback факта откатывает и сообщение.
*   **Надёжная обработка:** конкурентный claim через `SKIP LOCKED`, lease,
    retry с exponential backoff, dead-letter и контролируемый replay.
*   **Идемпотентный потребитель:** таблица receipts и уникальная пара
    `consumer + idempotency_key` не дают повторить внешний эффект.
*   **Наблюдаемость:** ready/processing/dead, возраст очереди, correlation ID;
    MCP `outbox.stats/search`, а `outbox.replay` требует approval.
*   **Централизованная шина (EventBus):** Единая точка входа для всех событий системы.
*   **Гибкая подписка:** Подписка через код (`init.php`), через базу данных или через API.
*   **Автоматическое проксирование:** Интеграция с "Центром уведомлений" (erp217) на уровне ядра шины.
*   **Логирование и аудит:** Сохранение истории всех событий в БД (`erp_208_events`) для последующего анализа.
*   **Умная фильтрация уведомлений:** Автоматическое исключение инициатора события из списка получателей уведомлений (чтобы не получать уведомления о собственных действиях).
*   **REST API:** Интерфейс для публикации и мониторинга событий внешними системами.

## Настройка

Конфигурация находится в `application/config/erp208_events.php`:

```php
return array(
    'event_bus' => array(
        'log_published_events' => TRUE, // Сохранять ли каждое событие в таблицу erp_208_events
        'predefined_event_names' => array(
            'erp502.task_done',
            'erp221.deal.created',
            // Список для выбора в админ-панели
        ),
    ),
    'logging' => array(
        'enabled' => TRUE,
        'file'    => 'events.log', // Лог-файл в application/logs/
        'level'   => Log::DEBUG,
    ),
);
```

## Использование

### 1. Публикация события

Для гарантированной интеграционной доставки записывайте outbox **в той же
транзакции**, где сохранён бизнес-факт:

```php
$db = Database::instance();
$db->begin();
// ... сохранить выпуск/списание ...
Service_Erp208_EventBus::instance()->enqueue(
    'erp402.output.completed', $payload, 'output:'.$output_uuid
);
$db->commit();
```

Worker запускается ограниченными пакетами (обычно cron/systemd timer):

```bash
bin/console events:outbox --limit=50 --lease=120 --worker=integration-1

`Service_Erp208_Outbox::claim()` и `work()` также принимают необязательный префикс имени события последним аргументом. Это позволяет независимо запускать специализированного consumer и изолировать его lease/retry-поток; без префикса поведение общего worker не меняется.
```

Получатель обязан вызвать `remember_consumed()` до внешнего эффекта или иметь
эквивалентный уникальный idempotency key. Ручной replay допустим только для
`dead` и не отменяет это правило.

Для синхронных внутренних событий используйте `Service_Erp208_EventBus`:

```php
$payload = [
    'task_id' => 123,
    'status'  => 'closed',
    'target_user_ids' => [45, 46, 47], // Массив получателей для уведомлений
];

// Публикация (третий параметр - ID текущего пользователя/инициатора)
Service_Erp208_EventBus::instance()->publish('erp502.task_done', $payload, $current_user_id);
```

### 2. Подписка на событие

#### Способ А: Через код (статическая регистрация)
Обычно делается в `init.php` вашего модуля:

```php
Service_Erp208_EventBus::instance()->listen('erp502.task_done', function($payload, $event_name, $initiator_id) {
    // Ваша логика
});
```

#### Способ Б: Через БД (динамическая регистрация)
В интерфейсе модуля (`/erp208_events/list_subscribers`) создайте запись:
*   **Event Name:** `erp502.task_done`
*   **Callback Method:** `Model_ClassName::method_name`
*   **Is Active:** Да

### 3. Интеграция с Центром Уведомлений (erp217)

Шина событий автоматически проксирует данные в `erp217_notification_center`, если в `payload` указаны получатели.

**Особенности обработки получателей:**
*   `target_user_id` (int) — одиночный получатель.
*   `target_user_ids` (array) — список получателей.
*   **Исключение инициатора:** Если `initiator_id` (переданный при публикации) совпадает с ID получателя, уведомление этому пользователю **не отправится**.
*   **Принудительная отправка:** Если нужно уведомить инициатора о его же действии, добавьте в payload `'force_notification' => true`.

## API Интерфейс

Модуль предоставляет следующие эндпоинты (требуется право `erp208_events.api`):

*   `POST /erp208_events/api/publish_event` — Опубликовать событие.
*   `GET /erp208_events/api/get_events` — Получить список последних событий.
*   `POST /erp208_events/api/subscribe` — Создать новую подписку.

## Структура таблиц

*   `erp_208_events`: Журнал всех произошедших событий.
*   `erp_208_event_subscribers`: Реестр подписчиков и правил проксирования.

## Безопасность и права доступа

*   `erp208_events.list_events` — Просмотр лога событий.
*   `erp208_events.manage_subscriptions` — Управление подписчиками.
*   `erp208_events.publish_event` — Право на ручную публикацию событий.
