# erp410_shipment — продажи и отгрузка

Отвечает на вопрос «что и по какой цене продано клиенту, что из этого уже уехало
со склада и какие деньги за это пришли». Модуль закрывает конец
производственного контура:

```
заказ клиента (руками, из сделки CRM или импортом)
  → подтверждение (проверка кредитного лимита)
  → резерв товара на складе (erp401)
  → сборка отгрузки
  → проведение отгрузки: списание со склада (erp401) + запись цены в историю
  → счёт → оплата (частичная или полная)
```

Цепочка производства, в которой модуль занимает место сбыта:

```
техкарты → ПЗ → цех → планирование → закупки → качество → документы → [продажи]
```

Модуль не заводит свои справочники: покупатели — контрагенты с ролью
«покупатель» (erp301), номенклатура — реестр erp227, склад, остатки и резервы —
erp401. Ссылки на чужие модули мягкие (без внешних ключей): модули включаются и
выключаются независимо, а документы продажи остаются читаемыми.

## Как это работает

1. **Заказ** (`draft`, номер `ЗКЛ-ГГГГ-НННННН`) — обещание клиенту: позиции «что,
   сколько и по какой цене». Цена подставляется каскадом: цена строки, если её
   ввели → договорная цена клиента → базовая цена прайса → цена последней
   отгрузки по этой позиции → 0 с предупреждением. Источник цены виден в
   карточке и в прайсе, чтобы «ноль» не выглядел как настоящая цена.
2. **Подтверждение** (`confirm`) проверяет кредитный лимит клиента: если суммы
   заказа не хватает в свободном остатке, переход отклоняется; явное `force`
   обходит проверку и оставляет предупреждение в журнале.
3. **Резерв** (`reserve`) ставит по каждой открытой позиции резерв в erp401
   (`ref_type = erp410_order`, `ref_id` — строка заказа) и записывает
   `reservation_id` в строку. Если хотя бы один резерв не встал (нет остатка),
   уже созданные резервы откатываются — частичного резерва не остаётся.
   `release` снимает резервы и возвращает заказ в `confirmed`.
4. **Отгрузка** (`draft`, `ОТГ-ГГГГ-НННННН`) собирается из заказа: строки — это
   то, что заказ ещё не отгрузил. Сборка состояние заказа не меняет — заказ
   по-прежнему можно уточнить, а состав сборки правится в отгрузке; готовая к
   отправке отгрузка — `ready`.
5. **Проведение** (`post`) — момент, когда продажа становится расходом со склада:
   * по строкам с активным резервом вызывается `consume_reservation()` (товар
     списывается, резерв закрывается);
   * по строкам без резерва — `issue()` напрямую;
   * количества попадают в `qty_shipped` строк заказа: если уехало всё —
     заказ переходит в `shipped`, если часть (даже в пределах одной строки) —
     в `picking` с событием `erp410.order.partially_shipped`;
   * цена отгрузки пишется в историю (`source = shipment`) — следующая продажа
     этой позиции получит её как ориентир.
   Проведённую отгрузку отменить нельзя: обратное движение оформляется приходом
   в модуле склада.
6. **Счёт** (`draft` → `issued`, `СЧ-ГГГГ-НННННН`) выставляется из проведённой
   отгрузки или из заказа; повторное выставление отклоняется (`duplicate_invoice`).
   **Оплата** принимается частями: частичная сумма переводит счёт в
   `issued` и пишет `erp410.invoice.partially_paid`, полная (≥ остатка) — в `paid`.
7. **Закрытие** (`close`) — заказ отгружен и закрыт для правок; отменённый заказ
   (`cancel`) снимает резервы.

## Права

| Право | Кто | Что разрешает |
|-------|-----|---------------|
| `erp410.view` | admin, manager, accountant, demo | заказы, отгрузки, счета, клиенты, прайс — чтение |
| `erp410.manage` | admin, manager | заказы, позиции, сборка отгрузки, прайс, условия клиента |
| `erp410.ship` | admin, manager | проведение отгрузки — расход со склада |
| `erp410.invoice` | admin, manager, accountant | выставление счетов и приём оплаты |
| `erp410.*` | admin | всё, включая будущие действия |

## JSON API

Раздел `/sales/api/*` отдаёт JSON и требует право `erp410.view` (кроме
`token`, равного токену миграций, — для проверок стенда). Действия:

* чтение — `stats`, `orders`, `order`, `shipments`, `shipment`, `invoices`,
  `invoice`, `customers`, `customer`, `price`, `prices`;
* запись — `order_create`, `order_update`, `order_line_add`, `order_act`,
  `shipment_create`, `shipment_build`, `shipment_act`, `invoice_create`,
  `invoice_act`, `customer_save`, `price_record`.

Каждое действие проверяет своё право (`erp410.manage` / `erp410.ship` /
`erp410.invoice`) и вызывает сервис модуля: правила переходов, резерв, списание
и журнал живут в сервисах, а не в контроллерах. Ошибка возвращается в формате
`{ok: false, error: {code, message}}` и **останавливает выполнение**: Konine не
прерывает действие после отправки ответа, поэтому после `_json_fail()` стоит
`return;` (следит правило аудита `json_guards`).

Потребители: erp801_analytics (выручка и отгрузки), erp404_documents (печать

проверяет соседей через `class_exists()`.

## Проверка

```bash
make check-module module=erp410_shipment
bin/test --filter=Erp410
```

Сервисные тесты (`tests/Unit/Erp410ShipmentTest.php`) проверяют: нумерацию,
цены (каскад и запись в историю), резерв и его откат, лимит клиента, отгрузку
через резерв и напрямую, частичную отгрузку, счёт из отгрузки, дубль счёта,
частичную и полную оплату, отмену, состояния заказа и отгрузки, а также
объявления MCP и права. Живые страницы проверяются дымом (`bin/console
dev:smoke --module=erp410_shipment`).

## Ограничения и что дальше

* **Печати нет.** Накладная и счёт печатаются в erp404_documents; источник для
  `erp410_shipment` со стороны erp410 пока не добавлен — печать появится, когда
  у документов продажи будет макет.
* **Возвратов нет.** Возврат клиента — отдельный документ; сейчас обратное
  движение оформляется приходом в модуле склада.
* **Отсрочка не блокирует отгрузку сама.** Просроченная задолженность видна и
  подсвечена, но решение «не отгружать» принимает человек.
* **Цена за ноль.** Позиция без цены добавляется в заказ с нулём и
  предупреждением; жёсткой блокировки нет — по некоторым контрактам цена
  указывается в договоре иначе.
* **Брони склада.** Резерв ставится только при наличии остатка; отрицательный
  резерв не создаётся, частичного резерва не остаётся.
