> обязательной зависимостью производственных модулей. `erp227` владеет объектами

## Обзор
Модуль **Master Data Management (MDM)** предназначен для консолидации, очистки и верификации мастер-данных по изделиям и компонентам холдинга. Система обеспечивает создание «Золотой записи» (Golden Record) — наиболее достоверного набора атрибутов объекта, собранного из различных источников (ERP, PLM, AI).

## Принятие существующей схемы

Начальная PostgreSQL-миграция поддерживает базы, где MDM-схема была создана старым runner-ом, но запись в `migrations_pg` отсутствует. При запуске из `/migrate_pg` она:

- проверяет обязательные колонки уже существующих таблиц и секционирование `objects`, `object_properties`, `baselines`;
- в одной транзакции создаёт отсутствующие таблицы и индексы, переустанавливает функции, триггеры и RLS-политики и добавляет отсутствующие seed-записи;
- только после полного успеха регистрируется как применённая и позволяет выполнить следующие MDM-миграции;
- при несовместимой таблице откатывает транзакцию и показывает точный список отсутствующих колонок/несекционированных таблиц.

Вручную добавлять запись о `pgMigration_000_erp230_mdm_create_tables` в реестр нельзя.

## Основной функционал
*   **Консолидация данных:** Автоматический прием данных из внешних систем и сопоставление через кросс-референсы (`object_xref`).
*   **Управление Golden Record:** Выбор эталонного значения атрибута на основе баллов доверия (`trust score`) источников.
*   **Data Stewardship (Арбитраж):** Интерфейс для ручного разрешения конфликтов данных и верификации изменений.
*   **Управление НСИ:** Ведение иерархии типов изделий (`ltree`) и справочника единиц измерения (UOM).
*   **Цифровой двойник и Поиск:** Глобальный поиск, включая векторный/семантический поиск через LLM-индекс (`pg_vector`) и визуализацию структур (BOM).
*   **Контроль целостности:** Формирование неизменяемых снимков (Baselines) с проверкой цепочки хешей (Blockchain-like).

## Архитектура БД
База данных спроектирована на PostgreSQL 14+ с использованием продвинутых расширений:
*   `ltree`: Для иерархических структур (типы, орг. единицы).
*   `vector`: Для хранения эмбеддингов и семантического поиска.
*   `tstzrange`: Для реализации Time-Travel (хранение истории изменений атрибутов).
*   **Секционирование:** Таблицы `objects`, `object_properties` и `baselines` секционированы по годам (`created_at`) для обеспечения высокой производительности.

### Ключевые таблицы:
1.  `objects`: Реестр мастер-записей.
2.  `object_properties`: EAV-хранилище атрибутов с указанием источника и периода валидности.
3.  `object_links`: Графовые связи для построения EBOM/MBOM.
4.  `baselines`: Снимки состояния объекта с контролем целостности через `snapshot_hash`.
5.  `sources`: Реестр систем-источников с указанием уровня доверия (`trust`).
6.  `object_state`: Денормализованное представление актуального состояния объекта, включая агрегированные атрибуты (`attributes` в формате jsonb). Используется для быстрого получения отображаемого имени (`name`).
7.  `object_embeddings`: Векторные представления (эмбеддинги) объектов для семантического поиска.

## Принципы работы с Golden Record

### 1. Автоматический выбор (Trust Score)
При поступлении данных из разных систем (например, Teamcenter и AI Matcher), MDM сравнивает уровень доверия источников:
*   Если данные из **PLM (Trust: 90)** конфликтуют с данными из **AI (Trust: 30)**, система автоматически отдает приоритет PLM.
*   Логика реализована на уровне БД через функцию `upsert_property`.

### 2. Жизненный цикл атрибута
Атрибуты хранятся в модели EAV с использованием `tstzrange`. Это позволяет:
*   Видеть актуальное значение на текущий момент (`is_current`).
*   Восстановить состояние объекта на любую дату в прошлом.

Обратите внимание: атрибут `name` (наименование объекта) не является полем таблицы `objects`, а хранится как свойство. Отображаемое имя подтягивается в заголовки карточек и списки из `object_state.attributes->>'name'`.

### 3. Жизненный цикл объекта (State Machine)
Смена состояния объекта строго контролируется матрицей допустимых переходов на уровне модели (`Model_Erp230_Object::transition_to()`):
*   `draft` → `active`, `archived`
*   `active` → `archived`, `merged`
*   `archived` → `active`
*   `merged` → (терминальное состояние)

Прямая установка состояния `merged` извне запрещена — оно назначается исключительно операцией слияния (`action_merge`), которая переносит свойства и связи с проигравшей записи (loser) на выигравшую (winner) и фиксирует событие в baseline для аудита.

### 4. Безопасность (RLS)
Доступ к данным ограничен на уровне строк (Row Level Security). Контекст безопасности устанавливается **на каждый HTTP-запрос** в `Controller/Erp230/Main::before()` через `set_config('app.current_user_id', ...)` и `set_config('app.role', ...)`. Дополнительно контекст дублируется по событию `auth.login_success`.
*   **Admin:** Полный доступ ко всем данным холдинга.
*   **Editor/Viewer:** Доступ только к объектам своей организации и дочерних подразделений (проверка через `ltree` путь `org_path`).

## Маршрутизация (Routing)
Актуальный набор роутов модуля (порядок важен: специфичные объявляются выше общего):

*   `erp230_api_object_sub` — вложенные действия объекта: `erp230_api/object/<id>/<action>`.
*   `erp230_api_twin_state` — состояние цифрового двойника на момент времени: `erp230_api/twin/<id>/state` (action: `state_at`).
*   `erp230_mdm_api` — общий API-роут: `erp230_api(/<action>(/<id>))`.
*   `erp230_mdm_base` — базовые контроллеры UI: `erp230_<controller>(/<action>(/<id>))` (index, stewardship, dictionary, widget, main, objects).

## Архитектурный принцип: тонкие контроллеры, толстые модели
Вся работа с БД — включая рекурсивные CTE (разузлование BOM), time-travel-срезы и агрегаты дашборда — сосредоточена в моделях. Контроллеры остаются тонкими: они лишь принимают параметры запроса, вызывают доменные методы моделей и сериализуют результат (JSON/View). Прямые вызовы `DB::query` из контроллеров исключены.

Ключевые доменные методы `Model_Erp230_Object`:
*   `display_name()` — отображаемое имя: `object_state.attributes->>'name'` с фолбэком на текущее свойство `key='name'` (один запрос, без N+1).
*   `current_properties()` — актуальные свойства в виде `key => детали`.
*   `children($type = 'ebom')` — прямые дочерние связи (одноуровневый BOM).
*   `bom_tree($type = 'ebom', $depth = 20)` — разузлование вниз (рекурсивный CTE), плоский список рёбер.
*   `where_used($type = 'ebom', $depth = 20)` — обратный обход вверх (где используется компонент).
*   `state_at($at = NULL)` — срез свойств на заданный момент времени (time-travel).
*   `dashboard_stats()` — статические агрегаты для дашборда (сводка по `objects` + количество `types`/`org_units`).

## Техническая структура модуля

*   `Controller/Erp230/Main.php`: Базовый контроллер модуля. Устанавливает RLS-контекст на каждый запрос.
*   `Controller/Erp230/Api.php`: Тонкий REST-слой для интеграций и фронтенда. Делегирует чтения доменным методам модели (`display_name()`, `current_properties()`, `children()`, `bom_tree()`, `where_used()`, `state_at()`), сам лишь нормализует параметры и формирует ответ (например, `_nest()` для дерева BOM).
*   `Controller/Erp230/Objects.php`: UI-контроллер работы с объектами; отображаемое имя берётся через `$object->display_name()`.
*   `Controller/Erp230/Index.php`: Дашборд. Метрики получает через `Model_Erp230_Object::dashboard_stats()`, кэширование выполняется в контроллере.
*   `Model/Erp230/Object.php`: Мастер-запись, машина состояний (`transition_to`) и вся доменная работа с БД (CTE/агрегаты/чтения). См. перечень методов выше.
*   `Model/Erp230/Property.php`: Бизнес-логика обработки атрибутов и весов доверия.
*   `Model/Erp230/Baseline.php`: Механизмы хеширования и верификации снимков.
*   `Model/Erp230/Search.php`: Семантический (векторный) поиск (`semantic_search`).
*   `Model/Erp230/Xref.php`: Кросс-референсы (read-only для ORM, запись только через `DB::query` из-за составного PK).
*   `Service/Erp230/Consolidation.php`: Сервис первичной обработки входящих данных. Содержит канонический `create_snapshot()`.
*   `Service/Erp230/GoldenRecord.php`: Пересборка Golden Record; `create_snapshot()` проксирует в `Consolidation`.

## Интеграция и поиск
Для активации векторного поиска используется таблица `object_embeddings`. Метод `Model_Erp230_Search::semantic_search($vector_json, $limit)` выполняет запрос с сортировкой по косинусному сходству (`ORDER BY embedding <=> :vec`, оператор `vector_cosine_ops`) и возвращает `object_id` и `distance`. Это позволяет находить аналоги изделий даже при различии в текстовом описании. При отсутствии реализации/расширения API возвращает корректный `503`.
