Бизнес-логика и обзор системы MDM (v5.3)

Настоящий документ описывает архитектурные принципы, бизнес-логику и ключевые механизмы функционирования модуля управления мастер-данными (MDM), сертификации и цифровых двойников.

### 1. Концепция «Золотой записи» (Golden Record)

Центральной задачей системы является формирование максимально достоверного набора данных об объекте (изделии, компоненте, агрегате) при условии, что данные могут поступать из множества противоречивых источников.

*   **Уровни доверия (Trust Score):** Каждый источник данных (`sources`) имеет числовой показатель доверия (от 0 до 100). 
*   **Автоматический арбитраж:** При обновлении свойства функция `upsert_property` сравнивает уровень доверия нового источника с текущим. Если новый источник менее надежен, изменение отклоняется (`rejected_low_trust`).
*   **Приоритеты:** Данные из инженерных систем (PLM, Teamcenter) по умолчанию имеют более высокий приоритет, чем данные из учетных систем (ERP) или систем автоматического распознавания (AI).

### 2. Временная модель данных (Time-Travel)

Система реализует концепцию неизменяемости данных (Immutability) для аудита и анализа истории.

*   **EAV + Valid Period:** Свойства объектов хранятся в таблице `object_properties` с использованием типа `tstzrange`. 
*   **История изменений:** Вместо перезаписи (UPDATE) значения, система «закрывает» текущую версию свойства датой настоящего момента и создает новую запись.
*   **Срез состояния:** Благодаря этой модели, система может мгновенно реконструировать облик изделия на любую дату в прошлом (метод `state_at`).

### 3. Организационная структура и безопасность (Multi-tenancy)

Система спроектирована для работы в рамках крупного холдинга с разграничением прав доступа между дочерними обществами.

*   **Иерархия (ltree):** Организационные единицы (`org_units`) и типы объектов (`types`) организованы в деревья. Это позволяет применять правила доступа и поиска ко всей ветке (например, «все объекты КБ Сухого»).
*   **Row Level Security (RLS):** Безопасность реализована на уровне ядра БД. Пользователь видит только те строки, которые соответствуют его `org_path`. 
*   **Ролевая модель:**
    *   `viewer`: Только чтение данных своей организации.
    *   `editor`: Создание и редактирование объектов своей организации.
    *   `admin`: Полный доступ, включая управление справочниками и удаление (soft-delete).

### 4. Целостность и сертификация (Baselines)

Для целей сертификации и фиксации этапов проектирования/производства используется механизм бейслейнов.

*   **Снимки (Snapshots):** Бейслейн — это неизменяемый JSON-снимок всех свойств объекта в конкретный момент времени.
*   **Хэш-цепочки (Blockchain-like):** Каждая запись в `baselines` содержит хэш своих данных и хэш предыдущего бейслейна. Это гарантирует, что данные не были подменены напрямую в базе данных.
*   **Верификация:** Функция `verify_baseline_chain` позволяет проверить целостность всей истории изменений объекта. Любое несанкционированное изменение приведет к разрыву цепочки хэшей.

### 5. Цифровой двойник и производительность

Для обеспечения высокой скорости работы при больших объемах данных (миллионы свойств) используются механизмы денормализации и секционирования.

*   **Object State:** Актуальные свойства из «вертикальной» таблицы EAV агрегируются в «плоскую» таблицу `object_state`. Это позволяет выполнять быстрый поиск и фильтрацию без сложных JOIN-соединений.
*   **Секционирование (Partitioning):** Таблицы `objects`, `object_properties` и `baselines` автоматически разбиваются на секции по годам. Это упрощает обслуживание БД и ускоряет запросы к актуальным данным.
*   **Векторный поиск:** Система хранит эмбеддинги объектов (`object_embeddings`), что позволяет выполнять семантический поиск (поиск по смыслу и сходству характеристик), а не только по точному совпадению кода или названия.

### 6. Жизненный цикл объекта

Объект в MDM проходит через строгую последовательность состояний:
1.  **Draft:** Черновик, виден только создателю.
2.  **Active:** Эталонная запись, доступная для использования в связанных системах.
3.  **Archived:** Объект выведен из эксплуатации, но сохранен для истории.
4.  **Merged:** Объект признан дублем и объединен с другой «золотой записью».

Любое изменение состояния фиксируется в аудите и может требовать создания автоматического бейслейна.
