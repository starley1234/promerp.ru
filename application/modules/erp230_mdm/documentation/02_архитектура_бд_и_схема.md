Архитектура БД и схема системы MDM (v5.3)

Настоящий документ содержит детальное описание физической структуры базы данных, механизмов обеспечения целостности, безопасности и производительности.

### 1. Схема базы данных (ER-диаграмма и логика)

Система построена на гибридной модели: классические справочники (НСИ) сочетаются с гибкой структурой EAV (Entity-Attribute-Value) для хранения характеристик объектов.

#### 1.1. Ядро системы (Объекты и Свойства)
*   **objects**: Главная таблица реестра. Использует секционирование (Partitioning) по дате создания (`created_at`). Это позволяет сохранять высокую производительность при росте базы до десятков миллионов записей.
*   **object_properties**: Хранилище атрибутов. Реализует концепцию **Time-Travel**:
    *   Поле `valid_period` (тип `tstzrange`) определяет интервал актуальности значения.
    *   Поле `is_current` (computed) позволяет мгновенно выбирать только действующие значения.
*   **object_state**: Денормализованное представление объекта. Содержит агрегированный JSON со всеми текущими свойствами. Обновляется автоматически триггером `refresh_object_state`.

#### 1.2. Иерархии и связи
*   **org_units** и **types**: Используют расширение `ltree` для хранения путей (например, `ROOT.PLANT1.SHOP5`). Это обеспечивает:
    *   Поиск по всей ветке иерархии одним запросом.
    *   Наследование прав доступа.
*   **object_links**: Таблица связей для построения структур изделия (EBOM/MBOM). Поддерживает типизацию связей и количественные показатели (`qty`).

### 2. Механизмы обеспечения достоверности

#### 2.1. Арбитраж данных (Trust Score)
Логика встроена в функцию `upsert_property`. При попытке обновить значение свойства система:
1. Извлекает `trust` текущего источника и нового.
2. Если `new_trust >= old_trust`, старая запись «закрывается» (устанавливается верхняя граница `valid_period`), и создается новая.
3. Если доверие ниже — операция отклоняется с кодом `rejected_low_trust`.

#### 2.2. Целостность и аудит (Hash-Chains)
Таблица **baselines** реализует механизм, аналогичный блокчейну:
*   Каждый бейслейн содержит `snapshot_hash`.
*   Хэш вычисляется на основе данных текущего снимка и `prev_hash` (хэша предыдущего бейслейна этого объекта).
*   Триггер `trg_baseline_chain` гарантирует неизменность цепочки при вставке.
*   Функция `verify_baseline_chain` позволяет выявить любые манипуляции с данными на уровне БД.

### 3. Безопасность (Row Level Security)

Безопасность реализована на уровне ядра PostgreSQL, что исключает утечку данных даже при прямом доступе к БД через сторонние инструменты.

*   **Контекст пользователя:** Перед выполнением запросов приложение устанавливает переменные `app.current_user_id` и `app.role`.
*   **Политики (Policies):**
    *   `viewer`: Видит объекты, где `org_path` совпадает или является дочерним по отношению к его организации (`path <@ user_org_path`).
    *   `editor`: Может изменять данные только своей ветки организации.
    *   `admin`: Имеет доступ ко всем записям и операциям удаления.

### 4. Производительность и масштабирование

#### 4.1. Секционирование (Partitioning)
Таблицы `objects`, `object_properties` и `baselines` разбиты на секции по годам. 
*   Функция `ensure_partition` автоматически создает новые таблицы (например, `objects_y2026`) при наступлении нового периода.
*   Запросы к актуальным данным затрагивают только последнюю секцию, что минимизирует нагрузку на дисковую подсистему.

#### 4.2. Индексация
*   **GIST индексы**: Используются для полей `ltree` (пути) и `tstzrange` (периоды), обеспечивая мгновенный поиск по иерархии и временным срезам.
*   **GIN индексы**: Применяются к JSONB полям в `object_state` для быстрого поиска по произвольным атрибутам.
*   **HNSW индексы**: Используются в таблице `object_embeddings` для векторного поиска похожих объектов (цифровых двойников) с использованием расширения `pgvector`.

### 5. Схема жизненного цикла данных (Data Flow)

1.  **Вход**: Данные поступают через `upsert_property` (проверка Trust Score).
2.  **Обработка**: Триггеры обновляют `object_state` и проверяют уникальность `master_code`.
3.  **Хранение**: Данные распределяются по секциям в зависимости от даты транзакции.
4.  **Фиксация**: По требованию или событию создается `baseline` с расчетом хэш-суммы.
5.  **Выход**: Потребители читают данные из `object_state` (текущие) или через `verify_baseline_chain` (сертифицированные).
