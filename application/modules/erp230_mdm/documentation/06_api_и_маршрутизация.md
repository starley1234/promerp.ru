API и маршрутизация системы MDM (v5.3)

Настоящий документ описывает механизмы взаимодействия с системой через REST API, структуру маршрутов и логику работы сервисного слоя.

### 1. Принципы построения API

API системы MDM спроектировано по стандарту REST и ориентировано на интеграцию с внешними инженерными (PLM) и учетными (ERP) системами.

*   **Формат обмена:** JSON.
*   **Идентификация:** Все объекты используют UUID (v4) в качестве первичных ключей.
*   **Контекст безопасности:** Каждый запрос выполняется в рамках сессии пользователя. Перед выполнением SQL-запросов API-контроллер устанавливает переменные `app.current_user_id` и `app.role` для активации политик RLS (Row Level Security).

### 2. Маршрутизация (Routing)

Основные маршруты модуля определены в `init.php`. Базовый префикс для API: `/mdm/api/`.

| Метод | Эндпоинт | Описание |
| :--- | :--- | :--- |
| **GET** | `/objects` | Список мастер-записей с фильтрацией по типу и организации. |
| **POST** | `/object` | Создание новой мастер-записи (паспорта объекта). |
| **GET** | `/object/<id>` | Полные данные объекта, включая текущие свойства и структуру. |
| **POST** | `/properties/<id>` | Пакетное обновление свойств (использует логику Trust Score). |
| **GET** | `/bom_tree/<id>` | Получение полного дерева состава изделия (рекурсивный CTE). |
| **POST** | `/snapshot` | Создание неизменяемого бейслейна (снимка состояния). |
| **GET** | `/resolve` | Поиск UUID объекта по внешнему ID (Xref) из другой системы. |

### 3. Ключевые методы моделей

#### Model_Erp230_Object (Мастер-записи)
*   `registry(filters)`: Возвращает список объектов. Автоматически применяет фильтры прав доступа, чтобы пользователь видел только разрешенные `org_path`.
*   `state_at(timestamp)`: Реализует функционал Time-Travel. Формирует состояние объекта, актуальное на указанный момент времени, выбирая записи из `object_properties`, где `timestamp <@ valid_period`.
*   `transition_to(new_state)`: Валидирует и выполняет переход по жизненному циклу (например, из `draft` в `active`).

#### Model_Erp230_Property (EAV и Доверие)
*   `upsert_safe(...)`: Главный метод записи данных. 
    1. Проверяет `trust_score` источника.
    2. Если проверка пройдена, вызывает хранимую процедуру БД для «закрытия» старого значения и открытия нового.
    3. Инициирует обновление денормализованной таблицы `object_state`.

#### Model_Erp230_Baseline (Целостность)
*   `verify_chain(object_id)`: Проходит по всей цепочке снимков объекта, пересчитывая SHA-256 хэши. Если `current_hash` не совпадает с `prev_hash` следующей записи, метод возвращает ошибку валидации.

### 4. Сервисный слой (Service Layer)

Для сложных бизнес-процессов, затрагивающих несколько моделей, используются сервисы:

*   **Service_Erp230_Consolidation:** Отвечает за импорт данных. Сопоставляет входящие записи через таблицу `object_xref`. Если объект найден, обновляет его свойства; если нет — создает новую мастер-запись и связку (Xref).
*   **Service_Erp230_Search:** Реализует гибридный поиск. Сочетает классический полнотекстовый поиск по атрибутам и векторный поиск (через `pgvector`) для нахождения похожих цифровых двойников по их характеристикам.

### 5. Обработка ошибок и коды ответов

Система использует стандартные HTTP-статусы с расширенным телом ответа:

*   `200 OK`: Успешное выполнение.
*   `201 Created`: Объект успешно создан.
*   `403 Forbidden`: Ошибка RLS (попытка доступа к объекту чужой организации).
*   `409 Conflict`: Ошибка Trust Score (попытка записи данных из менее надежного источника) или нарушение уникальности `master_code`.
*   `422 Unprocessable Entity`: Данные не прошли валидацию по JSON-схеме типа объекта.

### 6. Пример интеграционного сценария

1.  **Поиск:** Внешняя система запрашивает `/mdm/api/resolve?source=PLM&remote=PART-99`.
2.  **Получение ID:** MDM возвращает внутренний `object_id`.
3.  **Обновление:** Внешняя система отправляет `POST /mdm/api/properties/{id}` с новыми значениями веса.
4.  **Арбитраж:** Система проверяет, что источник `PLM` имеет `trust=90`, что выше текущего `manual=50`.
5.  **Результат:** Свойство обновляется, создается новая версия в истории, старая версия сохраняется для аудита.
