Безопасность, RLS и ролевая модель MDM (v5.3)

Настоящий документ описывает механизмы разграничения прав доступа, реализованные на уровне ядра базы данных (Row Level Security), и структуру ролей пользователей.

### 1. Принципы Multi-tenancy

Система MDM спроектирована для обслуживания холдинговых структур, где данные различных дочерних обществ (ДО) должны быть изолированы друг от друга, но доступны на уровне управляющей компании.

*   **Иерархическая изоляция:** Использование типа `ltree` для поля `org_path` позволяет строить правила доступа на основе вложенности. Если пользователь привязан к узлу `ОАК.Сухой`, он автоматически получает доступ к данным узлов `ОАК.Сухой.КБ` и `ОАК.Сухой.Завод`, но не видит данные `ОАК.МиГ`.
*   **Сквозная безопасность:** Правила RLS применяются ко всем базовым таблицам: `objects`, `object_properties` и `baselines`. Это гарантирует, что даже при выполнении прямого SQL-запроса через сторонние инструменты (например, DBeaver), пользователь не увидит чужие данные.

### 2. Ролевая модель

В системе определены три базовые роли, управляющие уровнем доступа к объектам внутри разрешенной ветки организации:

| Роль | Права доступа | Описание |
| :--- | :--- | :--- |
| **viewer** | SELECT | Просмотр объектов и их свойств в рамках своей организации и ниже по дереву. |
| **editor** | SELECT, INSERT, UPDATE | Создание новых объектов, изменение свойств (через арбитраж). Запрещено удаление. |
| **admin** | ALL PRIVILEGES | Полный доступ к данным, управление справочниками, мягкое и физическое удаление, аудит. |

### 3. Техническая реализация RLS

Безопасность базируется на сессионных переменных PostgreSQL, которые устанавливаются приложением при каждом подключении.

#### Контекст пользователя
Перед выполнением бизнес-логики приложение выполняет:
```sql
SET app.current_user_id = 'user_uuid';
SET app.role = 'editor';
```

#### Функции проверки доступа
В БД реализованы вспомогательные функции для политик:
*   `current_user_org_path()`: Возвращает `ltree` путь организации текущего пользователя.
*   `tenant_can_see(p_org_path)`: Проверяет, является ли запрашиваемый путь частью разрешенной ветки (`path <@ user_org_path`).
*   `tenant_can_write(p_org_path)`: Проверяет права на запись (роль `admin` или `editor` в своей ветке).

#### Примеры политик (Policies)
```sql
-- Политика на чтение объектов
CREATE POLICY p_obj_select ON objects 
FOR SELECT USING (tenant_can_see(org_path));

-- Политика на изменение (только для editor и admin)
CREATE POLICY p_obj_update ON objects 
FOR UPDATE USING (tenant_can_write(org_path));
```

### 4. Безопасность свойств и арбитраж

Помимо RLS, доступ к изменению свойств (`object_properties`) ограничен функцией `upsert_property`. 

1.  **Защита от перезаписи:** Даже если у пользователя есть роль `editor`, он не может напрямую изменить значение, если уровень доверия (`trust score`) его источника данных ниже, чем у текущего значения.
2.  **Security Definer:** Функция `upsert_property` выполняется с правами владельца схемы, что позволяет корректно закрывать старые версии свойств (Time-Travel), сохраняя при этом строгий контроль доступа для вызывающего пользователя.

### 5. Целостность и аудит (Compliance)

Для обеспечения юридической значимости и защиты от несанкционированного изменения данных «задним числом» используется механизм бейслейнов:

*   **Неизменяемость:** Таблица `baselines` является Append-Only (только для вставки). Политики RLS запрещают UPDATE и DELETE для этой таблицы даже для роли `admin`.
*   **Цифровая подпись:** Каждый бейслейн может быть подписан электронной подписью (`signature`), хэш которой проверяется функцией `verify_baseline_chain`.
*   **Обнаружение манипуляций:** Если администратор БД попытается изменить данные в обход RLS (на уровне файловой системы или суперпользователя), цепочка хэшей `snapshot_hash` будет разорвана, что мгновенно выявится при следующей проверке сертификации объекта.

### 6. Рекомендации по настройке

1.  **Принцип минимальных привилегий:** Новым пользователям по умолчанию должна назначаться роль `viewer`.
2.  **Управление источниками:** Уровни доверия в таблице `sources` должны редактироваться только глобальным администратором MDM, так как они напрямую влияют на целостность «Золотой записи».
3.  **Аудит сессий:** Все изменения в `object_properties` логируют `source_id`, а в `baselines` — `actor_id`, что позволяет восстановить историю действий конкретного сотрудника.
