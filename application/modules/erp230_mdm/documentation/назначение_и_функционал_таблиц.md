Назначение и функционал таблиц базы данных MDM (v5.3)

Данная база данных спроектирована для управления мастер-данными (MDM), сертификацией и создания «цифровых двойников» сложных изделий (например, самолетов). Она поддерживает версионность, иерархии, разграничение прав доступа (RLS) и автоматическое секционирование данных по годам.

### 1. Основные сущности и их назначение

#### Блок 1: НСИ (Справочники)
*   **org_units**: Организационная структура (КБ, заводы, цеха). Использует тип `ltree` для быстрого поиска по дереву (например, «ОАК.Сухой.Цех1»).
*   **types**: Классификатор объектов (например: «Крыло», «Двигатель», «Заклепка»). Позволяет задавать JSON-схемы для валидации параметров.
*   **sources**: Источники данных (PLM-система, ERP, ручной ввод). У каждого источника есть уровень доверия (`trust`).
*   **uom**: Единицы измерения с коэффициентами пересчета (кг, граммы, метры).

#### Блок 2 и 3: Объекты и Свойства (EAV + Time-Travel)
Это ядро системы. Вместо создания сотен таблиц для разных деталей, используется гибкая модель:
*   **objects**: Реестр самих сущностей. Каждая запись — это «паспорт» объекта.
*   **object_properties**: Все характеристики объекта (вес, материал, длина). 
    *   **Time-Travel**: Свойства не удаляются. При изменении старая запись закрывается датой (`valid_period`), а новая открывается. Это позволяет увидеть, каким был объект месяц назад.
    *   **Конфликты**: Если данные приходят из разных систем, триггер выберет ту, у которой выше `trust` (доверие).

#### Блок 4: Графы (Связи)
*   **object_links**: Описывает состав изделия (BOM). 
    *   *Пример:* Связь «Крыло» (parent) -> «Нервюра» (child) с указанием количества (`qty`).

#### Блок 5: Бейслайны (Снимки состояния)
*   **baselines**: Фиксация состояния объекта на определенный момент (например, «Конструкторский облик утвержден»). 
    *   Использует **Hash-chain**: каждая новая запись содержит хэш предыдущей. Если кто-то вручную изменит данные в базе в обход системы, цепочка «сломается», и проверка `verify_baseline_chain` это покажет.

### 2. Как это работает (Механизмы)

#### Автоматическое секционирование (Partitioning)
Таблицы `objects`, `properties` и `baselines` автоматически делятся на части по годам (например, `objects_y2025`). Это предотвращает замедление базы при накоплении миллионов записей.

#### Безопасность (RLS)
Система автоматически фильтрует данные на уровне SQL. Если разработчик делает `SELECT * FROM objects`, база сама добавит условие, чтобы пользователь из «Завода №1» не увидел чертежи «Завода №2».

#### Цифровой двойник (Object State)
Для быстрой работы создается «плоская» таблица `object_state`. Она собирает все текущие свойства из EAV-таблицы в один JSON-объект. Это позволяет мгновенно получить текущий вид изделия без сложных соединений (JOIN).

### 3. Примеры использования в авиастроении

#### А. Добавление нового агрегата (Двигатель)
1. Создаем запись в `objects` с типом `engine` и мастер-кодом `ENG-123-2024`.
2. Триггер `trg_objects_before_ins` автоматически пропишет путь организации и проверит уникальность кода.

#### Б. Склейка данных из разных систем (PLM и Весовая лаборатория)
1. Система PLM (trust=90) передает вес двигателя: 2000 кг. Записывается в `object_properties`.
2. Датчик весовой платформы (trust=95) передает вес: 2005 кг.
3. Функция `upsert_property` видит, что у датчика доверие выше, «закрывает» старую запись PLM и создает новую актуальную запись.

#### В. Создание состава изделия (Связи)
Чтобы собрать самолет, мы добавляем записи в `object_links`:
*   `parent_id`: UUID Самолета
*   `child_id`: UUID Крыла
*   `link_type`: 'structural' (конструктивная связь)

#### Г. Проверка целостности (Сертификация)
Перед вылетом создается `baseline`. Если через год возникнет спор о комплектации, функция `is_chain_valid(object_id)` подтвердит, что запись о деталях не подменялась задним числом, так как хэш-цепочка неизменна.

### Краткая шпаргалка для разработчика:
*   **Нужно изменить свойство?** Используй `SELECT upsert_property(...)`. Не делай прямой `INSERT` в `object_properties`, иначе сломаешь логику доверия и версионность.
*   **Нужно прочитать текущее состояние?** Запрашивай таблицу `object_state`.
*   **Нужно дерево подчиненности?** Используй операторы `ltree` (например, `path <@ 'ОАК.Сухой'`).
*   **Важно:** Перед выполнением запросов от имени пользователя обязательно установи контекст: 
    `SET app.current_user_id = 'имя_пользователя';` — иначе RLS не даст увидеть данные.
