Состояния и жизненный цикл объекта MDM (v5.3)

Настоящий документ описывает логику переходов состояний объектов, правила смены статусов и автоматизированные действия, сопровождающие жизненный цикл мастер-данных.

### 1. Карта состояний (State Machine)

Каждый объект в системе MDM (`objects.state`) всегда находится в одном из четырех базовых состояний. Переходы между ними строго регламентированы.

| Состояние | Описание | Доступность |
|:---|:---|:---|
| **Draft** (Черновик) | Объект находится в процессе создания или первичного наполнения данными. | Виден только создателю и администраторам. Не участвует в глобальном поиске. |
| **Active** (Активен) | Эталонная «Золотая запись». Объект прошел проверки и готов к использованию. | Доступен всем потребителям (с учетом RLS). Используется в EBOM/MBOM. |
| **Archived** (Архив) | Объект выведен из эксплуатации (снят с производства, заменен). | Доступен только для чтения истории. Создание новых связей запрещено. |
| **Merged** (Объединен) | Объект признан дублем и присоединен к другому объекту. | Терминальное состояние. Перенаправляет запросы на «объект-победитель». |

### 2. Жизненный цикл и триггеры переходов

#### 2.1. Создание (Draft)
При создании объекта через API или интерфейс ему автоматически присваивается статус `draft`. 
*   **Действие:** В таблице `object_codes` резервируется `master_code`.
*   **Условие:** Наличие минимально необходимого набора атрибутов согласно схеме типа (`types.schema`).

#### 2.2. Публикация (Draft -> Active)
Перевод в `active` означает, что данные проверены и объект становится «Золотой записью».
*   **Автоматизация:** При переходе в `active` система автоматически создает первый **Baseline** (снимок состояния).
*   **Валидация:** Проверка целостности всех обязательных свойств и корректности единиц измерения (UOM).

#### 2.3. Модификация (Active -> Active)
Объект остается активным, но его свойства меняются через `upsert_property`.
*   **Механизм:** Если новое значение имеет более высокий `trust`, создается новая версия свойства в `object_properties`.
*   **Событие:** Поле `is_dirty` устанавливается в `true`, сигнализируя о необходимости обновления `object_state` или создания нового бейслейна.

#### 2.4. Архивация (Active -> Archived)
Объект переводится в архив, если он больше не должен использоваться в новых структурах.
*   **Ограничение:** Нельзя архивировать объект, если он является активным компонентом (child) в составе другого активного изделия.
*   **Результат:** Все входящие связи в `object_links` помечаются как исторические.

#### 2.5. Слияние (Active/Draft -> Merged)
Процедура устранения дубликатов.
*   **Процесс:** Все свойства и связи «объекта-дубля» переносятся на основной объект.
*   **Связь:** В поле `merged_into` записывается UUID основного объекта.

### 3. Временная шкала (Time-Travel) и состояния

Жизненный цикл объекта неразрывно связан с моделью временных интервалов (`valid_period`).

1.  **Актуальное состояние:** Определяется срезом `upper(valid_period) IS NULL`.
2.  **Историческое состояние:** Любая точка в прошлом реконструируется путем фильтрации свойств, где дата запроса входит в диапазон `valid_period`.
3.  **Неизменность:** Состояния `Archived` и `Merged` фиксируют финальную точку жизненного цикла, после которой создание новых версий свойств (новых записей в `object_properties`) блокируется на уровне бизнес-логики.

### 4. Интеграция с процессами сертификации

Для объектов, подлежащих обязательной сертификации, жизненный цикл расширяется внешними событиями:

*   **Compliance Check:** Перед переходом в `Active` вызывается функция проверки соответствия нормативным документам. Результат записывается в `compliance_ref` бейслейна.
*   **Digital Signature:** Переход в статус `Active` для критических узлов требует электронной подписи (поле `signature` в таблице `baselines`). Любое изменение свойств после подписи сбрасывает статус объекта обратно в `Draft` или требует выпуска нового извещения об изменениях.

### 5. Автоматическое обновление состояния (Refresh Logic)

При любом изменении в жизненном цикле (смена статуса, обновление свойства, слияние) срабатывает процедура `refresh_object_state(p_object_id)`. Она выполняет:
1.  Сбор всех текущих (`is_current = true`) атрибутов.
2.  Обновление JSONB-поля `attributes` в таблице `object_state`.
3.  Пересчет поискового индекса `tsvector` для полнотекстового поиска.
4.  Обновление даты `updated_at` в корневом объекте.
