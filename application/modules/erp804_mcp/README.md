# erp804_mcp — MCP-сервер: агенты и внешние воркеры в PromERP

Модуль даёт LLM-агентам (Claude Desktop, Cursor, Continue, собственные агенты)
и внешним программам доступ к сервисам системы по протоколу
[MCP](https://modelcontextprotocol.io) — «Model Context Protocol».
Агент видит список инструментов, вызывает их и получает структурированный
ответ; всё, что он делает, видно человеку и при необходимости подтверждается.

Модуль **не владеет бизнес-данными**. Он не знает ни про заказы, ни про
склад: инструменты объявляют сами модули файлом `mcp.php` в своём корне,
а `erp804_mcp` отвечает за ключи, права, проверку аргументов, журнал вызовов
и подтверждения.

```
LLM-агент ──MCP(JSON-RPC)──▶ /mcp ──▶ реестр инструментов ──▶ сервис модуля
   ▲                             │
   └── ключ агента, права ───────┴── журнал вызовов (erp_804_mcp_calls) + erp119
```

## Что умеет

* **Инструменты (tools)** — MCP-методы вида `production.order.get`,
  `audit.journal.search`, `system.whoami`. Каждый объявляет право (`scope`),
  признак изменения данных (`mutating`) и при необходимости
  `approval` — «требует подтверждения человеком».
* **Ключи агентов** — отдельная учётная запись со своими правами, признаком
  «только чтение» и сроком жизни. Токен вида `mcp_…` показывается один раз;
  в базе лежит только его SHA-256.
* **Права** — те же имена, что в `application/config/acl.php`
  (`erp402_production.view`, `erp228.view`, …), поддерживаются префиксы
  `erp402_production.*` и `*`.
* **Идемпотентность** — повторный вызов с тем же `idempotency_key` не
  выполняется второй раз, а возвращает прежний результат: агент может
  спокойно повторить запрос после обрыва связи.
* **Подтверждения** — изменяющие операции (`production.order.complete`,
  `production.order.cancel`) останавливаются в статусе
  `awaiting_approval` и ждут решения человека в `/mcp/calls`.
* **Журнал** — каждый вызов записан (`erp_804_mcp_calls`): кто, что, с какими
  аргументами, чем закончилось, сколько миллисекунд занял. Изменяющие вызовы
  дополнительно уходят в журнал действий erp119.
* **Служебные инструменты** (`self`) — «кто я», «какие инструменты мне
  доступны», «что стало с моим вызовом»: доступны любому действующему ключу
  без отдельного права, иначе агенту нечем проверить свою же операцию.

## Транспорты

| Транспорт | Точка входа | Кому |
|---|---|---|
| HTTP demo QA | `POST /mcp/demo/discovery` | принудительный read-only; tools выполняются строго в demo |
| HTTP demo operator | `POST /mcp/demo/agent` | симуляция работы в demo; запись определяется отдельным ключом и approval |
| HTTP discovery (JSON-RPC 2.0) | `POST /mcp/discovery` | компактный поиск и безопасный прокси в основной базе |
| HTTP full (JSON-RPC 2.0) | `POST /mcp` | существующий полный каталог и выполнение найденных инструментов |
| HTTP (сведения) | `GET /mcp`, `GET /mcp/discovery` | проверка транспорта без ключа |
| stdio | `bin/console mcp:serve --key=…` | локальные клиенты (Claude Desktop, Cursor) |

Ключ передаётся заголовком `Authorization: Bearer mcp_…`,
`X-Mcp-Key`, `X-Api-Key` или параметром `?key=` (для отладки).
Поддерживаются пакеты запросов (batch) и уведомления.

```bash
curl -s http://127.0.0.1:8080/mcp \
  -H "Authorization: Bearer mcp_…" -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

### Компактное обнаружение инструментов

Если полный `tools/list` занимает слишком много контекста, подключите LLM к
`/mcp/discovery`. Для проверки собранного стенда используйте именно
`/mcp/demo/discovery`: он после аутентификации переключает выполнение на
`promerp_demo` и принудительно делает ключ read-only, даже если основной ключ
настроен шире. Эти endpoints используют тот же ключ и протокол, но объявляют
только два максимально явных инструмента: `system.tool.search` для поиска и
`system.tool.call` для выполнения найденного действия через штатные проверки.

Алгоритм для агента намеренно простой:

1. вызвать `system.tool.search` и передать задачу обычными словами;
2. взять `results[0]`, если его описание совпадает с намерением;
3. заполнить обязательные значения в `results[0].tool_arguments.arguments`;
4. передать весь `results[0].tool_arguments` прямо в `system.tool.call`;
5. не добавлять ещё одну обёртку `arguments`, не придумывать имена и не
   повторять один и тот же неудачный вызов.

`system.tool.call` принимает предпочтительный формат
`{"tool_name":"…","arguments":{…}}`, запасной `arguments_json`, плоский
формат `{"tool_name":"…","id":"…"}` и исправляет одну ошибочную внешнюю
обёртку `{"arguments":{"tool_name":"…","arguments":{…}}}`. Целевые аргументы всегда
повторно проходят штатный валидатор. Ошибка называет целевой tool, обязательные
и фактически полученные поля, но не печатает чувствительные значения payload.

```bash
curl -s https://example.test/mcp/discovery \
  -H "Authorization: Bearer mcp_…" -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"system.tool.search","arguments":{"query":"показать остатки ABS на складе","mode":"read"}}}'
```

Поиск учитывает имя, русское описание, аргументы и словарь русских/английских
терминов ERP. По умолчанию он ищет только чтение; запись нужно запросить явно
через `mode=write` или `mode=any`. Ранжируются только инструменты, доступные
текущему ключу, не больше пяти кандидатов. Точное имя даже внутри обычной фразы
возвращает ровно один результат. Для частых придуманных имён вроде
`planning.need.list`, `quality.check.list` и `analytics.kpi.get` поиск явно
сообщает, что имя недоступно, и возвращает один канонический инструмент вместо
бесконечного повторения поиска. Большой `system.tools.list` намеренно заменяется компактным
`system.tools.summary` с количеством по модулям. Даже если слабая модель всё
же передаст `system.tools.list` прокси-вызову, сервер вернёт сводку, а не 162
описания. В каждом кандидате есть назначение, безопасность, аргументы и готовый
JSON-RPC `tools/call`.

Протокол: MCP `2025-06-18`. Методы: `initialize`, `ping`, `tools/list`,
`tools/call`, `resources/list`, `prompts/list`, `notifications/*`.
При сериализации схем сервер принудительно отдаёт пустой `properties` как JSON-объект
`{}`, а не массив `[]`; это требуется строгими MCP-клиентами, включая LM Studio.
Коды ошибок JSON-RPC: `-32001` нет/неверный ключ, `-32003` нет права или ключ
только для чтения, `-32601` неизвестный метод или инструмент, `-32602`
аргументы не прошли проверку, `-32010` нужно подтверждение, `-32603` сбой.

## Интерфейс (для людей)

| Адрес | Что там |
|---|---|
| `/mcp/console` | состояние сервера, статистика вызовов, ожидающие подтверждения, последние вызовы |
| `/mcp/tools` | каталог инструментов: право, признак изменения, аргументы, замечания к объявлениям |
| `/mcp/calls` | журнал вызовов с фильтрами, кнопки «Подтвердить» / «Отклонить» |
| `/mcp/keys` | выдача, отзыв и включение ключей; токен показывается один раз |
| `/mcp/api/*` | JSON API управления (info, tools, calls, call, keys, key, approve, reject) |

## Права (application/config/acl.php)

```bash
bin/console mcp:tools                       # каталог инструментов
bin/console mcp:tools --check               # проверить объявления mcp.php
bin/console mcp:tools --json                # то же машинно-читаемо
bin/console mcp:key --name="Агент склада" --scopes=erp401_wms.view
bin/console mcp:key --name="Мастер цеха" --scopes=erp402_production.* --actor=1
bin/console mcp:key --list
bin/console mcp:key --revoke=3
bin/console mcp:serve --key=mcp_…           # MCP по stdio
```

## Как добавить инструменты в свой модуль

Файл `<модуль>/mcp.php`:

```php
return array(
    'module' => 'erp402',
    'tools'  => array(
        'production.orders.search' => array(
            'title'       => 'Поиск производственных заказов',
            'description' => 'Что видит агент: описание — единственный способ, которым LLM выбирает инструмент',
            'scope'       => 'erp402_production.view',   // право из application/config/acl.php
            'mutating'    => FALSE,                      // изменяет данные?
            'approval'    => FALSE,                      // TRUE — ждать подтверждения человека
            'handler'     => function (array $args) {    // обращение только к сервисам модуля
                $result = Service_Erp402_Orders::instance()->search($args);

                return array('summary' => 'Заказов: '.(int) $result['total'], 'orders' => $result['rows']);
            },
            'schema'      => array(
                'type'       => 'object',
                'properties' => array(
                    'term'  => array('type' => 'string', 'description' => 'Поиск по номеру и названию'),
                    'limit' => array('type' => 'integer', 'minimum' => 1, 'maximum' => 100, 'default' => 20),
                ),
                'required'   => array(),
            ),
        ),
    ),
);
```

Правила:

1. Обработчик вызывает **сервисы своего модуля** и не пишет в чужие таблицы.
2. Право (`scope`) должно быть объявлено в `application/config/acl.php`,
   иначе `dev:audit` выдаст замечание.
3. Пользовательские изменяющие инструменты помечаются `'mutating' => TRUE` —
   ключи «только чтение» их не увидят.
4. Опасные операции (выпуск, отмена, удаление) помечаются
   `'approval' => TRUE`: агент получит ответ «ждёт подтверждения» и сможет
   спросить статус через `system.call.status`.
5. Верните `summary` — короткую человекочитаемую строку: она попадает в текст
   ответа, который читает модель.
6. `dev:audit --check=mcp` (и `make check`) проверяют объявления: обработчик,
   описание, схема, право, подключённость модуля.

Схема аргументов — упрощённый JSON Schema: `type`, `properties`, `required`,
`enum`, `default`, `minimum` / `maximum`. Сервер сам приводит типы
(LLM часто присылает `"10"` вместо `10`) и сообщает о недостающих
обязательных аргументах.

## Схема данных

| Таблица | Назначение |
|---|---|
| `erp_804_mcp_keys` | ключи агентов: `name`, `token_hash` (SHA-256), `token_prefix`, `scopes TEXT[]`, `read_only`, `enabled`, `expires_at`, `calls_count`, `last_used_at`, `created_by` |
| `erp_804_mcp_calls` | журнал вызовов: `key_id`, `key_name`, `tool_name`, `arguments JSONB`, `status`, `mutating`, `result JSONB`, `error`, `reason`, `duration_ms`, `approved_by/at`, `rejection_reason`, `idempotency_key`, `ip` |

Статусы вызова: `pending` (выполняется), `ok`, `error`, `awaiting_approval`,
`approved`, `rejected`. Уникальный индекс по `idempotency_key` (частичный) —
защита от повторного выполнения.

## Службы

| Класс | Ответственность |
|---|---|
| `Service_Erp804_Keys` | выдача/проверка токенов, права и их разбор, CRUD ключей, журнал erp119 |
| `Service_Erp804_Registry` | поиск `mcp.php` по подключённым модулям, проверка объявлений, приведение аргументов к схеме, вызов обработчика, контекст вызова |
| `Service_Erp804_Calls` | старт/финиш вызова, идемпотентность, ожидание подтверждения, одобрение и отклонение, поиск и статистика, журнал erp119 |
| `Service_Erp804_Server` | протокол MCP: JSON-RPC, `tools/list`, `tools/call`, пакеты, коды ошибок, парковка опасных вызовов |
| `Service_Erp804_Cast` | приведение типов из PostgreSQL (`t`/`f` → bool) |

Пошаговая настройка remote HTTP/stdio клиента и безопасного read-only ключа
описана в `docs/SIMPLE_ADVANCED_MODES_AND_AGENT_TESTING.md`. Готовые prompts

## Тесты

```bash
bin/test --filter=Erp804
```

Тесты покрывают реестр и объявления модулей, discovery-поиск и прокси-вызов,
выпуск и проверку ключей, отзыв и срок действия, видимость по правам и признаку
«только чтение», JSON-RPC (initialize, ping, batch, неизвестный метод),
запреты по правам, идемпотентный повтор, парковка опасного вызова, одобрение
и отклонение, статистика, журнал действий. Тестовые ключи называются
`ТЕСТ-804-*` и удаляются в `tearDown`.
