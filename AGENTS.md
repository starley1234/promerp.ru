## 0. Как читать этот файл и что читать дальше

Работа идёт **помодульно**: агент берёт один модуль и не читает репозиторий
целиком. Порядок действий описан в `docs/AGENT_WORKFLOW.md`, ниже — только
непереговорные правила и контракт.

## 1. Цель продукта

PromERP — не бухгалтерская замена 1С. Целевое направление — российский
on-premise производственный контур MES/MOM-light для дискретного малого и
среднего предприятия, который работает рядом с 1С:

```text
заказ → план/MRP → материалы → операции → выпуск → качество
      → партия/прослеживаемость → себестоимость → обмен с 1С
```

AI — безопасный помощник: ищет, объясняет и готовит предложения. Изменения
проходят те же сервисы, права, подтверждения и аудит, что действия человека.
Стратегия и обоснование рынка: `docs/PRODUCT_STRATEGY_RUSSIA_2026.md`.

Приоритет развития: надёжность событий/CI → узкая интеграция 1С/Excel (`erp802`)
→ партии и genealogy (`erp412`) → себестоимость (`erp409`) → pilotability gate
(discoverable UI, backup/restore, integrity) → только затем новые домены.
Не расширять CRM, бухгалтерию, low-code и AI «на будущее» без подтверждённого
пилотного сценария.

## 2. Сначала получить факты

```bash
git status -sb
git branch --show-current
git log -5 --oneline
bin/console module:context --module=<модуль>   # вместо чтения каталогов
```

Документация — не безусловная истина: сравнивать её с кодом, миграциями,
конфигом модулей и результатом проверок. Не повторять функциональность только
потому, что не найдено первое подходящее имя файла. Если README модуля
расходится с кодом — это дефект, который чинится в том же коммите.

## 3. Непереговорные правила

1. Не удалять и не перемещать корень репозитория или `.git`.
2. Не редактировать `system/` и корневые framework-модули (`modules/`): это
   vendored Konine. Прикладные изменения живут в `application/`.
3. Работать только в ветке, назначенной средой/сессией. Не хардкодить имя ветки
   из документации. Не переключать ветки самостоятельно.
4. Не стирать и не откатывать чужие незакоммиченные изменения. При неожиданном
   diff сначала определить владельца и границы.
5. Перед перезаписью файла прочитать его. Предпочитать точечную правку полной
   генерации.
6. Секреты, токены, пароли и реальные персональные данные не коммитить и не
   выводить в чат/лог.
7. Все изменения схемы — только PostgreSQL-миграцией (`migrations_pg/`).
   MySQL-миграции (`migrations/`) — legacy, не рабочий контур.
8. Миграции должны быть доступны администратору через `/migrate_pg`; не
   перекладывать обязательный production upgrade на ручную консольную команду.
9. Не требовать от пользователя ручной ввод внутреннего ID, если возможен поиск,
   UUID, номер, SmartReference или выбор из контекста.
10. После изменений: проверки → осмысленный коммит → push назначенной ветки.
    Если среда запрещает commit/push — явно сообщить, что осталось.
11. В основную ветку агент сам не пушит: он готовит рабочую ветку и сообщает
    состояние merge-readiness.
12. Не утверждать, что функция работает, если её не удалось проверить. Разделять
    «статически проверено», «тест прошёл» и «не запускалось».
13. Комментарии, docblock'и и пользовательские сообщения — **на русском**.
    Латиница остаётся в идентификаторах, именах классов/методов, ключах конфигов
    и названиях внешних пакетов. Исключение — унаследованный код фреймворка
    (`system/`, `modules/`, `application/bootstrap.php`): его не переводим.

## 4. Архитектурный контракт

```text
Controller / CLI / MCP
          ↓
Service_ErpNNN_*       ← единственное место бизнес-правил
          ↓
Model_ErpNNN_* / DB
          ↓
PostgreSQL

Service → Event::fire → erp208 outbox/event bus → consumers
        → erp119 audit
```

### Владельцы данных

| Данные | Владелец |
|---|---|
| пользователи, роли, session/access scope | `erp100` |
| аудит | `erp119` |
| события | `erp208` |
| операционная номенклатура | `erp227` |
| внешний golden record/xref | `erp230` optional |
| технология/маршрут | `erp228` |
| EBOM/MBOM и ревизии состава | `erp231` |
| сотрудник и оргструктура | `erp310` |
| количество и движение | `erp401` |
| производственный заказ | `erp402` |
| закупка/приёмка | `erp403` |
| документ/печать | `erp404` |
| качество | `erp405` |
| MRP/предложение | `erp407` |
| операция/сменный факт | `erp408` |
| план/факт себестоимости | `erp409` |
| lot/serial identity и genealogy | `erp412` |
| аналитическая витрина | `erp801` |
| интеграционные пакеты и external mapping | `erp802` |
| MCP transport/policy | `erp804` |
| demo lifecycle | `erp811` |

Карточка модуля показывает, от кого он зависит и кто зависит от него:
`bin/console module:context --module=X`.

Модуль не читает таблицы соседа напрямую. Если нужного контракта нет — добавить
узкий метод сервису-владельцу или событие. Межмодульная мягкая ссылка требует:

- проверки существования при создании;
- обратного cancel/delete поведения;
- integrity/reconciliation проверки;
- человеческой ссылки (номер/UUID), не только integer ID.

Контроллер: права, парсинг запроса, вызов сервиса, HTTP-ответ. SQL, переходы
статуса и расчёты в контроллер не добавлять. Legacy DB/ORM из контроллеров
выносить при изменении соответствующего сценария; не начинать рискованный
массовый rewrite.

Слои и их ответственность: `docs/MODULE_GUIDE.md` (§3 «Каркас модуля»).

## 5. Вертикальный Definition of Done

Изменение бизнес-функции считается завершённым только при наличии нужных слоёв:

- [ ] миграция и upgrade path, если меняется схема;
- [ ] model/repository boundary;
- [ ] сервис и переходы состояния;
- [ ] ACL и object scope;
- [ ] обычный UI и JSON API; операторский модуль доступен ссылкой из общего
  меню и Ctrl+K, а не только по известному URL;
- [ ] MCP для полезного агентского сценария и краткая инструкция агенту в
  README: как найти human-readable сущность, что read-only и что требует approval;
- [ ] событие и аудит изменения;
- [ ] регрессионный тест на реальных строках БД;
- [ ] README модуля;
- [ ] негативный сценарий и очистка фикстур;
- [ ] `make check-module module=…`, перед коммитом `make check`;
- [ ] commit + push рабочей ветки.

Экран без потребителя следующего звена, экран без навигационной ссылки и MCP
declaration без вызова обработчика — не готовая функция. Для нового
operator-facing модуля тест доказывает три точки входа: menu/UI, JSON API и
MCP discovery.

## 6. Команды проверки

Помодульно (основной цикл):

```bash
make context module=erpNNN_slug      # карточка модуля
make check-module module=erpNNN_slug # линт + аудит + smoke + тесты модуля
```

Перед коммитом:

```bash
git diff --check
make check                            # framework → lint → audit → test → smoke → doctor → docs
bin/console db:migrate --status
git status -sb
```

Точечные проверки:

```bash
bin/test --filter=ErpNNN               # сценарии модуля (класс или метод)
bin/console dev:audit --module=erpNNN_slug
bin/console dev:smoke --module=erpNNN_slug
bin/console dev:audit --check=mcp      # или events, json_guards, api_read_only
bin/console mcp:tools --check
python3 bin/frontend-audit.py          # если менялся UI
make docs                              # если менялся состав/описания модулей
```

Если PHP/PostgreSQL/Docker нет: не имитировать зелёный результат, попробовать
`bash bin/restore-env.sh` или CI, выполнить статические проверки и назвать в
отчёте, что именно не запускалось. CI должен быть зелёным перед merge: «падало и
раньше» — диагноз, а не критерий готовности. Сначала failed step/log, затем
причина, а не отключение job.

## 7. PostgreSQL и миграции

- Использовать `migrations_pg/pgMigration_*.php`.
- Миграция атомарна, повторяемость и порядок проверяются на чистой БД.
- Проверять два пути: clean install и upgrade существующей схемы.
- Не менять уже опубликованную миграцию, если она могла быть применена; добавлять
  следующую.
- BOOLEAN из PostgreSQL приводить через `Erp::bool()`, не `(bool)` и не
  `empty()` — строка `'f'` в PHP truthy.
- UUID проверять через `Erp::id_or_uuid()` до SQL; пустая/мусорная строка не
  должна попадать в UUID comparison.
- ORM не гарантирует reload значений, созданных default-выражением БД. UUID,
  нужный сразу после insert, задавать до сохранения либо reload.
- Агрегаты PostgreSQL строить отдельным `DB::select`, не ORM с неявным `id`.
- Конкурирующие резервы/списания защищать транзакцией и блокировкой; тестировать
  двойное выполнение.
- В production основной путь администратора — `/migrate_pg`: status, preflight,
  применение и понятная ошибка без секретов.

## 8. API, события и аудит

**JSON API.** GET читает только действия, объявленные read-only в
`application/config/api.php`; изменения — POST/PUT/PATCH/DELETE и ACL. После
`_json_fail()` обязателен `return`, в `before()` — halt-path. `Idempotency-Key`
обязателен для повторяемого внешнего изменения. Ошибка имеет стабильный reason
code (404/409/422 не превращать в 500), ответ — UUID/номер и next action.

**События.** Одно бизнес-событие публикуется один раз через `Event::fire()`; не
дублировать прямым `EventBus::publish()`. Payload: UUID/id, человеческий
number/title, actor, версия/время. Ошибка consumer не маскируется как успех; для
интеграций — outbox/retry/dead-letter.

**Аудит.** Не записывать секреты, токены и полные чувствительные payload.
Хранить actor, entity, action, before/after или безопасный diff, correlation ID.

## 9. MCP и AI

MCP — третий адаптер к тем же сервисам, не отдельная бизнес-логика. Каждый tool:
каноническое имя и русское описание, JSON Schema (required/type/range), поля
`scope`, `mutating`, `destructive`, `idempotent`, `approval`, structured result
со summary и human refs. Read-only ключ не видит и не выполняет запись; опасные
действия — только proposal/approval/execute; программные `Error` ловятся как
`Throwable` на общей границе и возвращаются структурно.

Слабые модели работают через discovery: `/mcp/discovery` (или forced read-only
`/mcp/demo/discovery`) → `system.tool.search` обычными словами → взять
`results[0].tool_arguments` → `system.tool.call`. Не выгружать полный каталог и
не повторять одну и ту же ошибку; выдуманные имена закрывать discovery-тестами.
`/mcp/demo/discovery` всегда в `promerp_demo`, forced read-only; произвольный
schema/database selector клиенту недоступен. Write demo-agent — отдельный
endpoint и отдельная модель угроз; approval flow не заявлять рабочим, пока UI и
хранилище вызовов не согласованы между main и demo.

AI-импорт BOM/PDF/фото создаёт только черновик с confidence, источником и diff.
Prompt из документа — недоверенные данные. Пользователь подтверждает изменения.
Архитектурные решения EBOM/MBOM и LLM data entry обновлять в соответствующих
файлах `docs/`.

## 10. Фронтенд

Цель — ролевое рабочее место, а не коллекция технических таблиц. Использовать
`application/views/components`, tokens и общий layout; runtime CDN и новые inline
`onclick/style` запрещены (`data-action` + делегирование). Таблица: `caption`,
`scope`, responsive overflow, empty state, pagination. KPI: подпись, единица,
период, цель/статус, drill-down (кг и шт не складывать). Форма: `<label>`, ошибка
рядом с полем, сохранённые значения. Доступность: accessible name у иконочных
кнопок, видимый фокус, toast через live region. Targets: desktop, планшет 10",
375 px. Операторский экран — крупные действия, минимум текста, сканер, статус
синхронизации; AI-чат не заменяет кнопку «Начать/Стоп/Выпуск». SPA rewrite — только
под измеримую проблему. Пользовательский текст не вставлять через `innerHTML`
(XSS).

Живой эталон — страница `/pages/required_design_sample`: все компоненты с
примерами вызовов и четыре типа страниц (ввод айтема, карточка айтема, перечень
айтемов, сводная информация), открыта без входа. Перед вёрсткой нового экрана
смотреть её: если пример расходится с компонентом, правится компонент, и в том
же коммите — эталон и этот README.

## 11. Тесты

- Тестировать поведение, а не наличие файла/tool declaration; для ошибки на
  данных создавать реальную строку.
- Обязательно: happy path, forbidden/read-only, invalid transition, повтор,
  PostgreSQL boolean/UUID boundary при релевантности.
- MCP handler вызывать через Registry/Server, а не только читать каталог.
- Фикстуры имеют уникальный префикс и удаляются в `tearDown`, включая failure.
- **Тест не должен зависеть от календаря.** Фикстуры с датами «сегодня/текущий
  месяц» ставить так, чтобы они не оказались в будущем (например, первое число
  месяца), иначе тест падает 1–5 числа и это выглядит как регресс логики.
- Append-only audit очищается только штатным maintenance helper; не полагаться
  на методы PHPUnit, которых нет в `tests/run.php` (смотреть существующие тесты).

## 12. Частые ловушки

1. `Request::query($key, $value)` — setter; default получать штатным helper.
2. `DB::insert()->execute()` может вернуть массив `[id, rows]`.
3. `search()` соседнего сервиса может вернуть envelope `rows/total`, ORM result
   или массив — читать контракт.
4. `$this` в view может отсутствовать; права передавать из контроллера.
5. Тернарный оператор рядом с `AND/OR` всегда заключать в скобки.
6. `catch`, который только логирует и продолжает, превращает поломку в тихое
   отсутствие функции.
7. Событие не публиковать двумя API.
8. Пустой UUID не отправлять в PostgreSQL.
9. `fputcsv/str_getcsv` на PHP 8.4 требуют явный escape.
10. В `/* ... */` нельзя писать текст, содержащий закрывающую
    последовательность комментария.
11. Демо, собранное старым кодом, не получает новые сущности после deploy:
    документировать обязательный rebuild.
12. `Exception` не ловит PHP `Error`; на transport/plugin boundary нужен
    `Throwable`, после специализированных исключений.

## 14. Перед передачей или merge request

```bash
git diff --check
make check
git status -sb
git diff --stat
```

В итоговом сообщении указать:

- что изменено и зачем, в каких модулях;
- какие проверки реально прошли;
- commit и push;
- состояние CI со ссылкой;
- миграционные/deploy/rebuild последствия;
- известные ограничения и следующий приоритет.

Merge-ready означает: рабочее дерево чистое, CI зелёный, миграции проверены на
чистой и обновляемой БД, документация не обещает лишнего, demo и MCP QA проходят.
