# EBOM и MBOM в PromERP: целевая архитектура

Дата решения: 2026-09-17. Обновлено: 2026-09-18.

Статус: **первый доменный срез реализован в `erp231_product_structure`**.
Работают схема ревизий и строк, lifecycle, проверка циклов, неизменяемость
approved, копирование EBOM→MBOM с mapping и MCP read/draft/approval boundary.
До production-ready остаются UI workbench, импорт staging, ECR/ECO workflow и
неизменяемый snapshot производственного заказа; подробная граница приведена в
README модуля. Поэтому утверждение «полная поддержка EBOM/MBOM» пока запрещено.

## 1. Почему одной таблицы `object_links` недостаточно

**EBOM** отвечает на вопрос «из чего изделие сконструировано», **MBOM** — «из
чего и как мы реально выпускаем изделие на конкретной площадке». Это разные
версионируемые документы. Универсальные связи erp227 и erp230 умеют показать
дерево, но не обеспечивают ревизию, утверждение, применяемость, замену,
сопоставление EBOM→MBOM и неизменяемый снимок для производственного заказа.

Текущее состояние:

* erp227 хранит оперативную номенклатуру и нетипизированные связи `bom`;
* optional erp230 хранит внешние графы `ebom`/`mbom`, но рабочие модули его не
  потребляют;
* erp228 описывает технологические операции, а материалы частично извлекаются
  из `structured_data` LLM-документа;
* erp402 копирует потребность в строки заказа, но не знает ревизию BOM.

Считать любой из этих механизмов полноценной системой EBOM/MBOM нельзя.

## 2. Владелец данных

Предлагается отдельный модуль **`erp231_product_structure`**:

* владеет утверждёнными ревизиями EBOM и MBOM;
* ссылается на номенклатуру erp227 только через сервисный контракт;
* принимает внешний EBOM из erp230/PLM как импортированный draft, но не зависит
  от доступности MDM;
* отдаёт утверждённый MBOM в erp228 и erp402;
* не хранит складские остатки, операции цеха и себестоимость.

`erp230_mdm.object_links` остаётся staging/golden-record внешнего источника, а не
операционной спецификацией производства.

## 3. Модель

### `erp_231_structures`

`id`, `uuid`, `product_item_id`, `kind` (`ebom|mbom|service`), `revision`,
`status` (`draft|review|approved|obsolete`), `site_id`, `source_system`,
`source_revision`, `effective_from/to`, `approved_by/at`, `created_at`.

Уникальность: изделие + вид + ревизия + площадка. Утверждённая ревизия
неизменяема: исправление создаёт новую.

### `erp_231_lines`

`structure_id`, `line_no`, `parent_line_id`, `component_item_id`, `qty`, `uom`,
`scrap_pct`, `supply_type` (`make|buy|phantom|consumable`), `operation_no`,
`effectivity`, `alternatives`, `note`.

Для MBOM дополнительно допустимы технологические материалы, упаковка, оснастка
и phantom-узлы. Операция — мягкая ссылка на шаг erp228, а не внешний ключ.

### `erp_231_mappings`

Сопоставление строки EBOM со строками MBOM: `ebom_line_id`, `mbom_line_id`,
`mapping_kind` (`same|split|merge|excluded|added`), причина и автор решения.
Именно эта таблица позволяет ответить, куда исчез конструкторский компонент.

### `erp_231_changes`

ECR/ECO: основание изменения, исходная и целевая ревизия, статус согласования,
влияние на открытые заказы и остатки.

## 4. Жизненный цикл

1. Конструктор создаёт или импортирует EBOM draft.
2. Валидация проверяет циклы, единицы, дубли, отсутствующие компоненты.
3. Уполномоченный сотрудник утверждает ревизию EBOM.
4. Технолог создаёт MBOM из утверждённого EBOM.
5. Правила и LLM предлагают преобразования; технолог принимает diff построчно.
6. MBOM связывается с версией техкарты erp228 и утверждается.
7. erp402 при создании заказа сохраняет **snapshot id/revision и строки**.
8. Новая ревизия не меняет уже выпущенный заказ автоматически; система только
   показывает impact и предлагает перепланирование.

## 5. Где полезен LLM

LLM не утверждает BOM и не подменяет правила. Он может:

* извлечь позиции из PDF/Excel/чертежа;
* сопоставить обозначение поставщика с erp227 и вернуть top-3 кандидата;
* предложить MBOM-преобразование: phantom, split/merge, операция, упаковка;
* объяснить разницу ревизий и выделить влияние;
* найти подозрительную норму, единицу или пропущенную позицию.

Каждое предложение хранит source, confidence и explanation. Применение — только
после детерминированной проверки и подтверждения человека. Через MCP чтение и
подготовка draft разрешены агенту; approve/obsolete требуют approval.

## 6. Интерфейс

* дерево + плоская таблица должны быть двумя видами одной ревизии;
* вместо ввода `item_id` — smart reference: поиск кода/названия, остаток,
  производитель, тип и единица в подсказке;
* импорт открывает staging-таблицу: исходное значение, найденный объект,
  confidence, ошибка, действие «принять/заменить/создать»;
* сравнение ревизий — added/removed/changed и фильтр только проблем;
* отдельный экран EBOM→MBOM mapping с непривязанными строками;
* массовые операции и клавиатурная навигация обязательны для спецификаций на
  сотни строк.

## 7. Definition of Done первого среза erp231

Версионируемые EBOM/MBOM, защита от циклов, smart reference номенклатуры,
копирование EBOM→MBOM, mapping, approve с правами, snapshot для erp402, JSON API,
MCP read/draft tools и сквозной тест «утверждённый MBOM → заказ → неизменяемый
состав». До этого маркировку «EBOM/MBOM поддерживается» в продукте не использовать.
