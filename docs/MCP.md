# Агентский доступ: MCP, API всех модулей и внешние воркеры

Документ отвечает на три вопроса заказчика: как мы закладываем управление
производством через LLM-агентов, что значит «у всех модулей должен быть API»
и где в этой картине место внешним Python-воркерам.

Актуально на 2026-09-15. Модуль: `application/modules/erp804_mcp`
(паспорт — `application/modules/erp804_mcp/README.md`).

---

## 1. Почему MCP, а не «свой HTTP API»

MCP (Model Context Protocol) — открытый протокол, которым клиенты
(Claude Desktop, Cursor, Continue, собственные агенты) спрашивают у сервера
список инструментов и вызывают их. Даёт три вещи, которых нет у обычного REST:

1. **Самоописание.** Агент получает инструменты с описанием и JSON-схемой
   аргументов — не нужно писать интеграцию под каждый экран.
2. **Единый транспорт.** Тот же сервер работает по HTTP (сетевые агенты) и по
   stdio (локальные клиенты вроде Claude Desktop) — код один.
3. **Готовые точки контроля.** Права (`scope`), признак изменения данных,
   подтверждение человеком, идемпотентность и журнал вызовов —
   это стандартные места приложения, а не изобретение под каждого агента.

Мы не отказываемся от JSON API модулей: MCP — витрина **над** сервисами,
а не второй набор бизнес-логики. И то и другое вызывает одни и те же службы.

## 2. Как это устроено

```
LLM-агент / внешний воркер
      │  JSON-RPC 2.0 (MCP 2025-06-18)
      ▼
POST /mcp  ──▶  Service_Erp804_Server   проверка ключа, метод, права
                     │
                     ├─ Registry: какие инструменты объявлены (mcp.php модулей)
                     ├─ Calls:    журнал вызова, идемпотентность, подтверждения
                     └─▶ handler из mcp.php  ──▶  Service_ErpNNN_*  ──▶  БД
                                                            │
                                                            └─▶ журнал erp119, шина erp208
```

* **Инструменты объявляют сами модули** — файлом `mcp.php` в корне модуля.
  Ядро (`erp804_mcp`) не знает предметной области: подключили модуль — его
  инструменты появились у агентов, выключили — исчезли.
* **Ключ агента** — отдельная учётная запись (`erp_804_mcp_keys`): права,
  «только чтение», срок жизни, счётчик вызовов. Токен `mcp_…` показывается
  один раз, в базе — только SHA-256.
* **Права — те же имена, что в `acl.php`** (`erp402_production.manage`,
  `erp228.view`, …). Поддержаны префиксы `erp402_production.*` и `*`.
* **Опасные операции помечены `approval`** (`production.order.complete`,
  `production.order.cancel`): вызов останавливается в статусе
  `awaiting_approval`, человек подтверждает его в `/mcp/calls`, агент
  спрашивает статус инструментом `system.call.status`. Так «управление
  производством через агентов» не теряет человека на выпуске и отмене.
* **Идемпотентность**: повтор с тем же `idempotency_key` не выполняется
  второй раз. Это обязательное условие для агентов: обрыв связи в цикле
  «подумал → вызвал → прочитал ответ» — обычное дело.
* **Журнал**: каждый вызов в `erp_804_mcp_calls` (кто, что, аргументы,
  статус, результат, миллисекунды), изменяющие — ещё и в журнал действий
  erp119 (`module = erp804`), то есть агентская активность видна там же, где
  действия людей.

### Подсказки агенту (annotations)

Каждый инструмент отдаёт не только схему аргументов, но и признаки по
спецификации MCP: `readOnlyHint`, `destructiveHint`, `idempotentHint`.
Умолчания шины: чтение — безопасно, изменение — «разрушающее», повтор
допустим. Модуль может их уточнить, и цех это делает:

| Инструмент | destructive | idempotent | Почему |
|---|---|---|---|
| `shopfloor.operation.output` | FALSE | **FALSE** | запись выработки: повтор удвоит факт — агент не должен повторять вызов вслепую |
| `shopfloor.operation.start` / `pause` / `resume` / `downtime_*` | FALSE | TRUE | состояние меняется обратимо, повтор не добавит эффекта |
| `shopfloor.operation.finish` / `cancel` / `delete` | TRUE | TRUE | закрывают или снимают операцию |
| `production.order.create`, `order.item_add`, `fill_from_tech_card` | FALSE | **FALSE** | создают данные: повтор создаст второй заказ или вторую строку состава |

Правило для новых инструментов: если повтор вызова добавляет данные (количество,
строку, документ) — ставьте `'idempotent' => FALSE`. Аналитика это соблюдает:
`analytics.save_snapshot` не идемпотентен (повтор создаёт второй снимок), а
`analytics.save_settings` — идемпотентен (повтор с теми же значениями ничего не
меняет). Это дешевле, чем разбирать
удвоенный факт в цехе.

### Адреса

| Адрес | Кому | Что |
|---|---|---|
| `POST /mcp` | агентам | JSON-RPC 2.0 по протоколу MCP (пакеты, уведомления) |
| `GET /mcp` | агентам и мониторингу | сведения о сервере: сколько инструментов и какие модули их объявили |
| `/mcp/console` | человеку | обзор: статистика, ожидающие подтверждения, последние вызовы |
| `/mcp/tools` | человеку | каталог инструментов с правами и схемами аргументов |
| `/mcp/calls` | человеку | журнал вызовов, кнопки «Подтвердить» и «Отклонить» |
| `/mcp/keys` | человеку | выдача, отзыв и включение ключей агентов |
| `/mcp/api/*` | интеграциям | JSON API управления (info, tools, calls, call, keys, approve, reject) |
| `bin/console mcp:serve` | локальным клиентам | тот же сервер по stdio (Claude Desktop, Cursor) |

`/mcp` занят протоколом: в браузере открывайте `/mcp/console`.

### Как агент это видит (пример)

```bash
bin/console mcp:key --name="Агент мастера" --scopes=erp402_production.view,erp402_production.plan

curl -s http://127.0.0.1:8080/mcp \
  -H "Authorization: Bearer mcp_…" -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{
        "name":"production.materials.shortages",
        "arguments":{"limit":10}}}'
```

Ответ: `content` (текст + JSON, удобно и модели, и человеку),
`structuredContent` (машинно-читаемо) и `call_id` — по нему видно, что
произошло дальше.

## 3. «API у каждого модуля»

Требование заказчика выполнено в двух форматах, и это осознанное решение:

| Формат | Кому | Что даёт |
|---|---|---|
| `classes/Controller/ErpNNN/Api.php` | браузеру, интеграциям, 1С, веб-формам | JSON-конверт `{"success":true,"data":…}` / `{"success":false,"error":{…}}`, права через `can()`, коды 401/403/404 |
| `<модуль>/mcp.php` | LLM-агентам и внешним воркерам | MCP-инструменты с описанием, схемой аргументов и правом |

Правило для новых модулей: **если у модуля есть бизнес-сущности, у него
должна быть хотя бы одна из этих точек входа.** За этим следит статический
аудит — `bin/console dev:audit --check=mcp` выдаёт предупреждение
«у подключённого модуля … нет ни JSON API, ни инструментов MCP».

Текущее состояние (проверка на 2026-09-16): **покрытие полное — 22 модуля из
22**, исключений больше нет. Каталог инструментов — 135 у 9 модулей
(`erp403_procurement` — 29, `erp402_production` — 19, `erp408_shopfloor` — 19,
`erp405_quality` — 19, `erp801_analytics` — 15, `erp407_planning` — 14,
`erp404_documents` — 13, `erp119_audit` — 3, `erp804_mcp` — 4; изменяющих 69,
под подтверждением человека 20). Закрыты и инфраструктурные модули, которые раньше
были исключением:

| Модуль | Что отдаёт | Зачем машине |
|---|---|---|
| `erp100_base` | `/erp100/api/me`, `/users`, `/user/<id>`, `/roles` | кто я, какие у меня роли и права (тот же список, что видит интерфейс); список пользователей для админских панелей и интеграций |
| `erp111_migrations_postgresql` | `/migrate_pg/api/status`, `/inventory`, `/orphans` | состояние схемы для развёртывания и мониторинга: что применено, что ждёт, есть ли расхождения |
| `erp118_links` | `/erp118_links/api/links`, `/menu`, `/groups`, `/check`, `POST /toggle` | личные закладки и меню для мобильного клиента; владелец берётся из сессии, `user_id` из запроса не принимается |

Правило проверяется тестом `ModuleConventionsTest::test_api_modules_have_entry_points`
и статическим аудитом `dev:audit --check=mcp` — оба падают, если у erp-модуля нет
ни `Controller/*/Api.php`, ни `mcp.php`.

### Проверено вживую (S2)

Сценарий «агент управляет цехом» пройден на dev-стенде:

1. ключ `--scopes=erp408.view,erp408.terminal,erp408.manage`;
2. `shopfloor.queue` — агент нашёл заказ без маршрута;
3. `shopfloor.route.plan` — вызов **запаркован** (`awaiting_approval`, вызов #148);
4. мастер подтвердил в `/mcp/console` → сервер выполнил вызов и создал операцию;
5. `shopfloor.operation.start` → `downtime_start` (нет материала) →
   `downtime_stop` → `output` (4 годных, 1 брак) — агент вёл смену;
6. `shopfloor.operation.finish` — снова подтверждение человека (вызов #154),
   после подтверждения операция закрыта: годных 9, брак 1, прогресс 90 %;
7. в журнале отметок 6 записей (`start`, `downtime_start`, `downtime_end`,
   два `output`, `finish`), в шине — `erp408.operation.completed`, в журнале
   аудита — запись по заказу «Цех: операция 10 … операций закрыто 1 из 1».

Негативные проверки там же: вызов без права отвечает `-32003 forbidden`,
вызов без ключа — `-32001 unauthorized`, а анонимный POST в `/shopfloor/api/*`
теперь отвечает 401 и **не доходит до данных** (см. ниже).

## 4. Внешние воркеры на Python: позиция

Коротко: **да, но как исполнители и вычислители, а не как второй мозг
системы.** Правило, которое нельзя нарушать: единственный владелец бизнес-правил
и данных — модуль PHP; воркер получает работу через API/MCP и возвращает
результат тоже через API. Прямая запись в таблицы `erp_*` из Python
запрещена — иначе мы теряем транзакции, права, журнал и события, то есть
ровно то, ради чего система существует.

### Где Python-воркер уместен

| Задача | Почему Python | Как стыкуем |
|---|---|---|
| Тяжёлые расчёты: оптимизация расписания, раскрой, планирование загрузки | зрелые библиотеки (OR-Tools, PuLP, pandas) | воркер берёт данные инструментами `production.*`/`planning.*`, возвращает предложение — запись делает PHP-модуль |
| ML/CV: распознавание документов, дефектов, контроль по фото | экосистема ML | загрузка файла через `erp212`, результат — `quality.inspection.record` (инструмент erp405 в будущем) |
| Импорт/экспорт и интеграции (1С, Excel, EDI) | готовые парсеры | ключ с правом `erp802_integration.*`, идемпотентные вызовы |
| Долгие пакетные задачи (пересчёты, миграции данных, отчёты) | параллелизм, очереди | воркер вызывает инструменты и опрашивает статус; для длинных задач — очередь/вебхуки (`erp802_integration`) |
| Локальные LLM/эмбеддинги (RAG по документации цеха) | своя модель, приватность | результат — текст/подсказка, в систему пишет человек |

### Где Python-воркер вреден

* **Бизнес-переходы** («зарезервировать материал», «выпустить продукцию»):
  это транзакции сервисов с проверками и журналом — пусть остаётся в PHP.
* **Прямые SQL-записи** в таблицы модулей: обходят права, валидацию, события
  и журнал; при изменении схемы воркер молча ломается.
* **Свои копии справочников**: номенклатура (`erp227`), контрагенты
  (`erp301`), техкарты (`erp228`) читаются через API, а не дублируются в
  локальной БД воркера.

### Идемпотентность JSON API (то же правило, что в MCP)

У MCP-вызовов есть `idempotency_key` — повтор с тем же ключом не выполняется
дважды. С 2026-09-16 то же правило работает и для обычного JSON API **всех
модулей**, без правок в модулях: достаточно прислать заголовок

```
POST /procurement/api/request_create
Idempotency-Key: 3f1c9a7e-…
Content-Type: application/json
```

* повтор с тем же ключом и тем же телом отдаёт **сохранённый ответ** (заголовок
  `Idempotent-Replay: true`) — второй заявки, второго заказа, второй приёмки не
  появляется;
* тот же ключ с другим телом — `409 conflict` (ошибка клиента, а не второй
  документ);
* параллельный запрос с тем же ключом — `409 in_progress`;
* другой пользователь чужой ключ не «доиграет» — тоже `409 conflict`;
* без заголовка поведение прежнее: защита не включается, веб-формы не задеты.

Ключ живёт 24 часа (`Service_Erp100_Idempotency`, таблица
`erp_100_api_idempotency`), уборка — `bin/console idempotency:purge`
(поставить в cron). Вместо заголовка можно передать параметр
`idempotency_key` — для клиентов, которые не умеют заголовки.

**Правило для агента и воркера:** ключ обязателен для любой изменяющей
операции. Ретраи и обрывы связи — норма, а «вторая заявка на ту же
потребность» — уже нет.

### Что нужно достроить под воркеры

1. Вебхуки «работа появилась» и «работа выполнена» — модуль `erp802_integration`
   (сейчас агент/воркер сам опрашивает систему).
2. Отдельные ключи на каждый воркер (`--client=python-worker`, узкие права,
   срок жизни) — уже поддержано, нужна привычка так делать.
3. Лимиты вызовов (rate limit) и квоты по ключу — в бэклоге `erp804_mcp`.
4. Пример воркера и минимальный SDK (тонкая обёртка над JSON-RPC) —
   положим в `docs/` при первом реальном воркере.
