`arena/01a0a4ce-test-promerp-ru` (Konine 3.4.0, PHP 8.4.14, PostgreSQL 16.2),

> но не описывает текущий состав: упомянутые ниже `erp202_llm_bom_parser`,

### 2.2 Внутри включённых модулей

1. **Дублирующие лэйауты и «свои» шапки.** Часть модулей тащит собственный
   layout (`erp228/views/erp228/layout/main.php` — уже удалён как дубль).
   Остальные должны использовать общий шаблон и `set_title`/`set_menu`.
2. **Пустые и почти пустые файлы**: `erp227/classes/Controller/Erp227/Widget.php`
   (класс без действий), `erp230/views/erp230/objects/partials/compare.php`,
   пустые представления в выключенных `erp221`/`erp202`. Либо наполнить, либо удалить.
3. **Диагностические страницы** (`erp217_test`, `erp227_test`, `erp202_test`,
   `erp230_apitest`, `TestBD`, `TestRegistry`). Полезны при разработке, но это
   10 боевых маршрутов в продакшн-сборке. Правильно: держать их в отдельном
   модуле `dev_tools`, который не включается на боевом контуре.
4. **Мёртвые конфиги**: `config/` есть у выключенных модулей
   (`521_llm_validation_app`, `PostgreSQL_PDO`, `erp199_sqr`, `erp221_crm`,
   `erp229_mdm`) — они попадают в каскад и создают ложное ощущение настройки.
5. **Legacy-миграции MySQL** у выключенных модулей: после порта их нужно
   удалять вместе с модулем, иначе схема проекта описана в двух диалектах.
6. **12 записей baseline** в `application/audit-baseline.php` — это «принятые
   отклонения». Каждое из них должно либо закрыться, либо превратиться в задачу
   спринта (сейчас часть уже неактуальна — `erp228` разобран и запись удалена).

### 2.3 Что лишнее в процессах

* **`vendor/autoload.php` — заглушка**, composer-зависимости не установлены:
  половина «composer-ного» кода (`Dompdf`, `PhpSpreadsheet`, `Monolog`, …)
  фактически не используется. Решение: либо ставить зависимости на CI/сервере,
  либо вычистить импорты до нужного минимума.
* **PHPUnit в репозитории не установлен**, тесты идут своим раннером. Это
  оправдано (быстро, без сети), но стоит зафиксировать: либо мигрировать на
  PHPUnit там, где он есть, либо оставить один механизм (сейчас два: `phpunit.xml.dist`
  и `tests/run.php`).
* **Docker/CI не проверены на живом окружении** — заявлены в репозитории, но
  ни разу не запускались (нет сети/докера в песочнице). Пока это документация,
  а не инфраструктура; в roadmap нужно пометить как «не подтверждено».

* Нет проверки на «медленные» запросы (EXPLAIN/план) — при росте данных `LIKE '%term%'`
  и N+1 в старых модулях станут проблемой.
* Нет тестов на конкурентный доступ (параллельные списания/резервы) — только
  логика `SELECT … FOR UPDATE`, без прогона.
* Нет тестовой БД-фикстуры: тесты используют рабочую базу и убирают за собой;
  для CI нужен отдельный прогон на пустой БД (миграции + тесты).

## 4. Что углубить

### 4.1 Данные и модели

1. **Единый владелец номенклатуры.** Сейчас «объект» живёт в трёх местах:
   реестр `erp227`, мастер-данные `erp230`, ссылка `target_id` в техкарте.
   Нужен явный контракт: `erp227` — единственный источник объекта, `erp230` —
   его атрибуты/типы и версии, `erp228`/`erp401`/`erp403` ссылаются по id и
   читают только через сервис.
2. **Спецификация (BOM) как сущность,** а не поле. Без неё нельзя посчитать
   потребность в материалах ни для заказа, ни для закупки.
3. **Нормы расхода на операцию.** У операции техпроцесса уже есть время и
   стоимость; добавьте материалы (позиция, количество, отход) — это вход для
   `erp402`/`erp403` и для себестоимости.
4. **Ревизии изделия.** `target_id` должен указывать на конкретную ревизию,
   иначе техкарта «поедет» после изменения модели.
5. **Единый поиск.** Колонки `search_text` (в `erp301`, `erp228`) — обходной
   путь для локали `C`. Пора вынести это в общий сервис (нормализация + `pg_trgm`
   или `tsvector`), иначе каждый новый модуль будет копировать решение.

### 4.2 Код

1. **Довести конвенцию «контроллер → сервис»** в `erp230` (87 обращений),
   `erp222` (53), `erp218` (40), `erp217` (34), `erp227` (29) — помодульно, с
   тестами на перенесённую логику. Это же снимет главный риск при добавлении API.
2. ~~**Права: объявить все используемые.**~~ **Сделано**: права включённых
   модулей объявлены, проверка `dev:audit --check=acl` ловит новое необъявленное
   право. Дальше: права на объект (владелец, подразделение) и аудит доступа.
3. **События через outbox.** 152 публикации в файловый лог: при сбое подписчика
   событие теряется. Нужна таблица исходящих событий + обработчик Minion
   (гарантия доставки, ретраи, идемпотентность).
4. **Фоновые задачи для LLM.** Генерация техпроцесса должна уезжать в очередь:
   карта `pending` → задача → `processing` → `ready`. Заодно это даст повторные
   попытки и лимиты токенов на сутки (поле `limits.daily_token_limit` уже есть в конфиге).
5. **Единый модуль dev-инструментов.** Диагностические страницы, `dev:*` задачи и
   тестовые данные — в отдельный модуль, отключаемый на проде.

### 4.3 Производительность и надёжность

1. Индексы под реальные запросы (`search_text`, `(status, is_deleted)`,
   `(tech_card_id, is_actual)` — уже есть; дальше — под отчёты `erp801`).
2. Транзакции и `SELECT … FOR UPDATE` — не только в складе, но и в закупках/заказах.
3. Кеш справочников (склады, типы, единицы) — сейчас каждый запрос идёт в БД.
4. Метрики: длительность генерации, число ошибок по модулям, размер очереди.

## 5. К чему идём

### 5.1 Целевая картина

```
                   ┌───────────────────────── Интеллект (800–899) ─────────────────────────┐
                   │  аналитика, прогноз минимумов, ABC/XYZ, портал поставщика            │
                   └───────────────▲──────────────────────────────▲───────────────────────┘
                                   │                              │
   Справочники (100–299)           │        Операции (300–599)     │
   ─────────────────────           │        ──────────────────     │
   erp227 изделия и реестр  ───────┴──────► erp402 производственные заказы
   erp230 мастер-данные                   ► erp403 закупки ──► erp401 склад
   erp228 техпроцессы ────────────────────► erp401 расход материалов, резервы
   erp301 контрагенты ────────────────────► erp404 документы и печатные формы
   erp212 файлы, erp208 события, erp217 уведомления, erp119 аудит, erp218 модули
```

Поток «заказ → изготовление → выпуск»: заказ (`erp402`) берёт техпроцесс
(`erp228`), проверяет обеспеченность по складу (`erp401`), при нехватке
инициирует закупку (`erp403`), приход закрывает потребность, расход по
операциям списывает материалы, выпуск фиксирует готовую продукцию, `erp404`
печатает документы, `erp801` считает себестоимость и отклонения.

### 5.2 Принципы (то, что уже работает и должно остаться)

1. Один владелец данных: чужие таблицы читаются только через сервис модуля-владельца.
2. Данные меняются только через сервис: контроллер и задача — тонкие обёртки.
3. Значимое действие публикует событие (`erpNNN.*`) и пишет строку в журнал.
4. У документа одна актуальная версия — это гарантирует БД, а не только код.
5. Удаление мягкое; история остаётся.
6. Миграции идемпотентны, в одном диалекте (PostgreSQL), с `down()`.
7. Права проверяются на каждой «двери» (страница, действие, API, виджет).
8. Каждый модуль: README-паспорт, тесты бизнес-логики, права, события, маршруты.
9. Фреймворк не правим: доработки — в `application/` и модулях проекта.
10. Быстрая проверка: `make check` за секунды вместо ручного обхода.

## 6. Риски

| Риск | Следствие | Что делать |
| :--- | :--- | :--- |
| Логика в контроллерах старых модулей (`erp230`, `erp222`, `erp218`, `erp217`, `erp227`) | при добавлении API/интеграций правила дублируются и расходятся | помодульный вынос в сервисы с тестами (S1–S3, по 1 модулю на спринт) |
| 85 необъявленных прав | неявный доступ, опечатки в именах прав | объявить права + проверка в аудите (быстро, 1 день) |
| ~~Нет аудита изменений~~ | закрыто `erp119_audit`: журнал + перенос событий шины | осталось: аудит просмотра объектов «чужими» ролями |
| События только в логе | потерянные уведомления, «тихие» сбои интеграций | outbox + Minion-обработчик |
| LLM в HTTP-запросе | таймауты, невозможность повторов | очередь Minion, статус `pending` |
| Локаль кластера `C` | сортировка и поиск по кириллице ведут себя неочевидно | общий сервис нормализации поиска + документация решения |
| Composer-зависимости не установлены | код «есть», но не работает; ложные ожидания | либо ставить на сервере/CI, либо вычистить |
| Docker/CI не проверены | вера в непроверенную инфраструктуру | пометить как непроверенное, проверить на первом же окружении |
