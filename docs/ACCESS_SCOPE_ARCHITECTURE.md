# Архитектура ролей и областей доступа

Дата решения: 2026-09-17. Владелец учётных записей и авторизации — `erp100_base`;
`erp310_workforce` владеет сотрудником и иерархией подразделений.

## Два независимых вопроса

1. **Роль / permission** отвечает «что можно делать» (`erp401_wms.view_stock`,
   `erp408.terminal`). Источник — роли пользователя и `application/config/acl.php`.
2. **Область данных** отвечает «с какими объектами это можно делать»
   (подразделение 7, склад 2, рабочий центр 11).

Наличие объекта в области никогда не добавляет permission. Сначала проверяется
`can()`, затем `in_scope()`. Администратор имеет unrestricted policy, но решение
всё равно журналируется изменяющим сервисом.

## Модель

`users.access_policy`:

- `unrestricted` — прежнее поведение, ограничения по объектам нет;
- `restricted` — доступен только явно разрешённый scope; отсутствие строк означает
  deny-all, а не allow-all.

`erp_100_user_scopes` хранит `user_id`, `resource_type`, `resource_id`, период
действия и `include_descendants`. Первая версия поддерживает:

- `department` — ID из `erp310_workforce`; descendants вычисляются рекурсивно,
  только если модуль включён;
- `warehouse` — ID склада `erp401_wms`, точное совпадение;
- `work_center` — ID рабочего центра `erp408_shopfloor`, точное совпадение.

В таблице нет внешних ключей на таблицы других bounded contexts. Существование
объекта проверяет provider соответствующего модуля при записи scope; отключение
optional-модуля не должно ломать вход в систему.

## Контракт применения

```php
if (!$this->can('erp408.view') || !$this->in_scope('work_center', $center_id)) {
    throw new HTTP_Exception_403('Доступ запрещён');
}
```

Для списков нужен фильтр на уровне SQL/service, а не постфильтрация после LIMIT.
Постепенная миграция модулей начинается с erp310, затем erp401 и erp408. Пока
конкретный bounded context не подключил scope-filter, его permission продолжает
работать по старой модели; UI не должен обещать ограничение там, где consumer ещё
не внедрён.

## Блокировка и отзыв сессий

`users.status=blocked` запрещает password login, remember-cookie и force login.
`users.session_version` записывается в сессию при входе. Блокировка или действие
«завершить все сеансы» увеличивает версию и удаляет remember-токены: любая уже
открытая файловая сессия становится недействительной на следующем запросе.

Нельзя блокировать себя и нельзя удалить/заблокировать последнего активного
администратора. Изменение ролей, policy, scopes и блокировка идут через единый
сервис, публикуют события для erp119 и в MCP требуют approval.

## Безопасность AI/MCP

Агент может читать карточки доступа с `erp100.users`. Изменение ролей, блокировка,
отзыв сессий и scopes требуют `erp100.roles` и human approval. LLM предлагает
изменение как diff, но не получает отдельного пути обхода сервиса или проверок
последнего администратора.
