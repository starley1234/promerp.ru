# Простой и расширенный режимы PromERP. Тестирование LLM-агентом через MCP

Дата решения: 2026-09-17.

## 1. Короткий вывод

PromERP нужен не «облегчённый второй продукт», а один продукт с двумя уровнями раскрытия возможностей:

- **Простой режим** — мастер первоначальной настройки, безопасные типовые процессы, понятные названия, минимум обязательных полей и готовые профили предприятия.
- **Расширенный режим** — те же документы и сервисы, но с полным набором параметров, политик, интеграций, аналитики и технической диагностики.

Делать две независимые реализации нельзя: они быстро разойдутся по правилам и данным. Режим должен влиять на навигацию, количество видимых полей, подсказки и доступные варианты, но не создавать вторую модель данных или второй набор бизнес-сервисов.

Это **не сложно архитектурно**, потому что сервисный и модульный фундамент уже есть. Но это заметная продуктовая работа: нужно последовательно пройти основные пользовательские маршруты, выбрать хорошие значения по умолчанию и убрать требования вводить внутренние ID. Сложность оценивается как средняя для ядра и средне-высокая для всей системы из-за неодинаковой зрелости модулей.

## 2. Как должен выглядеть простой режим

### 2.1. Первый запуск

Вместо каталога всех модулей пользователь видит мастер из 6 шагов:

1. **О предприятии** — название, часовой пояс, валюта, тип производства.
2. **Структура** — одно подразделение и один склад уже предложены; дополнительные можно добавить позже.
3. **Что производим** — импорт Excel или создание первой позиции через умный поиск и подсказки.
4. **Как производим** — короткая техкарта из операций; нормы и центры можно уточнить позже.
5. **Команда** — приглашение сотрудников и выбор понятных ролей: руководитель, снабженец, мастер, кладовщик, ОТК.
6. **Пробный цикл** — система создаёт тестовый заказ и проводит пользователя по цепочке «потребность → склад/закупка → выпуск → качество».

После мастера главная страница показывает не модули, а задачи: «что требует внимания», «что сделать сегодня», «что задерживается».

### 2.2. Принципы интерфейса

- Показывать 5–8 действительно нужных полей, остальные помещать в блок **«Дополнительные настройки»**.
- Никогда не требовать внутренний ID: только `SmartReference`, поиск, недавние и рекомендованные значения.
- Предлагать значение по умолчанию и объяснять его одним предложением.
- Использовать язык процесса: «Запустить в производство», а не название перехода state machine.
- Ошибка должна отвечать на три вопроса: что случилось, что осталось безопасным, что нажать дальше.
- В каждом разделе иметь действие **«Показать пример»** — оно создаёт данные только в demo/test-контуре.
- Не показывать настройку, пока она не влияет на решение пользователя.

### 2.3. Готовые профили

На старте достаточно 3–4 рецептов:

- контрактное мелкосерийное производство;
- сборочное производство;
- производство под заказ;
- склад и закупки без производственного контура.

Профиль задаёт значения по умолчанию, включённые модули, стартовые роли, статусы и подсказки. Он не должен блокировать последующий переход к полным настройкам.

## 3. Расширенный режим

Расширенный режим открывает:

- детальные политики нумерации и переходов;
- несколько организаций, складов, подразделений и областей доступа;
- партии/серии, планирование мощностей, расширенный MRP;
- произвольные атрибуты и схемы номенклатуры;
- MCP, интеграции, webhooks, аудит и подтверждения;
- параметры аналитических витрин;
- технические страницы миграций и диагностики.

Переключение может быть глобальным профилем организации и локальным переключателем пользователя **«Показывать расширенные настройки»**. Права доступа остаются независимыми: скрытие элемента интерфейса не является проверкой безопасности.

## 4. Рекомендуемая реализация

### 4.1. Один backend, разные представления

Добавить платформенный `ExperienceProfile`:

```text
organization.profile = simple | advanced
user.ui_density       = guided | standard | expert
module.capabilities   = набор включённых функций
```

Контроллер вызывает тот же application service. UI-представление выбирает, какие поля раскрыть и какие defaults передать. Валидация, события, аудит и транзакции остаются общими.

### 4.2. Progressive disclosure вместо глобального if

Не следует рассыпать по проекту проверки `if simple`. Нужны декларативные метаданные формы:

```text
field.level = basic | advanced | expert
field.default_policy = organization | role | scenario
field.reference = smart selector
```

Один renderer сможет одинаково сворачивать дополнительные поля во всех модулях. Это также даст LLM структурированное описание формы и уменьшит расхождение UI/API/MCP.

### 4.3. Внедрение вертикальными маршрутами

Порядок:

1. Первичный мастер и профиль организации.
2. Номенклатура + техкарта.
3. Производственный заказ + склад.
4. Закупка + приёмка.
5. Цех + качество.
6. Аналитика и документы.
7. Администрирование, MCP и интеграции.

Каждый маршрут считается готовым, когда работает целиком: UI → сервис → данные → аудит → подсказка → тест. Не нужно сначала добавлять переключатель во все экраны, оставляя процессы незавершёнными.

### 4.4. Оценка сложности

- Платформенный профиль, мастер и общий механизм раскрытия полей: **средняя сложность**, ориентировочно 2–3 вертикальных спринта.
- Доведение главного производственного пути до простого режима: ещё 3–5 спринтов.
- Последовательная обработка всех старых экранов и неоднородных контроллеров: наиболее дорогая часть; её лучше выполнять по востребованности, а не большим переписыванием.

Основной риск не технический, а продуктовый: выбрать правильные defaults и определить, какие решения действительно можно безопасно принять за пользователя.

## 4.5. Реализовано: переключатель режима интерфейса (2026-10-02)

Первый срез платформенного механизма — личный режим пользователя
**«Простой / Профессиональный»**, по умолчанию простой.

- `Ui_Mode` (`application/classes/Ui/Mode.php`) — режим запроса; хранится в cookie
  `ui_mode` и в `users_settings.settings_json` (`Service_Erp100_UserSettings`).
- Выбирают режим **компоненты**, а не представления: `table` рисует плитки,
  `kpi` крупнее, `filters`/`toolbar`/`more` свёрнуты. `priority` колонки таблицы
  говорит, что главное для плитки. Правило проверяет `bin/frontend-audit.py`.
- `Ui_Navigation` скрывает пункты со знаком `pro` в меню, мобильном меню и Ctrl+K.
- Переключатель — компонент `mode_switch` (боковое меню, профиль), адрес
  `/ui/mode/<simple|pro>`.
- Подробности и правила для новых экранов — `application/views/components/README.md`,
  раздел «Режимы интерфейса».

Это уровень пользователя (`user.ui_density` из п. 4.1). Профиль организации,
мастер первого запуска и метаданные `field.level` для форм остаются следующими шагами.

## 5. Как подключить MCP-агента

### 5.1. Подготовить безопасный контур

Для тестирования рекомендуется demo-схема в основной dev-базе:

```env
DEMO_STORAGE=schema
DB_DEMO_SCHEMA=promerp_demo
```

Сначала `/demo/setup` должен завершить сборку без пропущенных слоёв. Агент не должен тестировать изменяющие сценарии на `public` с реальными данными.

### 5.2. Выдать первый ключ только для чтения

1. Открыть `/mcp/keys` под администратором.
2. Имя: `LLM QA read-only`.
3. Клиент: название используемого агента, например `Claude`, `Cursor` или `Continue`.
4. Права: `*`.
5. Включить **«только чтение»**.
6. Ограничить срок действия.
7. Сохранить показанный токен `mcp_…`: повторно он не отображается.

`*` вместе с `read_only` удобно для первого аудита: агент видит все читающие инструменты, а mutating-инструменты сервер запрещает независимо от текста prompt.

### 5.3. Настроить HTTP MCP

Для клиента с поддержкой remote HTTP MCP используется конфигурация такого вида:

```json
{
  "mcpServers": {
    "promerp-demo": {
      "url": "https://test.promerp.ru/mcp/demo/discovery",
      "headers": {
        "Authorization": "Bearer mcp_ВАШ_ТОКЕН"
      }
    }
  }
}
```

Название раздела настроек зависит от клиента. Токен нельзя записывать в репозиторий, prompt, скриншоты или общий лог; лучше хранить его в secret/environment настройке клиента.

Для локального клиента рядом с checkout доступен stdio:

```json
{
  "mcpServers": {
    "promerp-local": {
      "command": "/absolute/path/to/bin/console",
      "args": ["mcp:serve", "--key=mcp_ВАШ_ТОКЕН"]
    }
  }
}
```

### 5.4. Проверить подключение

Агент должен сначала вызвать:

1. Найти и вызвать `system.whoami`; если `read_only` не равен `true` — немедленно остановиться.
2. Вызвать компактный `system.tools.summary`, но не полный `system.tools.list`.
3. Через `system.tool.search` найти и вызвать `demo.status` и `demo.counts`.
4. Через поиск найти документацию выбранного процесса и его читающие инструменты.

Все вызовы видны в `/mcp/calls`. Если клиент не подключается, сначала проверить
`GET /mcp/demo/discovery`, затем токен и журнал вызовов. Полный `/mcp` сохраняется
для клиентов, которым действительно нужен каталог всех инструментов.

## 6. Prompt для первого read-only теста

```text
Ты — QA-аналитик производственной ERP. Работай только через MCP-сервер promerp-demo.

Правила:
1. Через system.tool.search найди и вызови system.whoami. Если read_only не равен true — НЕМЕДЛЕННО ОСТАНОВИСЬ и выдай блокирующий отчёт. Не продолжай даже при scope="*".
2. Не вызывай system.tools.list: он слишком велик. При необходимости вызови компактный system.tools.summary, а каждый следующий инструмент находи отдельным system.tool.search.
3. Не проси расширить права и не пытайся вызывать изменяющие tools. В поиске используй mode="read".
4. Найди и проверь demo.status и demo.counts. Если стенд не собран, слои пропущены или ключевые счётчики равны нулю — остановись и составь блокирующий отчёт.
5. Исследуй сквозные цепочки:
   - программа/дефицит → закупка → приёмка;
   - техкарта → производственный заказ → операции цеха;
   - выпуск → контроль качества → документы;
   - первичные данные → аналитические показатели.
6. Для каждого шага проверь, что сущность находится поиском, ссылки между сущностями разрешаются и итоговые количества/статусы согласованы.
7. Не считай пустой результат успешным, если demo-сценарий обещает данные.
8. Не выдумывай отсутствующие факты. В отчёте указывай tool, аргументы, наблюдаемый результат и ожидаемое поведение.
9. В конце выдай:
   - краткий вердикт PASS / DEGRADED / FAIL;
   - блокирующие дефекты;
   - неблокирующие замечания UX;
   - нарушения целостности данных;
   - непокрытые проверки из-за отсутствующих MCP tools;
   - предложения, какие инструменты MCP добавить.
```

## 7. Второй этап: агент с изменениями

После успешного read-only аудита нужно выдать **отдельный** короткоживущий ключ для demo-схемы. Не снимать `read_only` у первого ключа.

Права выдаются по одному процессу, например `erp402_production.*`, а опасные операции должны оставаться с `approval=true`. Агент обязан:

- использовать уникальный `idempotency_key` для каждой логической операции;
- после `awaiting_approval` сообщить человеку номер вызова и ждать решения в `/mcp/calls`;
- проверять результат повторным читающим tool;
- не одобрять собственные вызовы;
- завершать тест отчётом и списком созданных сущностей.

Пример задания:

```text
Создай в demo-контуре один производственный заказ по существующей техкарте, проведи его только до стадии, разрешённой без подтверждения, и проверь резерв/дефицит. Перед каждым изменением покажи план. Используй idempotency_key с префиксом qa-20260917-. Если операция требует approval, остановись и сообщи call_id. Не изменяй существующие заказы и не работай вне demo-сценария.
```

## 8. Что ещё нужно для полноценного агентского тестирования

MCP хорошо проверяет сервисы и данные, но не заменяет браузерный E2E: он не видит сломанную кнопку, фокус, адаптивность или понятность текста. Полный контур должен состоять из трёх агентов/наборов тестов:

1. **MCP domain QA** — целостность процессов и бизнес-правил.
2. **Browser E2E** — формы, навигация, доступность и ошибки UI.
3. **Code/test agent** — unit/integration tests и анализ логов.

Следующие полезные MCP-добавления: `system.health`, структурированный отчёт `/demo` diagnostics, безопасный `test.run`, проверка миграций и ресурс с картой сквозных процессов. Запуск shell-команд через универсальный MCP tool добавлять нельзя; тестовые действия должны быть узкими, типизированными и журналируемыми.
