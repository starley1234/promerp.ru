# Производительность: что проверено, что сделано, что осталось

Разбор статический: в среде разработки этого среза не было PHP и PostgreSQL, поэтому
замеров «до/после» нет. Каждый пункт ниже объясняет, почему он должен помочь, и как это
проверить на стенде.

## Что сделано

1. **Поиск по части строки (`LIKE '%текст%'`) больше не читает таблицу целиком.**
   Списки (контрагенты, договоры, сотрудники, заказы производства, закупки, документы,
   отгрузки, техкарты и др.) ищут по денормализованной колонке `search_text`. Обычный
   btree-индекс по ней работает только для «начинается с». Добавлены GIN-индексы по
   триграммам (`pg_trgm`) — миграции `*_PerformanceIndexes` в каждом модуле-владельце таблицы.
   Для терминов короче трёх символов индекс не помогает (так устроен `pg_trgm`).
   Полезный эффект зависит от локали базы: для кириллицы нужна UTF-8 локаль
   (`ru_RU.UTF-8`/`en_US.UTF-8`); при `C` результаты остаются верными, но без ускорения.
2. **Индексы по реальным путям доступа:** `user_tokens(user_id)`, `users_oauth(user_id)`
   (выход, блокировка, каскад при удалении пользователя), `erp_401_reservations(warehouse_id,
   status)`, `erp_407_proposals(program_id)`, `erp_310_assignments(position_id)`.
3. **Помощники миграций** `add_indexes()`, `add_trigram_indexes()`, `drop_added_indexes()`
   в `Model_Erp111_Migration`: идемпотентны, проверяют имена, не роняют миграцию, если
   `pg_trgm` недоступен (предупреждение в журнале).
4. **Статика:** все свои скрипты шаблона (`theme-init`, `template`, `app`, `smart-reference`),
   jQuery и Font Awesome теперь подписаны версией (`Assets::url`). Раньше `app.js` шёл без
   метки при 30-дневном кэше nginx — после выкладки браузер держал старый скрипт. Версия
   считается по времени и размеру файла, а не по sha1 содержимого на каждый запрос.
   Исправлен путь jQuery в манифесте `Assets` (он указывал на несуществующий файл).
5. **Сжатие и кэш:** gzip в `docker/nginx/default.conf` и `mod_deflate`/`mod_expires` в
   `public_html/.htaccess`; CSS/JS — 7 дней (подписаны версией), шрифты и картинки — 30.
6. **`realpath_cache` в `docker/php/php.ini`:** автозагрузка Kohana ищет каждый класс по
   десяткам каталогов модулей.
7. **`doctor`** предупреждает, если в базе нет `pg_trgm`.

## Почему индексов добавлено немного

Схема уже проиндексирована аккуратно (составные индексы по `status + дата`, частичные
индексы очереди `erp_208_outbox`, `GIN` для JSONB и базы знаний). Скрипт-сверка «колонки
`*_id` без ведущего индекса» нашёл около 150 кандидатов, но почти все — ссылки на другие
модули без внешнего ключа или поля, по которым никто не фильтрует. Добавлять индекс «на
всякий случай» значит замедлять запись, поэтому взяты только пути с подтверждённым запросом.

## Ловушка, найденная и намеренно НЕ включённая

`Kohana::init(['caching' => TRUE])` в `bootstrap.php` выглядит как лёгкая победа (кэш путей
файлов), но в этой сборке `Kohana::cache()` на чтении использует файловый кэш, а при записи
в конце запроса — `Cache::instance()`, чья группа по умолчанию настроена на memcache
(`config/cache.php`). Включение без проверки может на каждом запросе обращаться к
несуществующему memcache. Включать только после проверки на стенде.

## Что сделать на продакшене

- `KOHANA_ENV=PRODUCTION`, `opcache.validate_timestamps=0` (и перезапуск php-fpm при выкладке).
- Убедиться, что в базе есть `pg_trgm` (`php bin/console dev:doctor`).
- Для страниц, которые покажутся медленными, снять `EXPLAIN (ANALYZE, BUFFERS)` и проверить,
  что используется `*_search_trgm`.
- Рассмотреть кэш ролей пользователя на время сессии: сейчас на каждый запрос выполняются
  выборка пользователя и ролей.
