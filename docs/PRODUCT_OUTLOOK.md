# Архитектура и перспективы PromERP: моё мнение (честно, без комплиментов)

**Дата:** 2026-09-15 · **Автор:** агент, который вёл S1–S2 в этом репозитории

> **Статус на 2026-09-18:** это исторический outlook, а не текущий backlog.
> Фактическая сверка выполненного и скорректированный порядок находятся в
> [`DEVELOPMENT_PLAN_2026.md`](DEVELOPMENT_PLAN_2026.md#сверка-с-прежними-рекомендациями-product_outlookmd).

**Вопросы:** стоит ли делать проект вообще; что с архитектурой; расширять
функционал и номенклатуру модулей или углублять то, что есть.

---

## 1. Короткий ответ

**Да, делать — но не «ещё одну ERP», а производственный контур (MES-lite).**
У проекта уже есть то, чего обычно нет у внутренних ERP-самописей: слоистая
модульная архитектура, сервисный слой, ACL, журнал действий, шина событий,
миграции PostgreSQL, автотесты, статический аудит, рабочая dev-среда и —
главное — агентский доступ по MCP, который сейчас есть у восьми модулей
(120 инструментов).

**Номенклатуру модулей расширять не надо.** 22 модуля при пяти реально
замкнутых бизнес-циклах — это перевес «ширины» над «глубиной». Ценность даст не
23-й модуль, а доведение производственного контура (план → закупка → цех →
качество → себестоимость) до состояния, когда его можно внедрить на заводе и
показать деньги на смене.

**Условие, без которого делать не стоит:** нужен хотя бы один живой пилот
(заказчик или свой цех). ERP без пользователя — это хобби, а не продукт:
требования начинают идти не из дорожной карты, а из реальных смен, и это
принципиально меняет приоритеты.

## 2. Что в архитектуре сильно (и это стоит защищать)

| Актив | Почему это редкость и почему работает |
| :--- | :--- |
| **Слоистая вертикальная нарезка** (100–199 ядро, 200–299 данные, 300–399 сущности, 400–599 операции, 800+ агенты/интеграции) | Номер модуля сразу говорит, где он живёт в домене и какие у него зависимости. Новый разработчик (и агент) не тонет |
| **Сервисы как единственная точка правил, контроллер как адаптер** | Одно и то же правило используют страница, JSON API и MCP-инструмент. Это и есть главный архитектурный выигрыш: агент делает ровно то же, что мастер руками, а не «свой путь в данные» |
| **Каждый модуль владеет своими таблицами, чужие — только через сервисы** | Модули можно снимать и заменять: `erp401` не знает таблиц `erp402`, `erp408` — таблиц `erp402`. Связь через события и мягкие ссылки позволила включить цех, не трогая склад |
| **События + журнал действий (erp208 + erp119)** | Факт из цеха доходит до производства одной строкой `Event::fire`, а всё, что случилось, остаётся в журнале: разбирать инциденты можно по данным, а не по памяти |
| **MCP-слой как «третий интерфейс»** | Инструменты объявляет сам модуль (`mcp.php`) — значит, агентская доступность растёт вместе с модулем, а не отстаёт на релиз. Схемы, права, подтверждения, идемпотентность, подсказки `destructive/idempotent` — это уровень, до которого большинство внутренних ERP не доходят |
| **Инженерная гигиена: тесты, smoke, lint, аудит, CI, миграции, baseline долгов** | Проверки дешёвые и быстрые (231 тест < 5 с, аудит 0,3 с) — приятный побочный эффект: ошибки ловятся мгновенно, в т.ч. агентом. Именно так и нашлись дефекты B6/B7 |
| **Документация рядом с кодом** (`README.md` модуля + `ARCHITECTURE` + спринт-отчёты + `AGENTS.md`) | Проект передаваем: новый человек или агент продолжает с любого места без археологии |

## 3. Что настораживает (риски, о которых лучше говорить вслух)

1. **Перевес номенклатуры над глубиной.** 22 модуля, но сквозные циклы закрыты
   в шести: контрагенты, техкарты, склад, производство+цех, планирование,
   закупки. Остальное —
   либо каркас (реестр, аудит, файлы, уведомления), либо legacy (CRM `erp221` —
   15 400 строк на MySQL, MDM `erp229` заменён `erp230`, парсер BOM `erp202`).
   Legacy, который «не портирован, но числится», стоит времени на поддержку
   иллюзии.
2. **Дубли домена не разграничены.** Реестр `erp227` ↔ MDM `erp229`/`erp230`;
   менеджер модулей `erp218` ↔ `erp219`; календарь и смены `erp408` ↔ труд
   `erp411` ↔ пользователи `erp100`. Пока владелец домена не назван прямо, каждый
   следующий модуль будет добавлять третью копию правды.
3. **Продуктовая неполнота для «ERP».** Нет мультикомпании, валют, налогов,
   печатных форм документов, партионного учёта и прослеживаемости, планирования
   мощностей. Для цеха это не критично, для «заменим 1С» — критично.
4. **Синхронные события без очереди.** Сейчас `Event::fire` работает в рамках
   запроса: упал слушатель — упало действие (или потерялось). Для агентов и
   внешних воркеров нужен outbox + воркер с ретраями, иначе «управление
   производством через агентов» упрётся в надёжность доставки.
5. **Права только ролевые.** `can('erp408.terminal')` не умеет «мастер участка
   видит только свой участок». Для одного цеха сойдёт, для нескольких — нет.
6. **Технологический выбор.** Konine 3.4 (форк Kohana) — узкая экосистема: найм
   сложнее, библиотеки беднее. Для этой предметной области это терпимо (здесь
   ценность в правилах, а не в фреймворке), но это осознанное ограничение, а не
   преимущество.
7. **Опасность «инженерной игрушки».** Самая большая угроза проекту — не
   качество кода, а отсутствие внедрений: можно ещё год доводить модули и не
   узнать, что мастеру нужна не карточка операции, а печать сменного задания и
   ввод количества одной кнопкой.

## 4. Расширять функционал или номенклатуру?

**Функционал — да, вглубь. Номенклатуру — нет.**

Что расширять (по возрастанию затрат, все пункты прямо усиливают уже готовое):

| Приоритет | Что | Зачем именно сейчас |
| :--- | :--- | :--- |
| P0 | Закрыть S3: `erp407_planning`, `erp403_procurement`, `erp405_quality` | Эти три замыкают цикл «нужно → купить → получить → проверить»; без них производство работает «на глаз» |
| P0 | Партионный учёт и прослеживаемость (партия материала → заказ → изделие) | То, за что производство платит: претензия к поставщику и разбор брака по партиям |
| P0 | Печатные формы: сменное задание, маршрутный лист, этикетки (порт `erp199` QR) | Мастеру нужен лист на смену; терминал без этикеток неудобен |
| P1 | `erp409_costing` — себестоимость по факту (нормо-часы центра + материалы + брак) | Данные уже пишутся цехом (`worked_sec`, `cost_per_hour`, `qty_scrap`) — модуль только считает |
| P1 | `erp801_analytics` — OEE/загрузка/простои по причинам | Прямая продающая ценность: диаграмма простоев окупает внедрение быстрее, чем учёт |
| P1 | `erp802_integration` в узком виде: 1С, Excel, вебхуки (не «всё подряд») | ERP почти всегда живёт рядом с бухгалтерией; без обмена проект не примут |
| P1 | `erp411_worktime`: смена/табель/сдельная оплата по операциям | Без сдельной оплаты цех не заинтересуется вводом факта |
| P2 | `erp404_documents`, `erp406_maintenance`, `erp410_shipment` | Нужны, но после того, как производственный контур начнёт приносить пользу |

Чего я **не** рекомендую делать (и что можно спокойно заморозить):

* **CRM (`erp221`)** — 15 400 строк legacy на MySQL, вне профиля «производство».
  Держать как есть (или удалить), пока не появится заказчик с деньгами на CRM.
* **Мультикомпания и налоги** — только под конкретный контракт, а не «на будущее».
* **Мобильные приложения и портал** — сначала API (он уже есть у всех модулей),
  клиент пусть делают те, кому надо.
* **Собственный BI, чат, задачи, файлы** — уже переизбыток сервисных модулей.

Словом: **сокращение номенклатуры — такой же прирост ценности, как и
расширение.** Каждая замороженная «игрушка» высвобождает недели на то, что
продаётся.

## 5. Где уникальность (то, ради чего стоит делать именно этот проект)

Большинство MES/ERP для малых и средних производств (10–200 человек) — это
либо дорогие тяжеловесы (SAP, 1С:ERP+УПП), либо таблицы Excel с надстройками.
Ниша проекта — **тонкий, быстрый цеховой контур + планирование + себестоимость,
который ставится за две недели и встраивается в уже существующий учёт**.
И именно здесь агентский слой становится настоящим отличием, а не игрушкой:

* **диспетчер-агент** — сам читает очередь заказов, предлагает раскладку по
  центрам и дням с учётом календаря (S2 это уже умеет, нужен человек на
  подтверждении);
* **помощник мастера** — «почему операция стоит?», «что мешает закрыть заказ?»,
  «сравни план и факт за смену» — на естественном языке по данным журналов;
* **разбор простоев** — LLM классифицирует комментарии и подсказывает причины;
* **внешние Python-воркеры** — оптимизация расписания (OR-Tools), распознавание
  дефектов по фото, разбор входящих документов; они берут работу через MCP и
  возвращают результат через API, не трогая таблицы (позиция — `docs/MCP.md`).

Это позиционирование честнее, чем «ещё одна ERP»: его можно продать заказчику,
у которого 1С уже есть, а MES нет.

## 6. Что я бы сделал в следующие два спринта

1. **S3 по плану**: `erp407_planning` → `erp403_procurement` → `erp405_quality`.
   В каждом — сразу JSON API, права в `acl.php`, тесты, README (правило уже
   работает и не даёт долгу копиться).
2. **Найти пилот** (даже внутренний: один участок, один мастер, один сменный
   терминал на планшете). Смотреть не на код, а на то, что мешает закрыть смену.
3. **Outbox + воркер событий** (`erp208`): таблица исходящих, воркер с ретраями,
   идемпотентные обработчики. Это фундамент и для интеграций, и для агентов.
4. **Идемпотентность на все изменяющие API** (не только MCP): заголовок
   `Idempotency-Key` в JSON API и `idempotency_key` в сервисах — агент и 1С
   должны уметь безопасно повторить запрос.
5. **ABAC хотя бы минимальный**: «мастер участка видит свой участок» (правило
   `erp408.view_own_center`), иначе второй цех станет проблемой.
6. **Печать документов**: сменное задание мастера и маршрутный лист — самое
   частое «верните мне бумагу» из практики.
7. **Метрики продукта**: OEE по центрам, время реакции на простой, доля операций
   с фактом, точность плана — то, что показывают директору.
8. **Разбор legacy**: явно пометить и отложить `erp221`, `erp229`, `erp202`,
   собрать в один отчёт «что не портировано и почему».
9. **CI на живых ветках** (GitHub Actions с PostgreSQL) — сейчас локальные
   проверки зелёные, но регрессии ловятся только на моей машине.
10. **Проверка целостности цеха**: регулярная задача «операции без центра»,
    «маршрут без календаря», «отметки без операции» — мягкие ссылки требуют
    такой гигиены, раз FK нет.

## 7. Как понять, что всё получилось (критерии, а не чувства)

| Метрика | Целевое значение |
| :--- | :--- |
| Пилоты, где система реально используется | 3 (не «внедрено», а «работает смену») |
| Время от начала внедрения до первой закрытой смены | ≤ 2 недели |
| Доля операций, закрытых из системы (не «по памяти») | ≥ 80 % |
| Экономия времени мастера на диспетчеризации | ≥ 1 час в смену |
| Прозрачность простоев | 100 % простоев с причиной и длительностью |
| Стоимость владения (сервер + сопровождение) | ≤ 1 дня админа в месяц |

Если через спринт-два этих цифр нет — значит, мы делаем не продукт, а
инженерную игрушку, и это будет видно раньше, чем ещё 20 модулей.

## 8. Итоговая позиция

* Проект **стоит делать**, потому что у него уже есть три редких качества:
  чистая модульная архитектура под производство, единая точка правил (сервисы)
  и агентский интерфейс, растущий вместе с модулями.
* Проект **не стоит расширять вширь**: приоритет — производственный контур,
  внедряемость и наблюдаемость (OEE, себестоимость, прослеживаемость).
* Проект **стоит проверять внедрением**, а не кодом: следующая польза придёт от
  первого мастера у терминала, а не от 22-го модуля.
