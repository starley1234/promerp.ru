# Архитектура PromERP (анализ текущего состояния)

Документ описывает **реальное** состояние кода на момент анализа (сентябрь 2026),
а не желаемое. Все выводы получены чтением кода и запуском системы.

> **Что здесь актуально, а что нет.**
> Разделы §6–§16 — проектные решения конкретных модулей, они остаются в силе.
> Инвентарь модулей (§2) и цифры первого запуска (§4) — исторический срез:
> они генерируются/обновляются кодом, а не руками.
>
> - актуальный инвентарь: `bin/console module:list` и `docs/MODULE_MAP.md`;
> - контекст одного модуля (таблицы, роуты, права, события, MCP, тесты, зависимости):
>   `bin/console module:context --module=erpNNN_slug`;
> - порядок работы над модулем: `docs/AGENT_WORKFLOW.md`;
> - текущие цифры проверок: `make check`.

## 1. Общая схема

```
                    Браузер
                       │
                  nginx (или php -S + bin/router.php)
                       │  "чистые" URL (index_file = FALSE)
                       ▼
              public_html/index.php
                       │
                       ▼
        application/bootstrap.php  ── Kohana::modules() ──► init.php модулей
                       │                                    (регистрация Route::set)
       ┌───────────────┼───────────────┐
       ▼               ▼               ▼
  Controller       Service          Model (ORM)
  (ErpNNN_*)     (Service_ErpNNN)  (Model_ErpNNN_*)
       │               │               │
       └───────► View (erpNNN/*)       ▼
                                Database_PostgreSQL (pg_* / PDO)
                                       │
                                  PostgreSQL 16
                          (ltree, pgvector, pgcrypto, btree_gist)
```

**Стек (проверено на текущей ветке):** Konine **3.4.0** «PHP84X» (`system/classes/Kohana/Core.php`) + PostgreSQL 16 + PHP 8.4.
PHP 8.1 — минимально допустимая версия, целевая — 8.4 (депрекейшены включены через `STRICT_DEPRECATIONS=1`).

Ключевые параметры ядра (`application/bootstrap.php`):

| Параметр | Значение |
| :--- | :--- |
| `base_url` | `/` |
| `index_file` | `FALSE` (чистые URL) |
| `I18n::lang` | `ru-ru` |
| Таймзона | `Europe/Moscow` |
| Сессии | `native`, `session.save_path = application/sessions` |
| Автозагрузка | Kohana cascade + `vendor/autoload.php` (Composer) |

## 3. Слои и соглашения

### 3.1 Именование

| Сущность | Шаблон | Пример |
| :--- | :--- | :--- |
| Каталог модуля | `erpNNN_slug` | `erp221_crm` |
| Классы | `<Layer>_ErpNNN_<Name>` | `Controller_Erp221_Deal`, `Service_Erp221_DealManager`, `Model_Erp221_Deal` |
| Таблицы | `erp_NNN_*` | `erp_221_deals` |
| Роуты | `erpNNN...` | `/erp208_events/api/...`, `/erp221/deal/index` |
| Миграции | `pgMigration_NNN_ErpNNN_*.php` в `migrations_pg/` | `pgMigration_001_Erp208_Events_CreateTables` |
| Views | `views/erpNNN/<controller>/<action>.php` | `views/erp221/deal/list.php` |

### 3.2 Service layer

Правило из README проекта: **чужие модули не делают запросы к БД напрямую**,
а обращаются к `Service_ErpNNN_*`.

Проверка показала: слой сервисов есть **не во всех** модулях
(`erp118_links`, `erp199_sqr`, `erp202_llm_bom_parser`, `erp221_crm` — смешанно),
а часть логики живёт прямо в контроллерах (`erp230_mdm` — 17 контроллеров на 6 сервисов).

### 3.3 События

Две независимые шины:

1. **Kohana `Event`** (`application/classes/Event.php`) — обёртка над `Event::fire()/listen()`.
2. **erp208 Events Bus** (`Service_Erp208_EventBus`) — Pub/Sub с журналом в БД
   (`erp_208_events`, `erp_208_event_subscribers`), автопроксированием в центр
   уведомлений (erp217) и REST API.

### 3.4 Миграции

* Запуск: `bin/console db:migrate` (CLI, основной путь) либо HTTP `GET /migrate_pg`
  (`Controller_Erp111_Migrate`) — в продакшене HTTP-запуск нужно закрыть ACL/отключить.
* Учёт: таблица `migrations_pg` (`migration`, `applied_at`).
* Базовый класс: `pgMigration` → `Model_Erp111_Migration` (методы `up()`, `down()`,
  `run_query()`, `create_table()`, `drop_table()`).
* Порядок: сортировка по имени файла в каждом модуле, модули — в порядке `Kohana::modules()`.
* **Транзакции есть**: каждая миграция выполняется в `BEGIN/COMMIT` на своём
  подключении (`Database_PostgreSQL::begin/commit/rollback` реализованы через `_command`),
  поэтому DDL в PostgreSQL откатывается целиком.
* **Мульти-БД**: группа подключения берётся из самой миграции (`$_db_group` →
  `Migration::db_group()`), реестр `migrations_pg` ведётся в каждой базе отдельно:
  `default` (основная БД), `mdm` (erp230/erp229), `postgresql_memory` (erp222, эмбеддинги).
* Флаги CLI: `--status`, `--dry-run`, `--module=<имя>`, `--down=<класс>`.

### 3.5 Авторизация и права

* `Auth` (драйвер ORM) + `Model_User` → `Model_Erp100_User` → `Model_Auth_User`.
* Пароль хешируется фильтром модели (`Model_Auth_User::filters()` → `Auth::hash()`),
  т.е. **при создании пользователя из кода пароль хешировать не нужно**.
* Роли: `roles`, `roles_users`; без роли `login` вход невозможен.
* Проверки в контроллерах: `$this->has_role()`, `$this->can()`, ACL-класс `application/classes/ACL.php`.

### 3.6 Работа с БД

* Драйвер `Database_PostgreSQL` (модуль `PostgreSQL`) — на функциях `pg_*`.
* Конфиг: `application/config/database.php` (генерируется из `application/config.dist/database.php`),
  группы: `default` (основная БД, env `DB_NAME`), `mdm` (`DB_MDM_NAME`, для erp230/erp229),
  `postgresql_memory` (по умолчанию основная БД, для erp222), `ontology`
  (`DB_ONTOLOGY_NAME` → `DB_MDM_NAME`).
* Расширения PostgreSQL: `ltree` (иерархии), `vector`/pgvector (эмбеддинги),
  `pgcrypto`, `btree_gist`, `uuid-ossp`.

## 5. Границы применимости и риски

* Система **живая и рабочая** на PHP 8.4 + Konine 3.4.0 + PostgreSQL 16.
* Актуальные риски и долги:

  1. **Composer-зависимости не установлены** — `vendor/` содержит только заглушку
     автозагрузчика. Модули, которым нужны Guzzle, PhpSpreadsheet, PhpWord, dompdf,
     Monolog, Carbon, phpdotenv, Mailer, MQTT/AMQP, CommonMark, в продакшене
     работать не будут до `composer install`. Отслеживает `dev:audit`
     (проверка `dependencies`) и `dev:doctor`.
  2. **Два модуля не портированы на PostgreSQL** — `erp199_sqr`, `erp221_crm`
     (схема в `migrations/` в MySQL-синтаксисе). План — `docs/MODULE_BACKLOG.md`.
  3. **`erp230_mdm` вне обязательного контура** (отдельная БД, автономный остров):
     статус optional/quarantine и критерии возврата — `docs/PROJECT_STATE_AND_PLAN_2026-09-17.md`.
  4. **Покрытие тестами неравномерно**: доменные модули 301/401–412/801/802/804/811
     покрыты сценариями, крупные платформенные (`erp230_mdm`) — существенно слабее.
     Карточка модуля показывает его тесты: `bin/console module:context --module=…`.
  5. **Правила владения данными соблюдаются не везде**: чужие таблицы в SQL видны
     в карточке модуля строкой «чужие в SQL (проверить!)» — это кандидаты на
     переход к сервису владельца.

## 6. Слой Operations: складской учёт (erp401_wms)

Диапазоны ID: `100-199` Core, `200-299` Platform/data, `300-399` Entities,
`400-599` Operations, `800-899` Intelligence. До появления `erp401_wms`
слой Operations (400-599) был пуст: в системе были реестр, MDM, техкарты
и шина событий, но не было операционного контура — движений, остатков, заказов.

### Решения, принятые в модуле

| Вопрос | Решение | Почему |
| :--- | :--- | :--- |
| Где живёт номенклатура | Не дублируется: `item_id` → `erp_227_objects.id` | Реестр erp227 уже ведёт объекты, версии и поиск |
| Как получать наименования | Только через `Service_Erp227_Registry` / `Service_Erp227_Search` | Прямые запросы к чужим таблицам запрещены (см. 3.2) |
| Единицы измерения | Добавлен `Service_Erp227_Registry::get_units()` | Справочник принадлежит реестру, наружу отдаётся сервисом |
| Целостность остатков | Транзакция + `SELECT ... FOR UPDATE` по строке остатка | Иначе параллельные списания уходят в минус |
| История | Журнал `erp_401_movements` append-only | Остаток можно пересчитать из движений |
| Ошибки бизнес-правил | `Exception_Erp401_Stock` + код причины | Текст показываем пользователю, код — для API (HTTP 422) |
| Интеграция | События `erp401.*` в шину erp208 и в локальный `Event` | Подписчики без связанности модулей |
| Уведомления | Подписчик `Service_Erp401_Notifications::on_stock_low` в таблице подписок erp208 | Центр уведомлений erp217 сам разошлёт по каналам |

### Модель данных

```
erp_401_warehouses  1 --- n  erp_401_balances  (склад, item_id) — остаток, резерв, минимум
erp_401_warehouses  1 --- n  erp_401_movements (приход / расход / перемещение / корректировка)
erp_401_warehouses  1 --- n  erp_401_reservations (active -> consumed | released)
                    n --- 1  erp_227_objects  (номенклатура, через сервис реестра)
```

Подробности — в `application/modules/erp401_wms/README.md`.

## 7. Слой Entities: контрагенты (erp301_counterparty)

Второй модуль, написанный уже по соглашениям операции-слоя (`erp401_wms`),
но в другом диапазоне: `300-399` — Entities, справочные сущности, на которые
опираются все расчёты. Контрагент — первая такая сущность: закупка, производство,
отгрузка и документы ссылаются на него, а не заводят свои списки поставщиков.

### Решения, принятые в модуле

| Вопрос | Решение | Почему |
| :--- | :--- | :--- |
| Роли контрагента | `roles jsonb` + GIN-индекс, значение — массив (`["supplier","customer"]`) | один контрагент бывает и поставщиком, и покупателем; фильтр `@>` без join-таблицы |
| Поиск по наименованию | Колонка `search_text` (заполняется в PHP через `mb_strtolower`) + B-tree LIKE | в этом кластере PostgreSQL локаль `C`, поэтому `ILIKE`/`lower()` не складывают кириллицу — «ПЛАТАН» не находился по «платан» |
| Код контрагента | `CP%04d`, следующий номер считает сервис (`next_code`) | человекочитаемый код в документах; последовательность БД не нужна |
| Уникальность | Проверяет модель до записи: код (всегда), ИНН (среди неудалённых), номер договора (внутри контрагента) | понятная ошибка пользователю вместо 500 из constraint |
| Удаление | Мягкое (`is_deleted`), каскадом по контактам, реквизитам и договорам | история договоров нужна после архивации контрагента |
| Скан договора | `file_id` → `erp_212_files`, файлы не дублируются | хранилище одно на систему (erp212) |
| Дубли контрагентов в CRM | Общий справочник вместо таблиц `erp221_crm` | закрывает пункт C2 «дублирование сущностей» |
| Срок договора | Задача `erp301:contracts:actualize` переводит истёкшие в `expired`, `--notice` — напоминания | статус не «протухает» без запроса пользователя |

### Модель данных

```
erp_301_counterparties  1 --- n  erp_301_contacts      (контактные лица, один основной)
erp_301_counterparties  1 --- n  erp_301_requisites    (банк/адрес, одни основные)
erp_301_counterparties  1 --- n  erp_301_contracts     (file_id -> erp_212_files)
                         roles jsonb @> [...]          (supplier / customer / carrier / contractor)

## 8. Слой Platform/data: технологические карты (erp228_tech_cards)

Модуль 228 — «мост» между конструкцией изделия и производством: он превращает
исходник (параметрическую модель или код OpenSCAD) в техпроцесс с операциями,
нормами времени и стоимостью. Порт с MySQL на PostgreSQL выполнен целиком:
схема, сервисы, маршруты, интерфейс, тесты.

### Решения, принятые в модуле

| Вопрос | Решение | Почему |
| :--- | :--- | :--- |
| Откуда берётся техпроцесс | Два режима: LLM (`llm.enabled`) и офлайн-шаблон по типу производства | модуль работает без внешнего API: демо, разработка и тесты не зависят от ключей и сети |
| Разбор ответа модели | `Service_Erp228_Parser` понимает JSON, JSON в ```фенсе, текст и markdown-списки; длительности «25 мин», «1,5 ч», «00:15:00» | модель отвечает нестабильно, а падать из-за формата нельзя |
| Версионность техпроцесса | Каждая генерация — новый документ, у карты одна актуальная версия (частичный уникальный индекс в БД + транзакция) | историю нужно сохранять, а «двух актуальных» быть не может даже при сбое кода |
| Поиск по названию | Колонка `search_text` (PHP `mb_strtolower`) + LIKE | локаль кластера `C`: `lower()`/`ILIKE` не складывают регистр кириллицы (то же решение, что в erp301) |
| Статусы и типы | `VARCHAR` + `CHECK` в БД, подписи и цвета — в статиках модели | ENUM в PostgreSQL неудобен для миграций, а подписи нужны интерфейсу |
| Материалы и остатки | Не дублируются: расход материалов — следующий шаг через `erp401` | модуль описывает «как изготовить», а не «из чего и сколько есть» |
| Секреты LLM | Ключи только в модуле `llm`, в конфиге модуля — флаги поведения | один владелец интеграции вместо ключей в каждом модуле |

## 9. Слой Platform/data: журнал действий (erp119_audit)

`erp119_audit` отвечает на вопрос «кто, когда и что изменил», который до него
не был закрыт: события писались в файловый лог и разбирать спор по ним было
нельзя. Модуль не переписывает чужие сервисы — он подключается к уже
существующим потокам данных.

### Как записи попадают в журнал

| Путь | Когда работает | Почему так |
| :--- | :--- | :--- |
| Прямой вызов `Service_Erp119_Journal::record()` / `change()` | сервис модуля сам знает, что сделал (изменения «до/после», подпись объекта) | в записи есть сравнение полей, а не только факт события |
| Наследие `Audit::log()` | 8 существующих вызовов в других модулях | старый вызов становится настоящей записью журнала, код не переписывается |
| Перенос из шины `erp208` (`erp119:sync`) | события, которые публикуют другие модули | шина уже сохраняет события (outbox), журнал дочитывает их по указателю и не задваивает |

Третий путь — ключевой для эксплуатации: он не добавляет работу в
пользовательский запрос (сбой подписчика не ломает бизнес-операцию) и
разбирается с событиями, которые были опубликованы до включения журнала.
Правило разбора имени события (`erp228.card.created` → модуль `erp228`,
сущность `tech_card`, действие `create`) задаётся в
`config/erp119_audit.php` (`event_rules`), а всё, что правилом не покрыто,
разбирается по конвенции имени, поэтому новые события модулей попадают
в журнал без правок кода.

### Схема

* `erp_119_audit_log` — секционирована по месяцам (`RANGE (occurred_at)`) плюс
  `DEFAULT`-секция: регламент хранения — это `DROP` секции, а не `DELETE`
  миллионов строк; строка с датой из будущего не теряется, а ждёт разбора
  (`erp119:partitions --attach-default`).
* Таблица только на запись: триггер запрещает `UPDATE`/`DELETE` (обслуживание —
  только владельцем таблиц, `SET erp119.maintenance = 'on'` или отключение триггера).
* `event_id` — след события шины: частичный уникальный индекс на каждой секции
  делает перенос идемпотентным (повторное чтение с начала не задваивает записи).
* `erp_119_audit_cursors` — указатель чтения шины (outbox).

### Что видит пользователь

Сводка `/audit`, лента `/audit/journal` с фильтрами (период, модуль, сущность,
действие, важность, автор, поиск), карточка записи с таблицей изменений
«поле: было → стало», история объекта `/audit/journal/entity`, выгрузка CSV,
JSON API и виджет «последние действия» для дашбордов других модулей.
Просмотр и выгрузка журнала сами пишутся в журнал (`source = web`, действие
`read`/`export`) — доступ к персональным данным не бывает безымянным.

### Защита данных

Пароли, токены, ключи и номера карт не пишутся в журнал: `config` →
`redact.keys`/`redact.pattern` (маска `***`), проверка идёт и по имени поля,
и по значению (JWT, `Bearer`, ключи `sk-…`). Длинные значения обрезаются по
`lengths`. Если запись в базу не проходит (например, ещё нет секции месяца),
строка уходит в файл-страховку `application/logs/audit-fallback.log` и
возвращается в базу командой `erp119:sync --replay` — журнал не теряет события
даже при аварии схемы.

### Регламент

| Задача | Расписание | Что делает |
| :--- | :--- | :--- |
| `erp119:sync` | `*/5 * * * *` | дочитывает события шины, по `--reset` перечитывает с начала (без дублей) |
| `erp119:partitions` | `10 3 * * *` | создаёт секции вперёд, разбирает `DEFAULT`, удаляет истёкшие (`--retention`, `--dry-run`) |

Проверки модуля: `bin/test --filter=Erp119` (35 тестов), `make check`
(аудит кода, тесты, дымовой прогон 445 адресов — маршруты и действия чтения API, диагностика среды).

## 10. Слой Operations: производство (erp402_production)

Третий модуль слоя Operations и ядро решения: он превращает план в готовую
продукцию и связывает между собой справочники (`erp227`), нормы (`erp228`),
склад (`erp401`), контрагентов (`erp301`), журнал (`erp119`) и шину (`erp208`).

### Решения, принятые в модуле

1. **Заказ — не документ склада, а диспетчер производства.** Складскими
   движениями владеет `erp401`: заказ только просит «зарезервируй»,
   «спиши», «прими на склад». Прямых записей в `erp_401_*` из `erp402` нет —
   всё через `Service_Erp401_Stock`.
2. **Состав берётся из техкарты, а не вводится руками.** `Service_Erp402_Bom`
   читает `structured_data` через `Service_Erp228_TechCards::actual_document()`
   и обходит дерево (`спецификация`/`materials`/`BOM`, ключи ru/en). Норма
   хранится как «на изделие» (`qty_per_unit`), потребность считается
   `норма × план` и пересчитывается при любом изменении плана.
3. **Несопоставленная номенклатура не блокирует работу.** Точное совпадение
   имени — автоматически, приблизительное — помечается «проверить», без
   совпадения — строка сохраняется с `item_id = NULL`. Заказ можно утвердить,
   такие строки видно в карточке и в отчёте о нехватке.
4. **Нехватка материалов — не исключение.** При выпуске в производство
   строки, которых нет на складе, получают статус `short`, заказ остаётся
   `planned`, пользователь получает отчёт. Исключение возникает только при
   списании в выпуске — там заказ нельзя закрывать «на бумаге».
5. **Частичный выпуск.** `complete($id, $qty)` принимает количество: заказ
   закрывается (`done`) только когда `qty_done >= qty`, иначе остаётся
   `in_progress`. Выпуск идёт в транзакции: сначала списание материалов,
   потом приёмка продукции; ошибка откатывает обе операции.
6. **Действия описуются сервисом, а не видом.** `Orders::allowed_actions()`
   (синоним `transitions()`) — единый источник правды: из него берут кнопки
   карточки, из него же исходит API `transition`. Старт работы разрешён и из
   плана (материалы придут позже), выпуск — и из зарезервированного
   состояния, без отдельного «начать».
7. **Номер заказа — из последовательности.** `erp_402_order_number_seq` выдаёт
   `ПО-ГГГГ-НННННН`; формат не зависит от часового пояса и параллельных
   запросов (в отличие от `COUNT(*) + 1` в старом коде).

### Модель данных

Две таблицы: `erp_402_orders` (заказ: номер, изделие, план и факт выпуска,
статус, приоритет, срок, склады материалов и продукции, заказчик и договор,
плановая себестоимость, `search_text` для поиска по кириллице) и
`erp_402_order_items` (состав: `line_no`, материал, норма, потребность,
списано, резерв, статус строки). Ссылки на другие модули — **мягкие** (без
внешних ключей): модули включаются и выключаются независимо.

Граф статусов: `draft → planned → released → in_progress → done`,
`cancelled` — из любого незавершённого, из `cancelled` можно вернуть в
черновик. Отмена снимает резервы (`Materials::release_all()`) и закрывает
незакрытые операции цеха; удаление заказа удаляет их вместе с ним (заказ, по
которому работа уже идёт, удалить нельзя — сервис отвечает `locked`).

### Маршруты и права

`/production` (сводка), `/production/orders` (список с фильтрами),
`/production/orders/view|edit|save|fill|item/*` (карточка, форма, состав),
`/production/orders/{plan,release,start,complete,cancel,delete}/<id>` (переходы),
`/production/api/*` (JSON: search, get, requirements, stats, transition,
options), `/production/widget/*` (summary, order_card, object_orders).

Права в `application/config/acl.php`: `erp402_production.view` (admin, manager,
accountant), `.manage` / `.plan` / `.complete` (admin, manager),
`erp402_production.*` (admin). Каждое действие карточки проверяет своё право:
смотреть может бухгалтер, планировать и закрывать — мастер и администратор.

### Связь с цехом (erp408_shopfloor)

`Orders::plan_operations()` ищет класс и вызывает
`Service_Erp408_Operations::instance()->plan_order($order, $user_id): int`.

Обратный каскад: `Orders::cancel()` закрывает операции заказа
(`Service_Erp408_Operations::cancel_for_order()`), `Orders::delete()` удаляет их
(`delete_for_order()`), а операция «в работе» или на паузе блокирует удаление
(`locked`). Выполненные операции не переписываются: факт остаётся фактом.
Модуль подключён с S2: вызов уходит в цех, маршрут строится по техкарте, а факт
возвращается событием `erp408.operation.completed` (см. раздел 11). Связь
осталась мягкой: если модуль снять, `class_exists()` вернёт ложь, `plan_operations()`
отдаст `0`, и производство продолжит работать как раньше.

резерв, списание, частичный выпуск, откат при нехватке, отмена, события и
журнал, разбор спецификации, заполнение из техкарты), `make check`, дымовой
прогон `/production*`. Подробности — `application/modules/erp402_production/README.md`.

## 11. Слой Operations: цех (erp408_shopfloor)

Пятый модуль слоя Operations и вторая половина производственного контура:
производство планирует, цех выполняет. Модуль отвечает на вопросы мастера —
«где, когда и что делать, сколько уже сделано».

**Данные.** Пять таблиц `erp_408_*`: рабочие центры и участки, шаблоны смен,
календарь (сколько часов работает центр в конкретный день), операции заказов и
журнал отметок. Операция хранит план и факт (годные, брак, секунды работы и
простоя), статус (`planned → in_progress → paused → done`, плюс `cancelled`) и
мягкие ссылки на заказ и номенклатуру — внешних ключей в чужие модули нет.
Журнал отметок пополняется только добавлением: в терминальном режиме это
основное доказательство того, кто и когда нажал кнопку.

**Правила вместо флагов.** Переходы описаны одной таблицей
(`transitions()` / `allowed_actions()`), поэтому интерфейс, JSON API и агент
получают один и тот же список допустимых действий для текущего статуса, а
сервис отвергает всё остальное с причиной `invalid_transition`. Время работы
считается по отметкам, а не по «нажали старт — пишем секунды»: пауза, простой и
возврат в работу не теряют факт.

**Маршрут из техкарты.** `plan_order()` берёт операции техкарты (erp228) или,
если карты нет, состав заказа и создаёт одну операцию «Изготовление по заказу»;
повторный вызов ничего не дублирует. Назначение на центр и день учитывает
календарь: нерабочая суббота переносится на следующий рабочий день.

**Интерфейсы.** Страницы `/shopfloor` (загрузка дня по центрам), `/shopfloor/operations`
(список и карточка с журналом отметок), `/shopfloor/terminal` (планшет у станка:
крупные кнопки, поиск задания по коду с места), `/shopfloor/centers` и
`/shopfloor/shifts` (справочники и календарь), JSON API `/shopfloor/api/*`
(10 действий), виджеты (`summary`, `order_operations` — маршрут в карточке
заказа, `operation_card`), 19 инструментов MCP (17 из них — с точными
подсказками `destructive`/`idempotent`, чтобы агент не удвоил выработку
повтором).

**Права.** `erp408.view` (admin, manager, accountant), `erp408.manage` (маршруты,
справочники, отмена, удаление), `erp408.terminal` (отметки у станка),
`erp408.*` (admin).

**Связь с производством.** Цех не пишет в чужие таблицы: факт уходит событием
`erp408.operation.completed` с агрегатом по заказу, а `erp402` сам решает, что с
ним делать (журнал заказа). Выпуск продукции по-прежнему оформляет склад
документом `Orders::complete()` — у данных один владелец. Записи в журнал
действий erp119 идут под сущностями `operation`, `work_center`, `shift`
(зарегистрированы миграцией 004 самого аудита).

**Проверки модуля.** `bin/test --filter=Erp408` (20 тестов: справочники,
календарь, маршрут из техкарты, очередь заказов без маршрута, назначение с
переносом на рабочий день, полный цикл отметок, брак и простой, защита от
двойного учёта, событие и журнал), дымовой прогон `/shopfloor*`, `dev:audit`.
Подробности — `application/modules/erp408_shopfloor/README.md`.

Живой сценарий агента (проверен вручную в S2): агент читает очередь
(`shopfloor.queue`), просит разложить маршрут — вызов паркуется как
`awaiting_approval`, мастер подтверждает в `/mcp/console`, дальше агент сам
начинает операцию, отмечает простой и выработку, а завершение снова требует
подтверждения человека.

## 12. Слой Operations: планирование (erp407_planning)

Шестой модуль слоя Operations и «мозг» производственного контура: производство
планирует, цех выполняет, а планирование отвечает на вопрос «что, сколько и
когда заказать или выпустить». Модуль ничего не заводит сам: спрос он берёт из
программы и заказов, состав — из техкарт (erp228), покрытие — из склада
(erp401) и незавершёнки (erp402).

**Данные.** Четыре таблицы `erp_407_*`: программы, строки программ, снимки
потребности и предложения, плюс две последовательности номеров
(`ПП-ГГГГ-НННННН` и `ПЗ-ГГГГ-НННННН`). Внешних ключей в чужие модули нет —
ссылки мягкие (`item_id`, `tech_card_id`, `order_id`, `target_ref`), поэтому
планирование не мешает производству удалять и пересоздавать заказы.

**Снимок вместо «текущего состояния».** Расчёт пишет результат с `run_uuid` и
датой прогона, программа помнит последний расчёт. Это важно по двум причинам:
экраны показывают согласованный набор цифр (а не смесь старого и нового), а
историю прогонов можно разбирать — почему вчера решили заказать именно
столько. Перерасчёт заменяет снимок программы, не трогая чужие данные.

**Расчёт.** Изделия строк разузловываются по составу техкарты до трёх уровней
(`Service_Erp402_Bom`), одинаковые позиции складываются в одну строку спроса.
Покрытие = остаток склада (`Service_Erp401_Stock`) + незавершёнка (заказы
erp402 в статусах `released`/`in_progress`, читаются через сервис производства,
а не запросом в чужую таблицу) + уже размещённые предложения и заказы. Дефицит
округляется до партии по атрибутам номенклатуры (`min_order_qty`,
`order_multiple`, `round_to`), дата заказа считается назад от срока выпуска по
сроку поставки позиции, просроченные помечаются `late`. Позиции без
номенклатуры не считаются «нулевыми» — расчёт сообщает предупреждением, что
остатки по ним не учтены.

**Предложения и исполнение.** Дефициты превращаются в предложения одной
кнопкой, по одной позиции — не больше одного открытого, поэтому повторный запуск
не задваивает. Переходы состояний описаны явно
(`new → approved → exported → done`, плюс `cancelled`), а передача в исполнение
помнит приёмник в `target_ref`: выпуск создаёт заказ производства
(`erp402:<id>`), закупка уходит в `erp403:<id>` — с S4 модуль закупок на
месте, и предложение превращается в настоящую заявку; ветка `waiting:erp403`
с предупреждением осталась для сборки без этого модуля.

**Интерфейсы.** Страницы `/planning` (доска: последний расчёт, дефициты,
очередь решений), `/planning/deficits`, `/planning/programs` и карточка
программы (строки, потребность, предложения, кнопки утверждения и расчёта),
`/planning/proposals`, JSON API `/planning/api/*` (13 действий), виджеты
(`summary`, `item_deficits`, `program_proposals`), 14 инструментов MCP.
Утверждение программы и передача предложения помечены `approval`: агент считает
и предлагает, а заказ порождает человек.

**Права.** `erp407.view` (admin, manager, accountant), `erp407.manage` (программы
и предложения), `erp407.plan` (расчёт, утверждение, создание предложений),
`erp407.approve` (передача в исполнение), `erp407.*` (admin).

**Проверки модуля.** `bin/test --filter=Erp407` (13 тестов: нумерация, жизненный
цикл программы, отказ считать пустую программу, сбор строк из открытых заказов
производства, расчёт с датами и просрочкой, покрытие складом, отсутствие
задвоения предложений, поток утверждение → передача → исполнение (с созданием
заявки закупки), создание заказа производства, страницы на реальных данных,
каталог MCP), дымовой прогон `/planning*`, `dev:audit`.
Подробности — `application/modules/erp407_planning/README.md`.

## 13. Слой Operations: закупки (erp403_procurement)

Седьмой модуль слоя Operations и «руки» контура снабжения: планирование
говорит, что нужно и к какому сроку, закупки — у кого купить, по какой цене и
что из купленного уже приехало на склад. Модуль не заводит своих
справочников: поставщики — контрагенты с ролью «поставщик» (`erp301`),
номенклатура — реестр `erp227`, склад, остатки и минимумы — `erp401`.

**Данные.** Восемь таблиц `erp_403_*` (заявки и их строки, заказы поставщикам и
их строки, приёмки и их строки, цены, условия поставщиков) плюс три
последовательности номеров (`ЗК-`, `ЗП-`, `ПР-ГГГГ-НННННН`). Ссылки на чужие
модули мягкие: модуль включается и выключается независимо, а документы закупки
остаются читаемыми.

**Цепочка документа.** Заявка (`draft → submitted → approved | rejected →
ordered`) отвечает на вопрос «что, сколько, к какому сроку». У неё три
источника: руками, автоматически по минимуму склада и из предложения
планирования (`source = erp407`, в `source_ref` — номер предложения). Заказ
собирается **только из согласованных** заявок: `Orders::from_requests()`
группирует открытые позиции по поставщику, позиции без поставщика получает
рекомендованного (`Suppliers::choose()`), цена берётся из строки заявки или
последнюю известную. Заявка, попавшая в заказ, становится `ordered` — двойной
закупки одной потребности не бывает. Отправка заказа (`send`) фиксирует цены,
приёмка (`ПР-ГГГГ-НННННН`) создаётся из заказа как «то, что ещё не принято», а
проведение приёмки — единственный момент, когда закупка становится складом:
приход в `erp401` (`doc_type = erp403_receipt`), рост `qty_received` строк
заказа, пересчёт заказа в `partially_received`/`received`, запись фактических
цен. Проведённую приёмку отменить нельзя (`already_posted`) — обратное движение
оформляется расходом в модуле склада.

**Цена и поставщик как история, а не атрибут.** `erp_403_prices` хранит, кто,
когда и на каких условиях поставлял позицию; источник цены указан явно
(`order`, `receipt`, `manual`). Сравнение поставщиков считает баллы: цена (до
50), срок поставки (до 30), оценка (×3), пунктуальность (до 15), «основной»
(+10), минимальная партия (−20).

**Качество на входе.** Строка приёмки несёт статус входного контроля
(`pending`/`passed`/`failed`); проваленная позиция **блокирует проведение**
(`quality_blocked`). Правило живёт в сервисе, поэтому одинаково работает и для
человека, и для агента; событие `erp403.receipt.quality` — точка стыковки с
`erp405_quality` (с S5 стык двусторонний: `Inspections::from_receipt_line()`
берёт партию из позиции приёмки, а итог контроля возвращается в строку
приёмки через `Service_Erp403_Receipts::set_quality()`).

**Интерфейсы.** `/procurement` (доска: состояние закупок, что на согласовании,
что не приехало), `/procurement/low-stock` (дефицит склада с предложением
количества), заявки, заказы, приёмки, поставщики с карточкой сравнения, JSON API
`/procurement/api/*` (24 действия), три виджета, 29 инструментов MCP. Печать
заказа поставщику и приёмки отдана документам (`erp404_documents`): шаблоны
`ORDER-SUPPLIER` и `RECEIPT-IN` берут данные этих сервисов. Под
подтверждением человека (`approval`): согласование и отклонение заявки,
отправка и отмена заказа поставщику, проведение и отмена приёмки, автосбор
заявок по дефициту.

**Права.** `erp403.view` (admin, manager, accountant), `erp403.manage`
(черновики, позиции, отправка, условия), `erp403.approve` (согласование и
проведение), `erp403.*` (admin).

**Проверки модуля.** `bin/test --filter=Erp403` (16 тестов: нумерация,
жизненный цикл заявки, отказ согласовать пустую, минимум склада без задвоения,
сбор заказа из заявок, отправка с записью цен, приёмка и входной контроль,
блокировка проведения проваленным контролем, сквозная цепочка «заявка → заказ →
приёмка → склад» с проверкой остатка и состояний, страницы и API на реальных
данных, каталог MCP), дымовой прогон `/procurement*`, `dev:audit`.
Подробности — `application/modules/erp403_procurement/README.md`, итоги —
`docs/SPRINT_S4_erp403.md`.

## 14. Слой Operations: качество (erp405_quality)

Модуль отвечает на вопрос «годится ли эта партия и что делать с браком» — и
доводит ответ до склада. Он не заводит своих справочников: номенклатура —
реестр `erp227` (через `erp401`), склады — `erp401`, поставщики — контрагенты
`erp301`, приёмки — `erp403`. Ссылки на соседей мягкие (без внешних ключей):
модуль включается и выключается независимо, документы качества остаются
читаемыми.

**Путь партии.**

```
партия (приёмка erp403 / заказ erp402 / операция erp408 / вручную)
  → контроль (годная / брак)
  → несоответствия: код дефекта, количество, причина, виновник
  → изоляция на склад карантина
  → решение: как есть / переделать / вернуть поставщику / в утиль / сортировка
  → исполнение решением склада (движение erp401), закрытие контроля
```

**Итог и решение — разные вещи.** `result` ставит проверка, `decision` принимает
человек, и второй может прийти позже. Состояние «итог `failed`, решения нет» —
не незаполненное поле, а партия на карантине, ждущая решения; очередь `pending`
на доске `/quality` и есть рабочее место контролёра. Отдельно: отсутствие
дефектов ещё не значит «годная» — `mark_passed()` действие осознанное.

**Карантин — движение склада, а не пометка.** `quarantine()` перемещает партию
на склад типа `quarantine` через `Service_Erp401_Stock::transfer()`
(`doc_type = erp405_quarantine`), `release()` возвращает её обратно. Пока партия
на карантине, контроль не закрывается и не отменяется. Нет склада карантина —
честная ошибка `warehouse_required` вместо записи «изолировано» без движения.

**Брак исполняется складом.** `scrap` перемещает партию на склад типа `scrap` и
пишет это движение в решение (`movement_ref`), `return` изолирует партию и
публикует `erp405.decision.return` для рекламации поставщику, `rework` —
событие для производства (`erp402`), `use_as_is`/`sort` —
`erp405.decision.accepted`. Если движения нет, в документе этого не написано.

**Входной контроль встроен в закупку.** `from_receipt_line()` берёт позицию
приёмки `erp403` и идемпотентен: одна позиция — один контроль. Итог входного
контроля уходит обратно в приёмку (`Service_Erp403_Receipts::set_quality()`),
снимая или подтверждая блокировку прихода — контракт S4 сработал без правок
закупки.

**Модель данных.** `erp_405_defect_codes` (справочник: категория, важность,
выключение вместо удаления), `erp_405_inspections` (партия, вид контроля,
состояние, итог, решение, карантин, `uuid`), `erp_405_defects` (код дефекта,
количество, причина, важность, мягкие ссылки на заказ/операцию/фото),
`erp_405_decisions` (решение, комментарий, ссылка на движение склада) +
последовательность номеров `ПК-ГГГГ-НННННН`.

**Интерфейсы.** `/quality` (доска: сводка, очередь решений, где теряем
качество, динамика), `/quality/inspections` (+ карточка, форма, переходы),
`/quality/quarantine`, `/quality/defects`, JSON API `/quality/api/*`
(19 действий), три виджета (`summary`, `quarantine`, `receipt_line`),
19 инструментов MCP. Под подтверждением человека (`approval`): списание в
утиль и возврат поставщику.

**Права.** `erp405.view` (admin, manager, accountant, worker), `erp405.inspect`
(контроль и дефекты), `erp405.decide` (решения, карантин, утиль),
`erp405.manage` (справочник кодов).

**Проверки модуля.** `bin/test --filter=Erp405` (17 тестов: справочник и защита
от повторов, нумерация и жизненный цикл, дефект переводит партию в брак,
превышение количества, запрет «годен» при дефектах, карантин и выпуск с
проверкой остатков, списание в утиль с движением, решение только по браку,
запрет отмены на карантине, идемпотентность входного контроля, статистика,
страницы на реальных данных, 403 анонимному API, контракт методов, каталог
MCP), дымовой прогон `/quality*`, `dev:audit`. Подробности —
`application/modules/erp405_quality/README.md`, итоги —
`docs/SPRINT_S5_erp405.md`.

## 15. Слой Operations: документы и печать (erp404_documents)

Модуль отвечает на вопрос «что мы отдали на бумагу и чем это подтверждается».
Три таблицы (`erp_404_templates`, `erp_404_documents`, `erp_404_prints`) и четыре
сервиса.

**Шаблон — рабочий инструмент, а не настройка разработчика.** Тело формы — HTML с
подстановками (`{{ref.number}}`, `{{document.title}}`, `{{meta.date}}`) и блоками
списков (`{{#rows ref.lines}}…{{/rows}}`, внутри — `{{index}}`). Шаблон привязан к
типу объекта; незнакомая подстановка — отказ при сохранении
(`unknown_placeholder`), а не пустое место на бумаге. Правка тела поднимает
версию.

**Документ помнит, чем его печатали.** При выпуске (`issue()`) данные собираются у
владельца, подстановки раскрываются, снимок HTML и версия шаблона
записываются в документ. После этого правки шаблона на выпущенную бумагу не
влияют — это и есть причина, по которой снимок хранится, а не пересобирается при
каждом открытии. Состояния: `draft → issued → printed → archived`, отмена
(`cancelled`) с обязательной причиной и занятым номером `ДК-ГГГГ-НННННН` из
последовательности.

**Данные — только через владельца.** `Service_Erp404_Sources` зовёт сервисы
`erp403` (заказ поставщику, приёмка), `erp402` + `erp408` (состав и маршрут
производственного заказа), `erp405` (паспорт партии), `erp408` (операция цеха) и
отдаёт «печатный» набор: числа в виде `1 250,000`, состояния — подписями.
Выключенный модуль-источник — честная ошибка `dependency`, отсутствующий объект —
`ref_not_found`: бумага не печатается с дырами.

**Печать — событие.** `erp_404_prints` хранит кто, когда и сколько копий;
`print_count` в документе — быстрый счётчик для списков, истина в журнале.
Печатать можно только выпущенное (`not_issued`), форма отдаётся страницей без
макета системы (браузер печатает, журнал ведёт модуль).

**Интерфейсы.** `/documents` (доска: сводка, «что печатаем»), карточка со
снимком и журналом печати, редактор шаблонов с проверкой на реальных данных,
страница печати, JSON API `/documents/api/*` (15 действий, 8 из них — чтение),
13 инструментов MCP. Под подтверждением человека — отмена документа
(номер занят, бумага могла уйти контрагенту).

**Права.** `erp404.view` (чтение), `erp404.print` (черновик, выпуск, печать,
архив, отмена), `erp404.manage` (шаблоны форм).

**Проверки модуля.** `bin/test --filter=Erp404` (10 тестов: стартовые шаблоны,
отказ на подстановку с опечаткой, рост версии при правке тела, жизненный цикл с
журналом печати, запрет правок и перевыпуска после выпуска, независимость снимка
от правок шаблона, экранирование и блоки строк, сводка, объявления и вызовы всех
13 MCP-обработчиков), дымовой прогон `/documents*`, `dev:audit`. Подробности —
`application/modules/erp404_documents/README.md`, итоги —
`docs/SPRINT_S5_2_erp404.md`.

## 16. Слой Intelligence: агентский доступ (erp804_mcp)

Модуль открывает систему LLM-агентам и внешним программам по протоколу MCP
(`2025-06-18`), не забирая на себя предметную логику.

**Как устроено.** Инструменты объявляют сами модули файлом `mcp.php` в своём
корне (`erp403_procurement` — 29, `erp402_production` — 19, `erp408_shopfloor` — 19,
`erp405_quality` — 19, `erp407_planning` — 14, `erp404_documents` — 13,
`erp119_audit` — 3, `erp804_mcp` — 4; всего 120);
`erp804_mcp` отвечает только за ключи агентов (`erp_804_mcp_keys`, токен
`mcp_…` хранится как SHA-256), права (имена те же, что в `acl.php`),
приведение аргументов к JSON-схеме, журнал вызовов (`erp_804_mcp_calls`) и
подтверждения. Транспорты: `POST /mcp` (JSON-RPC, пакеты, уведомления),
stdio (`bin/console mcp:serve`), интерфейс `/mcp/console` (`/mcp` занят
протоколом — в браузере открывать только консоль), `/mcp/tools`, `/mcp/calls`,
`/mcp/keys`, JSON API `/mcp/api/*`.

**Ключевые решения.**
* Опасные операции помечены `approval`: вызов паркуется в статусе
  `awaiting_approval`, человек подтверждает в `/mcp/calls`, обработчик
  выполняется тем же сервисом, что и из интерфейса.
* Идемпотентность через `idempotency_key` (частичный уникальный индекс):
  повтор возвращает прежний результат, не выполняя операцию дважды.
* Признак `self` — инструменты «о себе» (`system.whoami`, `system.call.status`)
  доступны любому действующему ключу: агенту есть чем проверить свою операцию.
* Изменяющие вызовы пишутся и в журнал действий erp119 (`module = erp804`),
  то есть агентская активность видна рядом с действиями людей.

**Идемпотентность.** Оба машинных входа защищены от повтора: у MCP это
`idempotency_key` в `erp_804_mcp_calls`, у JSON API — заголовок
`Idempotency-Key` (таблица `erp_100_api_idempotency`, сервис
`Service_Erp100_Idempotency` в ядре `erp100_base`). Защита включается сама для
любого `Controller_*_Api` на POST/PUT/DELETE и только при наличии ключа:
повтор получает сохранённый ответ (`Idempotent-Replay: true`), тот же ключ с
другим телом — `409 conflict`. Модулям менять ничего не нужно; уборка —
`bin/console idempotency:purge`.

**Дисциплина для модулей.** Если у модуля есть бизнес-сущности, у него должна
быть точка входа: JSON API (`Controller/*/Api.php`) или инструменты MCP.
Проверка встроена в статический аудит: `bin/console dev:audit --check=mcp`
(сейчас замечания только у инфраструктурных `erp100_base`,
`erp111_migrations_postgresql`, `erp118_links`). Замысел, каталог инструментов
и позиция по внешним (в том числе Python) воркерам — `docs/MCP.md`.

**Проверки модуля.** `bin/test --filter=Erp804` (31 тест: реестр инструментов,
ключи и права, JSON-RPC, запреты, идемпотентность, подтверждения и отклонения,
журнал), `bin/console mcp:tools --check`, `make check`.
