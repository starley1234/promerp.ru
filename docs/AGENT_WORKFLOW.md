# Помодульная работа агента (экономно по токенам)

Цель: правка **одного** модуля без чтения репозитория целиком. Доменные модули —
это 28 каталогов `application/modules/erpNNN_*` плюс 1300+ файлов каркаса; если
каждый раз читать всё, бюджет уходит на разведку, а не на работу.

Проверено на текущем репозитории: контекст одного модуля — одна команда и один
экран текста, проверки модуля — ~1 секунда.

---

## 1. Цикл работы

```bash
# 1. Контекст модуля: контракт, таблицы, роуты, права, события, MCP, тесты,
#    зависимости и список файлов, которые стоит прочитать.
bin/console module:context --module=erp401_wms
#    то же короткой целью Makefile:
make context module=erp401_wms

# 2. Прочитать ровно то, что перечислено в блоке «Читать в этом порядке»
#    (README модуля, init.php, migrations_pg, сервис — не больше).

# 3. Правка по контракту (см. раздел 3).

# 4. Проверки только этого модуля (~1 с):
make check-module module=erp401_wms
#    = отчёт линтера по модулю + статический аудит модуля + дымовой прогон
#      его маршрутов + тесты его сценариев (--filter=Erp401)

# 5. Если модуль писал в БД-схему: миграции и их состояние
bin/console db:migrate --module=erp401_wms
bin/console db:migrate --status

# 6. Перед коммитом — полный гейт (несколько секунд):
make check          # framework + lint + audit + test + smoke + doctor + docs-check
```

Если модуль пишет UI — дополнительно `python3 bin/frontend-audit.py`.
Если менялись MCP-инструменты — `bin/console mcp:tools --check`.
Если менялся состав модулей — `make docs` (перегенерировать README/ARCHITECTURE/MODULE_MAP).

## 2. Бюджет чтения

| Что | Когда | Цена |
| :--- | :--- | :--- |
| `bin/console module:context --module=X` | всегда первым | ~1 экран |
| `README.md` модуля | всегда | ~1–2 экрана |
| `init.php`, `mcp.php`, `migrations_pg/*` модуля | если меняются роуты/интерфейс/схема | по файлу |
| Сервис модуля | если меняется поведение | по файлу |
| `docs/AGENT_WORKFLOW.md` (этот файл) | один раз за сессию | 1 экран |
| `docs/MODULE_MAP.md` | когда нужно найти модуль-владельца | 1 строка на модуль |
| `AGENTS.md` | правила, один раз за сессию | 2 экрана |
| Другой модуль | только если меняется контракт между модулями — и точечно | по файлу |

Чего делать не нужно:

* читать `system/` и корневые `modules/` — это вендорный Konine, изменения только
  в `application/`;
* читать `docs/ARCHITECTURE.md` целиком — разделы §6–§16 нужны, только если
  работаете с этим модулем, а инвентарь берётся из `make modules`;
* листать `tests/Unit/*` целиком — карточка модуля называет его тест-файл;
* читать git-историю «на всякий случай» — сначала спросите карточку и README;
* тянуть полный каталог MCP/API в контекст — нужные имена есть в карточке.

## 3. Контракт правки модуля

Владелец данных — модуль. Соседние модули видят только его **сервис** и **события**.

| Слой | Куда | Правило |
| :--- | :--- | :--- |
| Схема | `migrations_pg/pgMigration_*.php` | только новая миграция, идемпотентно, `up()`/`down()`, транзакция раннера |
| Данные | `classes/Model/ErpNNN/*` | `_table_name`, явные `_table_columns`; чужие таблицы не читаем |
| Правила | `classes/Service/ErpNNN/*` | единственный вход в данные модуля; транзакции и `FOR UPDATE` — здесь |
| HTTP | `classes/Controller/ErpNNN/*` | права, разбор запроса, вызов сервиса, ответ; SQL в контроллере не появляется |
| JSON | `classes/Controller/ErpNNN/Api.php` + `application/config.dist/api.php` | read-only действия объявляются явно, изменения — POST/PUT/PATCH/DELETE |
| Агенты | `mcp.php` | tool с `scope`, `mutating`, схемой и structured-ответом; опасное — proposal/approval |
| События | `Service_Erp208_EventBus` через `Event::fire()` | одно событие — одна публикация, payload с UUID/номером |
| Права | `application/config.dist/acl.php` | `erpNNN_slug.ability`; контроллер проверяет `$this->can(...)` |
| Тесты | `tests/Unit/ErpNNN*Test.php` | поведение на реальных строках БД, фикстуры с уникальным префиксом и уборкой |
| Документ | `README.md` модуля | назначение, API сервиса, таблицы, события, права, эксплуатация |

Полный Definition of Done — `AGENTS.md`, §5. Шаблон каркаса — `docs/MODULE_GUIDE.md`.

## 4. Что читать и запускать под конкретную задачу

| Задача | Контекст | Проверки |
| :--- | :--- | :--- |
| Добавить поле/таблицу | карточка → `migrations_pg`, модель | `db:migrate --module=X`, `make check-module module=X` |
| Изменить бизнес-правило | карточка → сервис | `make check-module module=X` |
| Новый экран | карточка → контроллер + `views/erpNNN`, `application/views/components` | `dev:smoke --module=X`, `python3 bin/frontend-audit.py` |
| Новый MCP-tool | карточка (`MCP-инструменты`) → `mcp.php` | `bin/console mcp:tools --check`, `bin/test --filter=Erp804` |
| Интеграция с соседом | карточки **обоих** модулей, блок «Зависит от» / «Используют» | тесты обоих модулей + `make check` |
| Разбор инцидента в модуле | карточка → логи `application/logs/` | `dev:smoke --module=X --all` |
| Порт legacy-модуля (`erp199_sqr`, `erp221_crm`) | `docs/MODULE_BACKLOG.md`, README модуля, `migrations/` (MySQL) | сначала миграции, потом всё остальное |

## 5. Границы и типичные ошибки агента

1. **Не редактировать чужой модуль.** Нужен его контракт — добавить метод его
   сервису (в модуле-владельце) или подписаться на его событие. Прямое чтение
   чужих таблиц запрещено; карточка показывает такие места строкой
   «чужие в SQL (проверить!)».
2. **Не менять уже применённые миграции.** Добавляется следующая: чистка схемы
   в проде недопустима.
3. **Не считать документацию безусловной истиной.** Расхождение кода и README —
   это дефект, который надо починить в том же коммите (или явно сообщить).
4. **Не «делать зелёным» отчёт вместо починки.** Если что-то не запускалось —
   так и написать: «статически проверено», «тест прошёл», «не запускалось».
5. **Не расширять scope молча.** Задача про модуль A, а правка требует изменения
   схемы модуля B — это отдельный шаг; его нужно назвать явно.
6. **Не выдумывать сущности.** Перед добавлением нового справочника — проверить
   `docs/MODULE_MAP.md` и карточки соседей: возможно, владелец уже есть.

## 6. Проверка работы агента (для ревьюера)

```bash
git diff --stat                        # какие модули затронуты
bin/console module:context --module=X  # что должно было измениться
make check                             # общий гейт
git diff --check                       # пробелы/конфликты
```

Признаки хорошего диффа по модулю:

* изменения лежат внутри каталога модуля (+ ACL/API/MCP/тесты/README при
  необходимости), а не размазаны по репозиторию;
* новая миграция, а не правка старой;
* README модуля объясняет новое поведение;
* есть тест на новый сценарий, а не только на наличие файла.
