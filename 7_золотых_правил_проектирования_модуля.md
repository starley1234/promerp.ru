**7 золотых правил** проектирования модуля, адаптированный под стандарт **ID + Slug** (на примере `erp502_tasks`):

### 1. Правило «Черного ящика» (Изоляция БД)
Модуль полностью владеет своими данными. Все таблицы начинаются с префикса `erp[ID]_`.
*   **Пример:** `erp502_tasks`, `erp502_categories`.
*   **Запрещено:** Прямые SQL-запросы или `JOIN` к таблицам других модулей. Если модулю «Отчеты» нужны данные из «Задач», он запрашивает их через Сервис модуля 502.

### 2. Правило именования классов (Только ID)
В именах PHP-классов используйте только ID. Это защищает логику от поломок при изменении названия (слага) модуля.
*   **Пример:** `Model_Erp502_Task`, `Controller_Erp502_Main`.
*   **Зачем:** Чтобы при переименовании модуля из `tasks` в `jobs` вам не пришлось делать Find & Replace по всему коду.

### 3. Правило Сервисного слоя (Толстый Сервис)
Вся бизнес-логика, расчеты и работа с БД выносятся в класс Сервиса. Контроллеры остаются «тонкими».
*   **Класс:** `Mod_Erp502_Service`.
*   **Зачем:** Это единая точка входа для API, консольных задач (Minion) и вызовов из других модулей.

### 4. Правило HMVC-виджетов (Интерфейс)
Любой повторяющийся элемент интерфейса (например, список задач в карточке проекта) оформляется как внутренний контроллер.
*   **Вызов:** `Request::factory('erp502/widget/list')->execute()`.
*   **Результат:** Модуль сам знает, как себя отрисовать. Другим модулям не нужно знать структуру его View.

### 5. Правило событийного общения (Loose Coupling)
Модули общаются через события (Events), чтобы не зависеть друг от друга жестко.
*   **Пример:** При завершении задачи модуль 502 кидает событие `Event::fire('erp502.task_done', $data)`.
*   **Результат:** Модуль уведомлений «услышит» это и отправит письмо, но модуль 502 об этом даже не знает.

### 6. Правило прозрачного расширения (Overriding)
Никогда не меняйте файлы внутри `modules/erp502_tasks/` для нужд конкретного клиента.
*   **Как правильно:** Создайте файл с тем же именем в `application/classes/...`. Kohana сначала ищет файл в `application`, что позволяет переопределить логику модуля, не теряя возможности его обновлять.

### 7. Правило конфигурации и путей
Используйте ID для путей к View и полный слаг для файлов настроек.
*   **Views:** `views/erp502/list.php` (вызов `View::factory('erp502/list')`).
*   **Config:** `config/erp502_tasks.php` (загрузка `Kohana::$config->load('erp502_tasks')`).

### Эталонная структура модуля `erp502_tasks`:

```text
modules/erp502_tasks/
  ├── config/
  │     └── erp502_tasks.php      # Настройки модуля
  ├── i18n/
  │     └── ru.php                # Переводы (ключи вида 'erp502_tasks.title')
  ├── init.php                    # Роуты и регистрация событий
  ├── classes/
  │     ├── Controller/
  │     │     └── Erp502/         # Контроллеры (Main.php, Widget.php)
  │     ├── Model/
  │     │     └── Erp502/         # ORM Модели (Task.php, Category.php)
  │     └── Mod/
  │           └── Erp502/
  │                 └── Service.php # Главный сервис модуля
  └── views/
        └── erp502/               # Шаблоны (layout.php, list.php)
```

**Итог:** Внутри кода (классы, вьюхи) — **ID** (стабильность). В названиях папок, таблиц и конфигов — **ID + Slug** (порядок и читаемость).
